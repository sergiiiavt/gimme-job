# Скасування потрібного стану та можливості відновлення

## Діагностика перед скасуванням

Спочатку виконайте status і перегляньте зміни в індексі та поза ним. Визначте поточну гілку, активну операцію merge/rebase, останній записаний коміт і те, чи помилку вже опубліковано. Перед руйнівними операціями окремо збережіть цінні незакомічені та невідстежувані файли. Резервна гілка захищає коміт, а не всі файли робочого каталогу.

## Вибір за станом, який потрібно змінити

| Потреба | Інструмент | Що спочатку зрозуміти |
| --- | --- | --- |
| Прибрати шлях з індексу | `git restore --staged -- path` | Типово відновлює індекс із HEAD |
| Відкинути редагування відстежуваного файла поза індексом | `git restore -- path` | Перезаписує робочий файл версією з індексу |
| Перебудувати неопублікований останній коміт | `git reset --soft HEAD~1` | Пересуває гілку, зберігаючи індекс і робочі файли |
| Скасувати звичайний опублікований коміт | `git revert COMMIT_ID` | Додає нову зворотну зміну; можливий конфлікт |
| Знайти нещодавнє локальне переміщення посилання | `git reflog` | Локальні записи мають обмежений строк зберігання |

Це альтернативи, а не скрипт для послідовного виконання. До початкового коміту немає знімка HEAD для відновлення; якщо коміт не має батька, `HEAD~1` не існує.

## Restore не є універсальним скасуванням

Звичайний restore для шляху копіює версію з індексу в робоче дерево та відкидає несумісні редагування поза індексом. Якщо небажану зміну вже додано в індекс, звичайний restore не поверне файл до попереднього коміту. За потреби явно вказуйте джерело й ціль, розуміючи обидва перед виконанням.

`git restore --source=COMMIT_ID -- path` відновлює вибраний історичний вміст у робочому дереві; перевірте й додайте його в індекс, якщо плануєте новий коміт. Команда не пересуває поточну гілку назад у часі.

## Кілька наслідків reset

З аргументом коміту reset може пересувати поточну гілку. `--soft` залишає індекс і робочі файли без змін; типовий mixed-режим також скидає індекс, зберігаючи робочі файли. `--hard` додатково перезаписує відстежуваний робочий стан і може видаляти невідстежувані шляхи, які заважають запису. Не використовуйте його як загальне виправлення незбережених змін чи розходження історії.

Reset із шляхом — інша форма, яка змінює записи індексу без пересування гілки. Для навчання простого прибирання з індексу віддавайте перевагу зрозумілішому `restore --staged`.

## Revert зберігає спільну історію

Після вибору справжнього ідентифікатора звичайного коміту `git revert COMMIT_ID` записує нову зміну, яка скасовує його ефект відносно батька. Пізніші зміни можуть спричинити конфлікти. Revert не видаляє старий коміт, не стирає оприлюднений секрет і не відкочує вже розгорнутий сервіс.

Для скасування коміту злиття потрібно обрати основного батька; це також впливає на майбутні злиття. Дослідіть граф і командний релізний процес замість вгадування `-m 1`. Відновлення production може додатково потребувати старішого артефакту, сумісного стану бази та операційної перевірки.

## Відновлення зміщеного коміту

```sh
git reflog --date=iso
git show --stat RECOVERED_COMMIT_ID
git branch recovery/inspection RECOVERED_COMMIT_ID
```

Замініть RECOVERED_COMMIT_ID справжнім переглянутим ідентифікатором і використовуйте вільну назву гілки. Створення гілки відновлення дає коміту ім’я без перезапису поточного робочого дерева. Після цього порівняйте й вибірково інтегруйте потрібне.

Reflog локальний, не є звичайною спільною історією комітів і може очищуватися з часом. Він не гарантує відновлення файла, який Git ніколи не записував, і не замінює резервних копій. Під час пошуку втраченої роботи уникайте збирання сміття та нових руйнівних команд.

## Detached HEAD і незавершені операції

Якщо корисні коміти створено в detached HEAD і ви досі в цьому стані, `git switch -c recovery/my-work` дасть їм назву гілки. Якщо вже перейшли далі, перегляньте reflog. Для активного merge, rebase або cherry-pick читайте status і використовуйте відповідний процес продовження чи скасування замість додавання сторонніх reset-команд.

## Контрольне запитання та відповідь

**Запитання:** Невдалий коміт уже перебуває у спільній main. Чи варто скинути main назад і зробити примусовий push?

**Відповідь:** Зазвичай потрібно додати перевірений revert або виправлення та пройти процес доставки змін. Переписування спільної main може порушити роботу колег і правила гілки. Окремо оцініть міграції даних, зовнішні наслідки й відновлення production.
