# Читання історії та правильне порівняння ревізій

## Почніть із запитання

Оберіть порівняння під конкретне запитання: що не закомічено, що змінилося в одному коміті, чим відрізняються поточні вершини гілок або що внесла функціональна гілка від спільного предка. Навіть переконливий diff може відповідати не на те запитання, якщо його кінцеві точки неправильні.

## Читайте граф, а не лише список

```sh
git log --oneline --graph --decorate --all -15
git show --stat HEAD
git show HEAD -- settings.ini
```

Позначки показують посилання, які вказують на коміти. Лінії графа відображають походження, зокрема кількох батьків у комітів злиття. Час коміту корисний для контексту, але саме граф визначає зв’язки; лише дати не доводять залежності змін. Скорочений ідентифікатор об’єкта може стати неоднозначним, тому для довготривалих доказів використовуйте повний.

## Порівняння знімків і шляхів

`git diff A B` порівнює два підсумкові дерева; `git diff A..B` для diff означає те саме порівняння знімків. Обмежити його одним шляхом можна через `-- settings.ini`. `git diff --name-status A B` допомагає оцінити змінені шляхи, `--stat` узагальнює розмір, а повний diff пояснює вміст.

У цих прикладах замініть A та B відомими назвами гілок, тегами або ідентифікаторами комітів. Не вводьте позначення в кутових дужках з іншої документації як синтаксис shell.

## Дві крапки та три крапки

| Команда | На яке запитання відповідає |
| --- | --- |
| `git log A..B` | Які коміти досяжні з B, але не з A? |
| `git log A...B` | Які коміти належать лише одній зі сторін? |
| `git diff A B` | Чим відрізняються знімки двох вершин? |
| `git diff A...B` | Чим B відрізняється від спільної бази A та B? |

Diff із трьома крапками асиметричний: перестановка A та B змінює сторону, яку порівнюють із базою. Пулреквести на хостингу часто використовують порівняння від спільної бази, але перевіряйте фактичну базу й поточні коміти, а не вважайте всі екрани порівняння однаковими.

## Перевірка гілки відносно оновленої бази

Після `git fetch origin` ці команди переглядають гілку `feature/retry`, якщо відповідні посилання існують:

```sh
git log origin/main..feature/retry --oneline
git diff --stat origin/main...feature/retry
git diff origin/main...feature/retry -- settings.ini
```

`origin/main` відображає останнє отримання даних, а не поточний стан сервера в реальному часі. Fetch не зливає його з локальною main. Якщо база знову зміниться, порівняння для перевірки та результат пробного злиття також можуть змінитися.

## Пошук причини зміни рядка

`git log -p -- path` показує зміни шляху. `git log -S 'retries=' -- settings.ini` шукає зміни кількості входжень рядка; `-G` шукає додані чи видалені рядки, що відповідають регулярному виразу. Це різні запитання. `git blame` пов’язує наявні рядки з комітами; перш ніж робити висновки про намір, прочитайте повідомлення, пов’язані зміни й обговорення.

## Відтворювані докази

Записуйте точний коміт, базу порівняння, команду чи перевірку з помилкою та відповідне середовище. Назва гілки може пересунутися; знімок успішної перевірки без ревізії — слабкий доказ для пізнішого розгортання. Історія Git показує записаний вміст, а не повноту тестів чи успіх релізу.

## Контрольне запитання та відповідь

**Запитання:** Main змінилася після відгалуження функціональної гілки. Чому `git diff main feature` може показувати зміни, яких автор функціональної гілки не робив?

**Відповідь:** Команда порівнює два поточні знімки, тому включає й відмінності, спричинені змінами лише в main. Порівняння від спільної бази виокремлює внесок функціональної гілки; сумісність результату інтеграції перевіряйте окремо.
