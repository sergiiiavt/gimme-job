# Дослідження стану та пошук регресій

## Визначте, що саме виконується

Почніть із кореневого каталогу репозиторію, відкритої ревізії, гілки та локальних редагувань. Потім визначте артефакт, процес і зовнішню конфігурацію, які використовує перевірка з помилкою. Наявність очікуваного коду в каталозі не доводить, що запущений сервіс використовує саме його.

```sh
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short --branch
git log -5 --oneline --decorate
```

Порівняйте це з ревізією та середовищем, зафіксованими CI. Чисте робоче дерево не охоплює ігнорованих результатів збирання, зовнішніх сервісів чи локально встановлених версій залежностей.

## Відокремте проблеми стану від дефектів продукту

| Симптом | Корисна перевірка |
| --- | --- |
| Зміни немає в diff | Перевірте індекс, робоче дерево, ігноровані й невідстежувані файли |
| Гілка здається застарілою | Виконайте fetch, перевірте upstream і порівняйте точні посилання |
| Push відхилено | Розрізніть права, правила й розходження історії в тексті помилки |
| Назви файлів відрізняються лише регістром | Перевірте відстежувані шляхи й поведінку файлової системи |
| Змінився кожен рядок файла | Перевірте кодування, закінчення рядків і атрибути |
| Інтеграція не продовжується | Прочитайте status для merge, rebase або cherry-pick |

Не змінюйте конфігурацію навмання, доки команда не запрацює. Стисло фіксуйте симптом, очікуваний стан і докази для кожної гіпотези.

## Blame дає початок дослідження

`git blame -L 1,20 -- path` пов’язує діапазон рядків із комітами. Це не визначення особистої відповідальності за дефект. Навколишній дизайн міг змінитися пізніше, а форматування — пересунути авторство. Простежте diff коміту, батьківську версію та обговорення; використовуйте історію шляху й пошук рядків, щоб встановити час зміни поведінки.

## Стабільний критерій для bisect

Bisect шукає між відомими справною та несправною ревізіями першу зміну, яка перемикає спостережувану властивість. Оберіть відтворювану перевірку з фіксованими вхідними даними й контрольованим середовищем. Якщо помилка з’являється та зникає незалежно від ревізії, результат може бути оманливим.

Зберігайте виконувану перевірку поза репозиторієм, історію якого переглядаєте, якщо в старих комітах її немає. Забезпечте запуск для кожного кандидата або явно позначайте неперевірювані ревізії. Відсутність інструмента збирання не є доказом регресії продукту.

## Запуск і завершення пошуку

Замініть назви великими літерами перевіреними ідентифікаторами, а абсолютний шлях — шляхом до своєї перевірки. Спочатку збережіть роботу:

```sh
git bisect start
git bisect bad KNOWN_BAD_COMMIT
git bisect good KNOWN_GOOD_COMMIT
git bisect run python3 /absolute/path/check_regression.py
git bisect log
git bisect reset
```

Для `bisect run` код 0 означає справну версію, 1–127 зазвичай означають несправну, крім 125, який пропускає неперевірювану ревізію. Деякі інші коди зупиняють пошук. Перевірка має відрізняти справжню помилку твердження про продукт від збою підготовки середовища. Надмірні пропуски можуть залишити кілька можливих перших несправних комітів замість одного.

## Підтвердження кандидата

Відтворіть помилку на знайденому коміті та очікувану правильну поведінку на відповідному батьку з тими самими вхідними даними. Перегляньте зміну та її залежності. Для історії з багатьма злиттями визначте, що саме потрібно знайти: першу інтеграцію в основну лінію чи початкову функціональну зміну; батьківські зв’язки та додатковий пошук за first-parent змінюють запитання.

Bisect знаходить перехід за вашим критерієм, а не повне пояснення причин. Спостережуваний перехід можуть пояснювати прапорець функції, міграція даних або припущення тестової перевірки.

## Фіксація доказів і повернення стану

Запишіть ідентифікатори справної та несправної версій, команду перевірки, середовище, кандидата й підтвердження. Після дослідження виконайте `git bisect reset`, щоб вийти зі стану пошуку. Якщо відтворення потребує незакомічених чи приватних даних, опишіть залежність, не публікуючи самі дані.

## Контрольне запитання та відповідь

**Запитання:** Стара ревізія не збирається через відсутній історичний набір інструментів. Чи має bisect-скрипт повертати той самий результат, що й за дефекту продукту?

**Відповідь:** Ні. Відновіть сумісне середовище або явно пропустіть неперевірювану ревізію. Інакше пошук може знайти межу сумісності інструментів замість потрібної регресії.
