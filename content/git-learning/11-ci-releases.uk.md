# Від ревізії до доставки змін

## Стани Git, CI та production

Коміт записує код. CI виконує налаштовані перевірки. Розгортання публікує артефакт і конфігурацію в середовище. Це окремі події з окремими доказами. Злитий коміт не доводить оновлення production, а успішне розгортання — правильності всіх сценаріїв продукту.

Простежуйте реліз від ревізії коду до зібраного артефакту, цільового середовища та спостережуваної поведінки. Зберігайте цей зв’язок і тоді, коли хостинг створює синтетичну ревізію злиття для PR чи черги.

## Яку саме ревізію перевірили

Віддавайте перевагу відтворюваним командам, які розробники можуть виконати локально, а CI — у чистому робочому каталозі. Встановлюйте оголошені залежності, запускайте відповідні перевірки стилю, типів, вмісту, тестів і збирання та за потреби зберігайте діагностичні артефакти. Секрети розгортання не повинні бути доступними довільним недовіреним внескам.

Процес для PR може перевіряти вершину гілки або згенерований результат злиття залежно від конфігурації. Досліджуйте спосіб отримання коду й ревізію, а не припускайте. Результати для попередньої вершини чи іншої бази інтеграції можуть уже не підтверджувати поточну пропозицію.

## Виконання правил на стороні приймання

Захищені гілки або правила репозиторію можуть вимагати перегляду, успішних перевірок, лінійної історії чи обмежувати оновлення. Точна поведінка залежить від налаштувань хостингу та прав. Локальні hooks дають швидкий зворотний зв’язок, але є локальним кодом, можуть бути відсутніми й часто допускають обхід; вони не забезпечують серверної авторизації.

Використовуйте унікальні змістовні назви обов’язкових перевірок і розрізняйте пропущений, незавершений та успішний стани. Workflow, який не запускається для зміненого шляху, може залишити обов’язкову перевірку в очікуванні. Виправляйте конфігураційний контракт, а не мовчки обходьте релізну умову.

## Теги позначають точки релізу

У чистому репозиторії на потрібному перевіреному коміті цей локальний приклад створює анотований навчальний тег:

```sh
git rev-parse HEAD
git tag -a v0.1.0-lab -m "Local collaboration lab release"
git show --no-patch v0.1.0-lab
```

Використовуйте вільну назву. Легкий тег є прямим посиланням; анотований має об’єкт із повідомленням і метаданими та може бути підписаний. Створення локального тегу його не публікує. За наявності дозволу надсилайте конкретний потрібний тег, а не всі сторонні локальні теги.

Узгодьте незмінність опублікованих релізних тегів. Технічно Git може пересунути посилання, але зміна тегу після його отримання споживачами руйнує припущення, що назва релізу визначає один артефакт. Сторінка релізу на хостингу й тег Git пов’язані, але є різними об’єктами.

## Підписи та походження артефактів

Підпис коміту чи тегу може підтверджувати, що певний ключ підписав об’єкт відповідно до правил довіри. Він не доводить, що власник перевірив код, залежності безпечні чи розгорнутий артефакт зібрано саме з нього. Дані про походження артефакту та перевірені вхідні дані збирання покривають іншу частину цього ланцюга.

## Термінові виправлення та перенесення

Перед виправленням визначте розгорнуту версію й підтримувану гілку. Переносьте перевірену зміну через cherry-pick лише після аналізу залежностей; тестуйте її зі справжніми версіями залежностей і схеми старішої гілки. Потім внесіть еквівалентне виправлення до інших уражених підтримуваних ліній, щоб майбутній реліз не повернув дефект.

Явно опишіть аварійний процес: хто схвалює, які перевірки залишаються обов’язковими, як відновити попередній стан і як зафіксувати подальші дії. Терміновість не змінює того, на який стан впливає команда Git.

## Перевірка після доставки

Підтвердьте запуск production-процесу для злитої ревізії, розгортання його артефакту, успішні перевірки стану та видиму потрібну поведінку. Якщо інтерфейс має старий вигляд, перевірте кеш або версії ресурсів. Міграції бази, секрети та зовнішні інтеграції можуть змінювати поведінку правильного коду між середовищами.

## Контрольне запитання та відповідь

**Запитання:** Main має успішні перевірки, а тег релізу існує. Чи можна сказати, що виправлення розгорнуте?

**Відповідь:** Ще ні. Перевірте запуск розгортання та цільове середовище, визначте доставлену ревізію або артефакт і перевірте живу поведінку. Посилання Git і результати CI описують лише частину процесу доставки.
