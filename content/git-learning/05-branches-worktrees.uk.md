# Гілки, незавершені зміни та паралельні задачі

## Гілка позначає напрям роботи

Створюйте гілку від ревізії, яку збираєтеся розвивати. Її назва описує призначення, але не ізолює віддалені залежності, локальні бази даних чи інші файли поза Git. Короткоживучі гілки скорочують час розходження змін, однак назви та тривалість роботи визначає команда.

У клонованому репозиторії спочатку збережіть локальні редагування, отримайте дані й явно оновіть main. Приклад передбачає наявність `origin/main` і чисте робоче дерево:

```sh
git fetch origin
git switch main
git merge --ff-only origin/main
git switch -c feature/retry
git status --short --branch
```

Якщо fast-forward неможливий, дослідіть розходження; не примушуйте main перейти в інший стан лише заради успіху команди. У локальному репозиторії з розділу 3 віддаленого репозиторію ще немає: створіть гілку безпосередньо від записаного коміту через `git switch -c feature/retry`.

## Перемикання не завжди прибирає редагування

Git може перенести сумісні незакомічені зміни під час перемикання гілки. Деякі перемикання, які перезаписали б зміни, він відхиляє. Тому факт перемикання гілки не доводить чистоту середовища. Перевіряйте status до та після перемикання, особливо під час відтворення дефекту або релізних перевірок.

Перемикання змінює відстежувані файли, але не обов’язково видаляє ігноровані результати збирання, кешовані залежності чи дані. Правильна ревізія та відтворюване середовище збирання — окремі вимоги.

## Тимчасове збереження через stash

```sh
git stash push -u -m "WIP before investigating a release"
git stash list
git stash show --stat 'stash@{0}'
git stash apply 'stash@{0}'
git status --short
```

Ця послідовність створює новий stash лише за наявності змін для збереження. `-u` включає невідстежувані, але не ігноровані файли. `apply` залишає stash, щоб результат можна було перевірити до явного видалення запису. `pop` також намагається видалити stash після успішного застосування; за конфліктів запис може залишитися. Якщо записів кілька, вказуйте потрібний явно.

Stash локальний і може конфліктувати під час повторного застосування. Він не є перевіреним комітом, механізмом синхронізації з командою чи надійною резервною копією. Для довшої роботи тимчасова гілка з чітко позначеним WIP-комітом іноді зрозуміліша.

## Кілька робочих дерев

У репозиторії з локальною main створіть окрему гілку та каталог:

```sh
git worktree add -b fix/release ../git-release-worktree main
git worktree list
```

Пов’язані робочі дерева спільно використовують об’єкти репозиторію та більшість посилань, але мають окремі файли, індекси й HEAD. Git зазвичай не дозволяє відкрити одну гілку у двох робочих деревах одночасно. Використовуйте різні гілки, а не звично обходьте цей захист.

Встановлюйте потрібні залежності у відповідному робочому дереві. База даних, назва контейнера чи фіксований порт застосунку все ще можуть бути спільними поза Git. Робочі дерева ізолюють каталоги коду, а не всі ресурси виконання.

## Свідоме прибирання

Коли додаткове робоче дерево чисте, а його роботу збережено, приберіть його через `git worktree remove ../git-release-worktree`. Збереження чи видалення відповідної гілки — окреме рішення. `git branch -d feature/retry` перевіряє безпечність видалення за історією злиття; `-D` обходить цю перевірку. Після squash-злиття еквівалентні зміни можуть існувати в main без початкових комітів як предків, тому відмова видалення сама собою не доводить відсутність функціональності.

## Вибір відповідного інструмента

Використовуйте гілку для цілісної зміни, stash — для короткої перерви, а робоче дерево — для одночасної роботи з кількома ревізіями. Жоден інструмент не замінює спілкування, коли двоє людей змінюють ту саму функціональність. Перед передачею роботи опублікуйте потрібні коміти в узгодженій гілці та поясніть, що залишилося незавершеним.

## Контрольне запитання та відповідь

**Запитання:** Ви перейшли на main, але досі відтворюєте поведінку лише з функціональної гілки. Чи обов’язково це помилка Git?

**Відповідь:** Ні. Перевірте перенесені локальні редагування, ігноровані згенеровані файли, запущені процеси, зовнішній стан і фактично відкритий коміт. Самих назв гілок недостатньо для визначення всього середовища виконання.
