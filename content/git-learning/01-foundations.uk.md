# Git: основи й послідовність навчання

## Результати та передумови

Навчіться пояснювати, що записує Git, де зараз перебуває зміна та яка операція може вплинути на колег. Потрібні базові навички роботи з файлами й терміналом; знання програмування допоможуть із прикладами, але не є обов’язковими. Команди розраховані на Git 2.28 або новіший і POSIX shell. У Windows використовуйте Git Bash або WSL; графічні клієнти працюють із тією самою моделлю репозиторію.

Цей шлях опубліковано зі статусом **«Потребує перевірки»**. Спочатку розбирайте пояснення та перевіряйте результат у навчальному репозиторії, а вже потім застосовуйте незнайомі операції зміни історії в командному проєкті.

## Git і сервіс хостингу

Git — розподілена система керування версіями. Звичайний повний клон зберігає історію проєкту локально, тому коміти, порівняння ревізій і створення гілок не потребують доступу до хостингу. Неглибокі та часткові клони навмисно обмежують локально доступні дані.

GitHub, GitLab і Azure Repos зберігають репозиторії та додають права доступу, пулреквести, перевірку коду й автоматизацію. Пулреквест — процес сервісу хостингу, а не об’єкт Git. Локальний коміт сам собою нічого не завантажує на сервер, не запускає віддалений CI і не розгортає сервіс.

## Знімки стану та об’єкти

Коміт посилається на знімок дерева файлів і містить метадані, повідомлення та посилання на батьківські коміти. Об’єкти tree описують записи каталогів, а blob — вміст файлів. Git повторно використовує незмінені об’єкти, тому не мусить копіювати весь проєкт для кожного коміту. Ідентифікатор коміту залежить від вмісту й метаданих, зокрема батьківських зв’язків; це не порядковий номер ревізії.

Зміна повідомлення або відтворення коміту на іншій базі утворює інший ідентифікатор. Наявні коміти не редагуються на місці. Git виявляє зміни вмісту, але не визначає, чи правильно працює застосунок.

## Три стани, які потрібно перевіряти

| Розташування | Значення | Типова перевірка |
| --- | --- | --- |
| Робоче дерево | Поточні файли та їхні редагування | `git diff` |
| Індекс, або staging area | Запропонований вміст наступного коміту | `git diff --cached` |
| Поточний коміт | Записаний знімок, вибраний через HEAD | `git show HEAD` |

`git add` копіює вибраний вміст в індекс саме в момент виконання. Наступне редагування створює новішу зміну в робочому дереві. Коміт записує індекс, який може відрізнятися від видимого файла. Невідстежувані файли ще не мають закоміченої версії; порожні каталоги не відстежуються як окремі записи.

## Гілки, HEAD і досяжність

Гілка — рухоме посилання на коміт. Зазвичай HEAD посилається на поточну гілку; новий коміт пересуває її вперед. Тег переважно позначає фіксовану точку релізу. У стані detached HEAD посилання HEAD указує безпосередньо на коміт: створювати коміти можна, але для збереження зручного постійного імені роботи створіть гілку.

Гілка не є окремою папкою чи копією всіх файлів. Кілька назв гілок можуть указувати на той самий коміт, а видалення назви гілки не обов’язково відразу видаляє її коміти.

Розділ 9 пояснює відновлення, а розділи 10–11 пов’язують Git із перевіркою коду та доставкою змін. Завершують шлях діагностика, безпека та локальна лабораторія співпраці.

## Перша перевірка

У наявному репозиторії ці команди переглядають стан, не створюючи комітів:

```sh
git status --short --branch
git log -5 --oneline --decorate
git diff
git diff --cached
```

Порожній diff не доводить відсутність змін: невідстежувані файли видно в status, а підготовлені до коміту — в cached diff. До першого коміту `git log` повідомляє, що поточна гілка ще не має комітів; це очікувано.

## Контрольне запитання та відповідь

**Запитання:** Ви додали файл в індекс, знову відредагували його й створили коміт без повторного додавання. Яка версія потрапить у коміт?

**Відповідь:** Версія з індексу. Пізніше редагування залишиться в робочому дереві. Перевіряйте обидва diff, а не припускайте, що коміт міститиме все, що зараз показує редактор.
