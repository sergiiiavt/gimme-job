# Свідомий відбір змін і змістовні коміти

## Перегляньте стан перед додаванням в індекс

Продовжуйте в порожньому репозиторії `git-lab` із розділу 2. Status розрізняє невідстежувані зміни, зміни в індексі та зміни поза ним. У короткому форматі перша колонка зазвичай описує індекс, а друга — робоче дерево; нерозв’язані конфлікти мають окремі коди. Файл може мати позначки в обох колонках, якщо ви підготували одну версію, а потім знову відредагували його.

## Створення першого знімка

```sh
printf 'retries=1\n' > settings.ini
printf 'A local Git learning project.\n' > README.md
git add -- README.md settings.ini
git diff --cached
git commit -m "Add initial retry configuration"
git status --short
```

Очікуйте початковий коміт із двома файлами, після якого немає незбережених змін. Повідомлення описує результат; у тілі можна пояснити причину, важливі обмеження та спосіб перевірки. Змістовний коміт достатньо цілісний, щоб його можна було окремо перевірити, протестувати й за потреби скасувати.

## Додавайте саме потрібний вміст

`git add -- path` додає поточний вміст цього шляху в індекс. `git add -p` дозволяє обирати фрагменти, але вибрана підмножина все одно може бути неповною або некоректною. `git diff` порівнює робочі файли з індексом, а `git diff --cached` — індекс із HEAD. Перевіряйте обидва порівняння, коли файл містить різні зміни.

`git commit -a` додає в індекс зміни й видалення відстежуваних файлів, але не додає нові невідстежувані файли. Масове додавання через `git add .` може захопити згенеровані результати або секрети. Поки не розумієте весь diff, краще вказуйте конкретні шляхи.

## Версія в індексі та версія поза ним

```sh
printf 'retries=2\n' > settings.ini
git add -- settings.ini
printf 'retries=3\n' > settings.ini
git diff --cached
git diff
git restore --staged -- settings.ini
git status --short
```

Перший diff пропонує замінити 1 на 2, а другий показує пізнішу зміну з 2 на 3. Скасування додавання в індекс повертає запис індексу до HEAD і залишає робочий файл зі значенням 3. Коли будете готові, додайте потрібну остаточну версію; не створюйте коміт навмання лише тому, що файл у редакторі має правильний вигляд.

## Ігноровані й відстежувані файли

Файл `.gitignore` у репозиторії поширює правила виключення згенерованих або локальних файлів; `.git/info/exclude` діє лише локально. Ігнорування не припиняє відстеження вже закоміченого файла й не забороняє явне примусове додавання. Перевірити правило можна через `git check-ignore -v -- path`.

Якщо локальний файл налаштувань уже відстежується, узгодьте перехід на шаблон у репозиторії та ігнорований робочий файл. `git rm --cached -- path` прибирає відстежуваний шлях із наступного знімка, залишаючи робочу копію; історичний вміст залишається в Git. Це не видалення секрету.

## Зручні для перевірки зміни

Не змішуйте без причини форматування, оновлення залежностей, перейменування та зміни поведінки. Використовуйте `.gitattributes` для узгодженої нормалізації тексту; не виправляйте величезний diff закінчень рядків простим приховуванням пробілів із припущенням, що поведінка не змінилася. Git часто визначає перейменування за подібністю вмісту, а не зберігає постійну подію перейменування.

Перед комітом перегляньте `git diff --cached --stat`, повний diff індексу та `git diff --cached --check`. Остання команда виявляє деякі проблеми з пробілами й маркерами конфліктів, але не запускає тести й не перевіряє зміст застосунку.

## Amend і межа спільної історії

`git commit --amend` замінює поточний останній коміт новим комітом із поточним індексом та оновленими метаданими. Він не дописує маленьке редагування до старого коміту. Використовуйте amend для власної неопублікованої роботи; після публікації узгоджуйте зміну з усіма, хто може залежати від старого коміту, та дотримуйтеся правил гілки.

## Контрольне запитання та відповідь

**Запитання:** Ви додали `.env` до `.gitignore`, але Git досі показує його зміни. Чому?

**Відповідь:** Файл уже відстежувався. Визначте, як прибрати його з майбутніх знімків, і замініть скомпрометовані облікові дані, якщо він містив секрети. Правило ігнорування не переписує історію й не відкликає доступ.
