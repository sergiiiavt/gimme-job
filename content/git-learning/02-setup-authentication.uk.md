# Налаштування, автор комітів і автентифікація

## Вибір і перевірка встановлення

Встановіть Git з офіційного інсталятора або підтримуваного джерела пакетів вашої ОС, потім виконайте `git --version`. У цьому шляху використовуються `switch`, `restore` та `init --initial-branch`; наведені команди потребують Git 2.28 або новішого. На macOS можуть співіснувати кілька встановлень, тому перевірте, які виконувані файли використовують термінал та IDE. У Windows синтаксис прикладів підтримує Git Bash.

Оберіть редактор, у якому впевнено вмієте зберігати файл і завершувати роботу. Коміт, злиття або rebase можуть відкрити його й очікувати; термінал, який здається завислим, іноді просто чекає закриття редактора.

## Створення навчального репозиторію

Виконайте команди в батьківському каталозі, де ще немає `git-lab`. Навчальні дані автора вигадані й налаштовуються лише для цього репозиторію.

```sh
git init --initial-branch=main git-lab
cd git-lab
git config --local user.name "Course Learner"
git config --local user.email "learner@example.invalid"
git status
```

Для справжньої роботи використовуйте ім’я та адресу, які вимагає команда. Локальні налаштування репозиторію мають пріоритет над звичайними користувацькими значеннями. Окреме налаштування можна переглянути через `git config --show-origin --get user.email`; не поширюйте повний вивід конфігурації, адже там можуть бути приватні URL або дані, пов’язані з обліковими даними.

## Клонування наявного проєкту

Клонування створює локальний репозиторій, налаштовує віддалений репозиторій, зазвичай із назвою `origin`, і відкриває його типову гілку. Перш ніж виконувати цей окремий приклад поза іншим робочим каталогом, замініть OWNER та REPOSITORY:

```sh
git clone https://github.com/OWNER/REPOSITORY.git
cd REPOSITORY
git remote -v
git status --short --branch
```

Не ініціалізуйте другий репозиторій усередині клонованого проєкту. Перед виконанням перегляньте README та скрипти налаштування: отримання коду й довіра до процесу його збирання — різні рішення. Типова гілка репозиторію не обов’язково називається `main`.

## Автор коміту не є автентифікацією

`user.name` та `user.email` стають метаданими коміту. Вони не виконують вхід у GitHub і не надають доступу. Для отримання чи надсилання даних приватного репозиторію використовується транспортна автентифікація: переважно HTTPS із менеджером облікових даних або токеном чи SSH із ключем, дозволеним на хостингу.

Для HTTPS використовуйте підтримуваний хостингом вхід або менеджер облікових даних. Не додавайте токен до URL клонування, повідомлення коміту, знімка термінала чи файла проєкту. Для SSH зберігайте приватний ключ у таємниці, передавайте лише публічний і звіряйте незнайомі відбитки ключів сервера з офіційною інформацією сервісу. Організаційний SSO може вимагати додаткового дозволу навіть після успішної автентифікації облікового запису.

## Область дії налаштувань

`--local` змінює цей репозиторій, а `--global` — користувацькі типові значення. Перед зміною правил merge, pull чи закінчень рядків прочитайте командну політику. Під час навчання задавайте поведінку безпосередньо в команді, наприклад `git pull --ff-only`, щоб успадковане налаштування непомітно не обрало іншу стратегію інтеграції.

Якщо працюєте з кількома робочими обліковими записами, локальні або умовні налаштування допоможуть розділити авторство. Підписування комітів — ще один рівень конфігурації; воно не замінює транспортну автентифікацію й не доводить правильність коду.

## Текст на різних платформах

Якщо команді потрібна однакова обробка закінчень рядків, відповідні правила варто зберігати у `.gitattributes`. Наприклад, `* text=auto` вмикає нормалізацію тексту, а `*.sh text eol=lf` задає LF для shell-скриптів. Не нормалізуйте весь наявний репозиторій без узгодження: це може створити величезний diff і приховати функціональні зміни. Обговоріть правило та винесіть нормалізацію в окрему перевірену зміну.

## Перевірка готовності

Ви маєте знати кореневий каталог репозиторію, поточну гілку, адресу автора, URL віддаленого репозиторію та підтримуваний спосіб автентифікації. Успішне клонування підтверджує доступ на читання на той момент; воно не підтверджує право на push, відповідність правилам гілки чи дозвіл на розгортання. Публічні репозиторії часто можна клонувати без входу.

## Контрольне запитання та відповідь

**Запитання:** Ви налаштували правильну адресу автора, але push повертає помилку авторизації. Що перевіряти?

**Відповідь:** URL віддаленого репозиторію, фактичний обліковий запис HTTPS/SSH, дозвіл для токена чи ключа, організаційний SSO та права на репозиторій. Зміна автора коміту не виправить транспортну авторизацію.
