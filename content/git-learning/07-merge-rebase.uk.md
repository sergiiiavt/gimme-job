# Свідома інтеграція змін

## Почніть із походження та відповідальності

Перед інтеграцією отримайте потрібні віддалені дані, перегляньте граф і збережіть незакомічені зміни. Визначте, чи гілка особиста, спільна або захищена та яких правил історії очікує команда. Merge, rebase і cherry-pick розв’язують різні задачі; жодна команда не замінює перевірку підсумкової поведінки.

## Fast-forward і коміти злиття

Якщо поточна гілка є предком цільової, fast-forward пересуває її посилання до цілі без створення коміту злиття. Якщо обидві сторони мають власні коміти, звичайне злиття об’єднує їх від спільного предка й у разі успіху створює коміт із кількома батьками.

У функціональній гілці після отримання даних origin:

```sh
git merge origin/main
git status
git log --oneline --graph --decorate -10
```

Це вносить main у функціональну гілку, а не навпаки. Команда може виконатися автоматично, зупинитися через конфлікт або відкрити редактор повідомлення. Злиття з `--no-ff` вимагає явного коміту злиття навіть тоді, коли можливий fast-forward. Корисність такого запису визначають правила команди.

## Rebase відтворює послідовність роботи

В особистій неспільній гілці альтернативою є:

```sh
git branch backup/retry-before-rebase
git rebase origin/main
```

Використовуйте унікальну назву резервної гілки. Rebase відтворює вибрані зміни на новій базі; звичайні відтворені коміти отримують нові ідентифікатори через зміну батьків. Порожні або вже застосовані зміни можуть оброблятися по-різному залежно від параметрів і поведінки Git. Перевіряйте підсумковий diff, а не кількість ідентифікаторів як доказ збереження поведінки.

Не виконуйте обидва приклади автоматично як один рецепт: це альтернативні рішення інтеграції. Переписування опублікованих комітів потребує узгодження й може бути заборонене правилами. Інтерактивний rebase дозволяє змінювати повідомлення, порядок або об’єднувати власні коміти, але після цього слід перевіряти проміжні й остаточні стани.

## Squash як інший спосіб запису історії

Squash-інтеграція записує об’єднані зміни новим комітом, не роблячи початкову вершину гілки батьком злиття. Це може спростити історію main, але початкові коміти не стануть її предками. Локальний `merge --squash` готує об’єднану зміну до окремого коміту; хостинг може надавати власну операцію squash-and-merge.

Довготривалі гілки, які багаторазово інтегрують через squash в одну ціль, можуть створювати заплутані порівняння. Зазвичай наступну зміну краще почати від оновленої інтеграційної гілки.

## Cherry-pick для вибраної зміни

`git cherry-pick COMMIT_ID` застосовує зміну вибраного коміту до поточної гілки й зазвичай записує новий коміт. Використовуйте справжній перевірений ідентифікатор у потрібній цільовій гілці з чистим робочим деревом. За потреби `-x` записує початковий ідентифікатор для простежуваного перенесення виправлення.

Успішне застосування без конфлікту не доводить наявності передумов. Виправлення може залежати від попередніх змін схеми, API чи рефакторингу. Для комітів злиття потрібен свідомий вибір основної лінії через `-m`; не вгадуйте номер батька лише для усунення помилки.

## Конфлікти й точки зупинки

Для скасування незавершеного злиття використовуйте `git merge --abort`; для rebase — `git rebase --abort` або, після розв’язання конфліктів, `git rebase --continue`. Cherry-pick має відповідні операції продовження та скасування. Читайте `git status`, щоб визначити поточну операцію. Rebase може зупинятися кілька разів, адже відтворює коміти по одному.

## Перевірка підсумкової поведінки

Після інтеграції перегляньте історію, остаточний diff від потрібної бази й відповідні тести. Зберігайте резервні посилання, доки результат не зрозумілий. Навіть злиття без текстових конфліктів може поєднати несумісні припущення, наприклад перейменоване налаштування та код, який усе ще читає стару назву.

## Контрольне запитання та відповідь

**Запитання:** Чому rebase спільної гілки відрізняється від злиття main у неї?

**Відповідь:** Rebase замінює ідентифікатори комітів, які колеги вже могли використати, і їм доведеться узгоджувати свою роботу з переписаною історією. Merge зберігає наявні ідентифікатори та додає зв’язок інтеграції. Вибирайте з урахуванням відповідальності, правил і потреб перевірки.
