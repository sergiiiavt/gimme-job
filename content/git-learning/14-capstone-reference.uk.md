# Локальна лабораторія співпраці та довідник задач

## Що демонструє лабораторія

[Виконуваний приклад](https://github.com/sergiiiavt/gimme-job/tree/main/examples/git-collaboration) створює локальний bare-репозиторій і двох учасників у новому тимчасовому каталозі. Він виконує справжні команди Git і перевіряє файли, посилання та коди завершення. Самій лабораторії не потрібні обліковий запис хостингу, мережа чи токен.

Це керована перевірка механіки Git, а не локальна реалізація прав GitHub, перегляду PR чи CI. Командні рішення розглянуто в розділах 10–11; відпрацьовуйте їх за справжніми правилами хостингу вашої команди.

## Запуск із копії репозиторію

Потрібні Git 2.28+ та Python 3.9+. Із кореневого каталогу репозиторію GimmeJob:

```sh
python3 examples/git-collaboration/verify_workflow.py
```

У Windows використовуйте встановлений Python і Git, доступний через PATH; еквівалентним засобом запуску може бути `py`. Скрипт використовує стандартну бібліотеку Python та викликає Git безпосередньо, тому не потребує Bash, Docker, npm чи встановлення Python-пакетів. Початкове отримання проєкту — окрема дія від запуску цієї автономної лабораторії.

## Простежте переходи станів

Лабораторія окремо перевіряє індекс і пізніші редагування, stash невідстежуваного файла, fetch без зміни робочих файлів, справжній конфлікт rebase, явне розв’язання та інтеграційне злиття. Потім перевіряє revert, відновлений detached-коміт, друге робоче дерево, відмову за застарілого явного очікування force-with-lease, результат bisect і анотований тег релізу.

Очікувані конфлікти та відхилені push потрібно розпізнавати як очікувані результати. Сприйняття кожного ненульового завершення як приводу повторити команду примусово — саме та помилка, яку виявляє приклад.

## Значення доказів

Кожен етап друкує коротке повідомлення PASS лише після успішних перевірок. Помилка містить локальну команду та її вивід. Скрипт використовує вигадані дані авторів, вимикає успадковані налаштування Git для дочірніх команд і прибирає тимчасовий каталог після завершення. Він не змінює посилання вашого поточного репозиторію чи глобальні налаштування Git.

Читайте код разом із виводом. Простежуйте локальну гілку, віддалену гілку та вміст робочих файлів до й після кожної операції. Успішне виконання підтверджує ці сценарії у встановленому середовищі Git, а не всі можливі процеси роботи з ним.

## Перегляд і запис змін

| Задача | Команда | Стан або обмеження |
| --- | --- | --- |
| Переглянути поточний стан | `git status --short --branch` | Включає невідстежувані шляхи |
| Переглянути зміни поза індексом | `git diff` | Робоче дерево проти індексу |
| Переглянути наступний коміт | `git diff --cached` | Індекс проти HEAD |
| Додати один шлях | `git add -- path` | Фіксує його поточний вміст |
| Прибрати шлях з індексу | `git restore --staged -- path` | Зберігає робочі редагування |
| Записати індекс | `git commit` | Створює локальний коміт |

Перед комітом перегляньте остаточний diff індексу та виконайте відповідні перевірки. Поточний вміст файла в редакторі може відрізнятися від вмісту в індексі.

## Інтеграція та відновлення

| Задача | Команда | Потрібне рішення |
| --- | --- | --- |
| Оновити відомості про сервер | `git fetch origin` | Без автоматичної локальної інтеграції |
| Оновитися без розходження | `git pull --ff-only` | Відхиляє розбіжну історію |
| Почати окрему задачу | `git switch -c feature/name` | Оберіть правильний початковий коміт |
| Злити отриману базу | `git merge origin/main` | Можливий коміт злиття або конфлікт |
| Перенести особисту гілку на нову базу | `git rebase origin/main` | Замінює ідентифікатори відтворених комітів |
| Скасувати звичайну спільну зміну | `git revert COMMIT_ID` | Перевірте зворотну поведінку й конфлікти |
| Знайти нещодавні локальні рухи посилань | `git reflog` | Локальність і обмежене зберігання |

Команди із символічними ідентифікаторами потребують справжніх перевірених значень. Довідник не вирішує, чи допустиме переписування спільної історії; це питання співпраці та дозволів.

## Зв’язок з іншими навчальними шляхами

Застосовуйте навички в [програмуванні](/learn/programming), [автоматизації](/learn/automation), [Docker](/learn/docker) та [Cloud & DevOps](/learn/cloud-devops). Для кожної зміни відпрацьовуйте ланцюг: визначити ревізію, створити цілісний коміт, опублікувати в потрібну гілку, перевірити точний diff, пройти відповідні перевірки, інтегрувати й за потреби підтвердити доставку.

## Контрольне запитання та відповідь

**Запитання:** Push із force-with-lease відхилено після оновлення гілки колегою. Який правильний наступний крок?

**Відповідь:** Отримайте та дослідіть його справжню зміну, узгодьте відповідальність і збережіть чи інтегруйте її. Не оновлюйте очікування для автоматичного повтору push: це знищує зміст захисту й може перезаписати роботу колеги.
