# Розв’язання конфліктів зі збереженням змісту

## Текстові та змістові конфлікти

Текстовий конфлікт означає, що Git не зміг автоматично обрати об’єднану версію. Змістовий конфлікт виникає, коли зміни технічно поєднуються, але суперечать одна одній у поведінці. Лише перший обов’язково зупиняє Git. Щоб зберегти задум обох авторів, перегляньте базу, обидві зміни, вимоги та залежний код.

## Створення окремого конфлікту

Виконайте приклад у новому батьківському каталозі, де ще немає `git-conflict-lab`. Він створює лише локальний репозиторій із вигаданими даними автора:

```sh
git init --initial-branch=main git-conflict-lab
cd git-conflict-lab
git config user.name "Course Learner"
git config user.email "learner@example.invalid"
printf 'retries=1\n' > settings.ini
git add settings.ini
git commit -m "Record baseline"
git switch -c feature/retry
printf 'retries=3\n' > settings.ini
git commit -am "Allow three retries"
git switch main
printf 'retries=2\n' > settings.ini
git commit -am "Raise baseline to two retries"
git merge feature/retry
```

Остання команда очікувано завершується помилкою через конфлікт вмісту. Обидві гілки змінили той самий рядок від спільного предка. Ненульовий код завершення є частиною демонстрації, а не приводом застосовувати примусову команду.

## Перегляд трьох версій

```sh
git status
git diff --name-only --diff-filter=U
git show :1:settings.ini
git show :2:settings.ini
git show :3:settings.ini
```

Для цього звичайного злиття стадія 1 індексу містить базу, стадія 2 — поточну сторону, а стадія 3 — вхідну. Не кожен конфлікт має всі три записи: додавання та видалення можуть змінювати їхню наявність. Робочий файл містить маркери з варіантами тексту.

## Свідоме розв’язання прикладу

Припустімо, узгоджена вимога — три повторні спроби. Запишіть повний потрібний файл, додайте його в індекс і перегляньте результат перед завершенням злиття:

```sh
printf 'retries=3\n' > settings.ini
git add -- settings.ini
git diff --cached
git diff --cached --check
git commit -m "Merge retry feature with three-retry policy"
git status --short
```

Видалення маркерів — лише технічний крок. У справжньому проєкті запустіть відповідні тести й перевірте залежну поведінку. Якщо вимога неясна, отримайте рішення відповідальних осіб замість вибору більшого числа лише тому, що воно здається обережнішим.

## Інші сторони під час rebase

Під час rebase поточна сторона зазвичай містить нову базу та вже відтворену роботу, а інша — коміт, який зараз відтворюється. Тому `ours` і `theirs` можуть сприйматися навпаки порівняно зі злиттям main у функціональну гілку. Досліджуйте фактичний вміст і поточну операцію; ці назви не є синонімами «моє» та «чуже».

Після виправлення та додавання файлів у межах rebase використовуйте `git rebase --continue`, а не окремий рецепт створення коміту злиття. Наступний коміт також може конфліктувати. Пропускайте коміт лише тоді, коли встановили, що його зміну потрібно відкинути або вона вже присутня.

## Скасування й повторна спроба

Для незавершеного злиття вище `git merge --abort` є альтернативою розв’язанню, а не командою після завершення. Rebase і cherry-pick мають власні команди скасування. Початок із чистого стану робить результат скасування зрозумілішим; відновлення попередніх незакомічених редагувань не варто залишати випадковості.

## Інші види конфліктів

Конфлікти зміни й видалення, перейменування та двійкових файлів потребують рішення про підсумкові шляхи й вміст, а не лише редагування маркерів. Для згенерованих файлів визначте вихідні дані та повторно згенеруйте результат за документацією проєкту. Не обирайте навмання одну версію lockfile з припущенням, що вона досі відповідає опису залежностей.

## Контрольне запитання та відповідь

**Запитання:** Злиття завершилося без конфліктів, а всі маркери прибрано. Чи готова зміна?

**Відповідь:** Успішною була лише текстова інтеграція. Перевірте вимоги, сумісність API та схеми, відповідні тести й остаточний diff. Git не виявляє всі суперечливі бізнес-правила чи припущення середовища виконання.
