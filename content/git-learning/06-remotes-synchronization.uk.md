# Віддалені репозиторії, upstream і синхронізація

## Локальні та віддалені назви

Remote — іменоване налаштування URL іншого репозиторію та правил отримання посилань. `origin` — домовленість, а не спеціальний центральний орган. Локальна гілка `main` і віддалене посилання `origin/main` — різні посилання. Друге зберігає стан сервера, побачений під час останнього відповідного fetch.

Upstream пов’язує локальну гілку з іншою для типових операцій і порівнянь. Це не безперервна синхронізація. У процесі з fork назва `origin` часто вказує на ваш fork, а remote із назвою `upstream` — на початковий проєкт; назва remote і налаштування upstream для гілки — різні поняття.

## Спершу fetch, потім рішення

У чистій функціональній гілці з налаштованим origin:

```sh
git remote -v
git fetch origin
git branch -vv
git log --left-right --oneline HEAD...origin/main
```

Fetch завантажує об’єкти й оновлює налаштовані віддалені посилання без злиття з поточною гілкою. Log позначає коміти, що належать лише одній стороні. Лічильники випередження й відставання порівнюють локально відомі посилання та можуть бути застарілими до fetch. Успішне отримання даних нічого не доводить про правильність інтеграції функціональної гілки.

## Pull включає інтеграцію

`git pull` отримує дані, а потім інтегрує їх відповідно до параметрів і конфігурації. Використовуйте `git pull --ff-only`, коли потрібне лише fast-forward-оновлення. За розходження історії команда відмовить замість самостійного вибору злиття чи переписування комітів. Для розбіжної функціональної гілки виконайте fetch і свідомо оберіть merge або rebase з наступного розділу.

Помилка pull не є причиною відкидати локальну роботу. Визначте поточну гілку й коміти, унікальні для кожної сторони; збережіть їх перед зміною стратегії. Конфлікти самі собою не доводять чиєїсь помилки.

## Явна публікація гілки

```sh
git push -u origin feature/retry
git status --short --branch
```

Приклад передбачає наявність локальної гілки та потрібних прав. `-u` записує upstream після успішного оновлення. Push передає досяжні об’єкти й просить сервер оновити посилання; правила гілки можуть відхилити запит. Звичайний Git push сам собою не створює пулреквест.

Якщо віддалена гілка незалежно пересунулася, звичайний push переважно відхиляє оновлення, що не є fast-forward. Отримайте дані, перегляньте нові коміти й належно інтегруйте їх. Видалення віддаленої гілки або примусовий push для обходу відмови можуть знищити спільне посилання на чужу роботу.

## Переписування власної функціональної гілки

Після узгодженого rebase для вже опублікованої гілки може знадобитися оновлення, що не є fast-forward. Вкажіть явний очікуваний ідентифікатор у lease. Замініть EXPECTED_REMOTE_OID повним ідентифікатором вершини сервера, яку ви справді переглянули:

```sh
git push --force-with-lease=refs/heads/feature/retry:EXPECTED_REMOTE_OID origin HEAD:refs/heads/feature/retry
```

Сервер має відхилити запит, якщо вершина відрізняється від очікуваної. Успішний lease не доводить, що заміна зберігає всі перевірені зміни. Звичайний `--force-with-lease` спирається на локальні віддалені посилання, які фоновий fetch може оновити; явне очікування робить припущення видимим. Lease не є дозволом переписувати спільну чи захищену інтеграційну гілку.

## Видалення та очищення посилань

Видалення локальної й віддаленої гілок — окремі операції. `git fetch --prune origin` прибирає застарілі віддалені посилання згідно з правилами fetch, але не видаляє звичайні локальні функціональні гілки. Перед видаленням опублікованої роботи перевірте власника й політику зберігання.

## Класифікація помилок

Розрізняйте недоступність DNS чи мережі, помилку довіри TLS або SSH, невдалу автентифікацію, недостатні права, відмову захисту гілки, відсутні об’єкти та розходження історії. Зберігайте точний текст помилки, приховуючи токени й приватні URL. Виправлення облікових даних не усуне non-fast-forward, а rebase не надасть доступу.

## Контрольне запитання та відповідь

**Запитання:** Fetch завершився успішно, але файли поточної гілки не змінилися. Чому?

**Відповідь:** Fetch оновлює завантажені об’єкти й відомості про віддалені посилання. Він не відкриває origin/main і не інтегрує її з поточною робочою гілкою. Перегляньте порівняння й свідомо оберіть наступну операцію.
