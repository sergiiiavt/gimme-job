# Розподілене трасування

Одна дія користувача часто проходить через багато сервісів: вебсервер, API-шлюз, два бекенд-сервіси, базу даних, чергу й сторонній API. Коли дія повільна чи падає, логи кожного сервісу розповідають частину історії, а метрики кажуть, що десь щось не так. Розподілене трасування показує весь шлях саме цього запиту з часом на кожному кроці й кроком, на якому стався збій.

У цьому розділі: трасування й span, як контекст передається між сервісами, вибірка, як читати трасування, як QA використовує трасування для нестабільних тестів і роботи з продуктивністю і який вигляд має кореляція, поки в системі ще немає трасування. Сигнали описано в розділі [Спостережуваність для QA-інженерів](/learn/observability?topic=observability-for-qa).

**Передумови:** [Спостережуваність для QA-інженерів](/learn/observability?topic=observability-for-qa), [Логи, що відповідають на питання](/learn/observability?topic=structured-logs).

## Трасування й span

**Трасування** (trace) — це запис одного запиту через систему. Воно складається зі **span**: операцій із часом, як-от обробка HTTP-запиту, виклик іншого сервісу чи запит до бази даних. Через ідентифікатори батьків span утворюють дерево.

```diagram
trace 4bf92f3577b34da6a3ce929d0e0e4736                         усього 2 430 мс
└─ POST /checkout                (web, server)                  0 ─────────────── 2 430
   ├─ SELECT cart                (web → db, client)             12 ─ 38
   ├─ POST /payments             (web → payments, client)       45 ──────────── 2 410
   │  └─ POST /payments          (payments, server)             50 ──────────── 2 400
   │     ├─ перевірка на шахрайство (payments, internal)        55 ── 140
   │     └─ POST bank-api        (payments → bank, client)      150 ─────────── 2 390  status=Error (тайм-аут)
   └─ формування чека            (web, internal)                не дійшло
```

OpenTelemetry визначає, що містить span:

| Поле | Значення |
|---|---|
| Назва | Що це за операція, наприклад `POST /payments` |
| Trace id, span id, parent span id | До якого трасування належить span і де він у дереві; кореневий span не має батька |
| Час початку й кінця | Коли він виконувався |
| Атрибути | Деталі у вигляді ключ-значення: маршрут, код статусу, система бази даних, feature flag |
| Events | Позначки з часом усередині span, схожі на рядки логу |
| Links | Зв'язки зі span інших трасувань, наприклад із задачею, яку запустило повідомлення |
| Статус | Unset (завершено), Error або Ok, якщо його задано явно |

У span також є вид (kind): **server** і **client** для двох боків синхронного виклику, **producer** і **consumer** для асинхронних повідомлень та **internal** для роботи всередині одного процесу.

## Передавання контексту

Трасування переживає мережевий перехід, лише якщо викликач передає свій контекст тому, кого викликає. Рекомендація W3C Trace Context стандартизує це заголовком `traceparent`, який OpenTelemetry використовує за замовчуванням:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └ flags: 01 = sampled
             │  │                                └ parent id: 16 hex characters, the caller's span
             │  └ trace id: 32 hex characters, shared by every span of the request
             └ version: 00
```

Отримувач зберігає trace id, записує вхідний parent id як свого батька, створює власний span id і надсилає далі новий `traceparent`. Необов'язковий заголовок `tracestate` несе дані конкретного постачальника. Бібліотеки інструментування роблять це автоматично для поширених HTTP-клієнтів і серверів; черги й власні протоколи часто доводиться обробляти вручну.

Оскільки інструменти тестування — це клієнти, тест може сам почати трасування, надіславши `traceparent` з обраним trace id, а потім знайти це трасування, якщо тест упаде. Код нижче розбирає й перевіряє заголовок і будує заголовок для наступного переходу, як це робить propagator:

```python
import re
import uuid

TRACEPARENT = r"([0-9a-f]{2})-([0-9a-f]{32})-([0-9a-f]{16})-([0-9a-f]{2})"

def parse_traceparent(header):
    match = re.fullmatch(TRACEPARENT, header.strip())
    if not match:
        return None
    version, trace_id, parent_id, flags = match.groups()
    if version == "ff" or set(trace_id) == {"0"} or set(parent_id) == {"0"}:
        return None
    return {"trace_id": trace_id, "parent_id": parent_id, "sampled": (int(flags, 16) & 1) == 1}

def child_traceparent(incoming):
    context = parse_traceparent(incoming)
    if context is None:
        context = {"trace_id": uuid.uuid4().hex, "parent_id": None, "sampled": True}
    span_id = uuid.uuid4().hex[:16]
    flags = "01" if context["sampled"] else "00"
    return f"00-{context['trace_id']}-{span_id}-{flags}", context

for header in [
    "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00",
    "00-00000000000000000000000000000000-00f067aa0ba902b7-01",
    "not-a-trace-header",
]:
    outgoing, context = child_traceparent(header)
    print("in: ", header)
    print("out:", outgoing, "| continues trace" if context["parent_id"] else "| new trace")
```

Невалідний або відсутній заголовок починає нове трасування замість того, щоб зламати запит. Вважайте вхідний контекст ззовні системи недовіреним: ним можна вплинути на те, які трасування зберігаються, а baggage ніколи не повинен містити чутливих даних.

## Вибірка

Навантажені системи не зберігають кожне трасування. OpenTelemetry описує два підходи:

| | Head sampling | Tail sampling |
|---|---|---|
| Коли ухвалюється рішення | На початку трасування, не бачачи його | Після того, як прийшли всі або більшість span |
| Типове правило | Зберігати фіксовану частку, наприклад 5%, за trace id | Зберігати кожне трасування з помилкою, кожне повільне, частку решти |
| Переваги | Просто, дешево, узгоджено між сервісами | Зберігає цікаві трасування |
| Недоліки | Не гарантує, що трасування з помилками збережуться | Зберігає стан, складніше в запуску й експлуатації, часто прив'язане до постачальника |

Конвеєри з великим обсягом часто поєднують обидва. Емпіричне правило OpenTelemetry — замислюватися про вибірку приблизно з тисячі трасувань на секунду й уникати її на десятках трасувань на секунду. Для тестового середовища практичний висновок простий: переконайтеся, що трасування ваших тестових запусків зберігаються, наприклад позначаючи тестовий трафік як sampled.

## Як читати трасування

Більшість проблем продуктивності й надійності проявляються кількома впізнаваними формами:

| Що видно в трасуванні | Що це зазвичай означає |
|---|---|
| Один довгий span на критичному шляху | Повільна залежність, яку треба оптимізувати або раніше обривати тайм-аутом |
| Проміжки, не покриті жодним span | Черги, очікування пулу потоків, збирання сміття або відсутнє інструментування |
| Той самий запит повторюється багато разів | Патерн N+1 запитів |
| Виклики йдуть один за одним, хоча могли б паралельно | Послідовний fan-out |
| Невдалий span, а за ним схожий | Повтор; кілька поспіль можуть бути шквалом повторів |
| Кореневий span завершується раніше за дочірні | Робота триває у фоні після того, як відповідь уже надіслано |

Починайте з кореневого span, на кожному рівні йдіть за найдовшим дочірнім (це критичний шлях) і шукайте перший span зі статусом помилки.

## Трасування в роботі QA

| Задача | Як допомагає трасування |
|---|---|
| Нестабільний end-to-end тест | Надсилайте `traceparent` із тесту; коли він впаде, відкрийте його трасування й подивіться, який сервіс не відповів вчасно |
| Тестування продуктивності | Розкладіть повільний ендпоінт на span, що забирають час, замість вгадувати за загальною тривалістю |
| Тестування нової інтеграції | Перевірте, що контекст передається через новий перехід, щоб трасування не розпалося надвоє |
| Перевірка поведінки | Перевірки на основі трасування: запит зробив рівно один виклик бази, ніколи не звертався до застарілого сервісу, вклався в бюджет часу для кожного span |
| Відтворення проблем із продакшну | Знайдіть трасування збою за id, атрибутами чи часом і перенесіть його вхідні дані в тест |

Перевірки на основі трасування потужні, але крихкі, якщо перевіряють кожен span. Перевіряйте кілька властивостей, які справді важать, наприклад кількість викликів залежності або відсутність статусу помилки.

## Приклад: кореляція до трасування

Цей сайт ще не використовує розподіленого трасування. Він використовує крок перед ним — **operation id**. Кожна багатоетапна операція, як-от імпорт вакансій, створює ідентифікатор на кшталт `import_…` і записує його в кожну подію цієї операції: подію старту, подію завершення з результатом, тривалістю й кількістю елементів, а при збої — етап, на якому він стався.

| Що дає operation id | Що додало б трасування |
|---|---|
| Усі події одного запуску одним запитом | Час кожного кроку, а не лише загальний |
| Етап, на якому стався збій, і безпечну причину | Дерево причинних зв'язків між сервісами |
| Тривалість і кількість елементів для кожного запуску | Автоматичне передавання контексту між Worker, AI-сервісом і зовнішніми викликами |

Operation id дешевий і вже відповідає на більшість питань «що сталося в цьому запуску?». Природним наступним кроком було б передавати W3C `traceparent` від Worker до Python AI-сервісу, щоб один запит до Learning Path Advisor був одним трасуванням через обидва.

## Типові помилки

- **Зламане передавання контексту.** Один неінструментований перехід розділяє трасування надвоє, і повільна частина зникає з поля зору.
- **Лише head sampling.** Фіксована вибірка 5% зазвичай губить саме трасування з помилками.
- **Span без корисних атрибутів.** Span `HTTP POST` без маршруту й коду статусу нічого не пояснює.
- **Назви span із високою кардинальністю.** Ідентифікатори кладіть в атрибути, а не в назви на кшталт `GET /orders/48213`.
- **Сліпо довіряти вхідному контексту.** Зовнішні заголовки можуть бути зіпсованими чи підробленими; перевіряйте їх і в разі сумніву починайте нове трасування.
- **Перевіряти кожен span.** Тести на основі трасування, що перевіряють усе дерево, ламаються від кожного рефакторингу.
- **Ігнорувати проміжки.** Час, не покритий жодним span, часто і є місцем проблеми.

## Підсумок

Трасування записує один запит як дерево span із часом, атрибутами, events, links і статусом. Контекст передається між сервісами в заголовку W3C `traceparent`, який зберігає trace id і передає span викликача як батьківський. Head sampling простий, але губить цікаві трасування; tail sampling зберігає помилки й повільні запити ціною складності. Читайте трасування вздовж критичного шляху й шукайте довгі span, проміжки, повторні виклики й повтори. У роботі QA починайте трасування з тестів, використовуйте їх, щоб пояснювати нестабільні збої й повільні ендпоінти, і перевіряйте лише кілька властивостей span, які справді важать. Поки трасування немає, operation id у кожній події — дешевий і корисний перший крок.
