# Мережі контейнерів

## Результати

Простежуйте запит між хостом і контейнерами. Обирайте правильні DNS-ім’я та порт, залишайте внутрішні сервіси приватними й діагностуйте зв’язок за рівнями.

## Модель адресації

| Звідки надходить запит | Адреса в підсумковому проєкті |
| --- | --- |
| Браузер або curl на хості | `http://127.0.0.1:18080` |
| Контейнер перевірок Compose | `http://api:8000` |
| API перевіряє себе | `http://127.0.0.1:8000/health` |

У звичайному ізольованому контейнері localhost означає його власний мережевий простір імен. Це не ноутбук і не сусідня база даних. Власні bridge-мережі підтримують визначення імен; Compose типово створює таку мережу застосунку та DNS-імена сервісів.

## Публікація та доступність

`-p 127.0.0.1:18080:8000` зіставляє loopback-порт хоста 18080 з портом контейнера 8000. Без адреси хоста порт зазвичай прив’язується до всіх інтерфейсів. `EXPOSE` і Compose `expose` не публікують порт на хості та не є політиками контролю доступу.

Сервіси однієї мережі Docker можуть звертатися до портів контейнерів без публікації. Не публікуйте базу лише заради доступу з API. Для потрібних меж використовуйте окремі мережі та автентифікацію застосунку.

## Робочий приклад

Запустіть проєкт із його директорії та перевірте обидві сторони:

```sh
docker compose up --build -d --wait
curl --fail http://127.0.0.1:18080/health
docker compose exec api python -c "import socket; print(socket.gethostbyname('api'))"
docker compose --profile checks run --rm --no-deps checks
```

Контейнер перевірок звертається до `api:8000` через мережу застосунку. Зміна лише опублікованого порту хоста не потребує зміни внутрішньої адреси. Не фіксуйте IP контейнерів: заміна може змінити IP, тоді як ім’я сервісу залишається потрібною адресою.

## Доступ до хоста та відмінності платформ

Docker Desktop надає `host.docker.internal` для доступу до сервісів хоста. На Linux за підтримки конфігурації можна додати зіставлення host-gateway; не очікуйте наявності імен Desktop скрізь. Сервіс хоста має слухати доступний із контейнера інтерфейс і дозволяти з’єднання.

Host networking прибирає звичайну мережеву ізоляцію та має обмеження платформи й версії. Це не універсальне виправлення DNS. Overlay потрібна для кількох хостів; macvlan/ipvlan вирішують спеціальні завдання мережевої інтеграції.

## Проксі, DNS і TLS

Розрізняйте завантаження образів, мережу кроків збирання та трафік застосунку: налаштування проксі для одного не обов’язково поширюється на інші. Корпоративні CA можуть потребувати встановлення на кількох рівнях. Помилка перевірки TLS відрізняється від збою DNS чи відмови TCP.

Reverse proxy приймає зовнішній трафік і передає його застосунку. Завершення TLS, автентифікація, forwarded headers і таймаути потребують налаштування. `internal`-мережа обмежує зовнішні з’єднання, але не є системою авторизації застосунку.

## Контрольне запитання та відповідь

**Запитання:** API опубліковано як `18080:8000`. Сусідній контейнер звертається до `localhost:18080` без успіху. Яка адреса потрібна?

**Відповідь:** Якщо сервіси мають спільну мережу Compose, звертайтеся до `api:8000`. Опублікований порт потрібен для доступу з хоста. Localhost сусіда вказує на самого сусіда. До змін firewall перевірте DNS, адресу прослуховування та спільну мережу.

## Підсумок

Окремо визначайте джерело запиту, простір імен, DNS-ім’я, порт прослуховування й опублікований порт. Якщо це відповідає симптомам, досліджуйте DNS, TCP, TLS і HTTP в такій послідовності.
