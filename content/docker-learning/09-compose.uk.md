# Застосунки Docker Compose

## Результати

Описуйте застосунок через сервіси, мережі та томи, перевіряйте підсумкову конфігурацію, очікуйте готовності й запускайте ізольовані перевірки. Використовуйте сучасний плагін `docker compose`. Застаріле поле верхнього рівня `version` у нових файлах не потрібне.

## Модель застосунку

Сервіс — конфігурація контейнерів, а не образ. Кілька сервісів можуть використовувати однаковий образ з різними командами. Проєкт групує ресурси; назви сервісів дають внутрішні адреси. Іменовані томи зберігають дані незалежно від заміни контейнерів.

У проєкті `api` працює постійно, а `checks` — короткочасний процес із того самого образу. Перевірки мають окремий профіль, тому звичайний запуск не запускає тести.

## Читання мінімальної конфігурації

Це пояснювальний уривок із повної захищенішої конфігурації проєкту:

```yaml
services:
  api:
    build: .
    image: gimmejob-docker-course:local
    ports:
      - "127.0.0.1:18080:8000"
    volumes:
      - counter-data:/data
  checks:
    image: gimmejob-docker-course:local
    profiles: [checks]
    entrypoint: [python, checks.py]
    depends_on:
      api:
        condition: service_healthy
volumes:
  counter-data:
```

Dockerfile образу задає health check API. Без перевірки здоров’я залежності `service_healthy` не забезпечить готовність. Повний файл також задає адресу API для перевірок і вимикає успадкований API-probe у тестовому сервісі.

## Керування стеком

З `examples/docker-learning`:

```sh
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 90
docker compose ps
docker compose --profile checks run --rm --no-deps checks
docker compose logs --tail 50 api
docker compose down
```

`up` узгоджує стан сервісів і може замінити змінені контейнери; `start` лише запускає наявні. `run` створює одноразовий контейнер, `exec` використовує працюючий. Тут `--no-deps` доречний, бо `up --wait` уже запустив і перевірив API. Без такої підготовки дозволяйте запуск залежностей.

## Залежності та відновлення

Короткий `depends_on` задає порядок, а не готовність застосунку. Використовуйте `service_healthy` для залежності з перевіркою здоров’я та `service_completed_successfully` для успішної одноразової передумови, наприклад міграції.

Очікування готовності не замінює повторних підключень під час роботи. База може відмовити пізніше. Клієнтам потрібні обмежені повторні спроби, таймаути та відновлення з’єднання. Політика перезапуску не робить один хост високодоступною платформою.

## Проєкти, профілі та перевизначення

Для паралельних середовищ задавайте різні назви проєкту через `-p`. Це ізолює стандартні мережі й іменовані томи, але явно названі ресурси та фіксовані порти хоста все одно можуть конфліктувати. Параметризуйте порти або не публікуйте їх для внутрішніх CI-перевірок.

Профілі вмикають додаткові інструменти; кілька `-f` поєднують конфігурації. Злиття має визначені правила й не зводиться до повної заміни YAML-об’єкта. Перевіряйте `docker compose ... config` з тими самими файлами, середовищем і параметрами проєкту, що й під час розгортання. Результат може містити секрети: не публікуйте його без перевірки.

## Контрольне запитання та відповідь

**Запитання:** База запускається перед API, але перше підключення іноді не вдається. Чому?

**Відповідь:** Запуск процесу не є готовністю. Додайте змістовний health check бази та умову здоров’я залежності; залиште повторне підключення для пізніших відмов. Фіксована затримка лише вгадує момент готовності.

## Підсумок

Сприймайте Compose як модель застосунку з явним запуском і станом. Перевіряйте об’єднану модель та зберігайте діагностику перед видаленням контейнерів.
