# Поза Docker: екосистема контейнерів

## Результати

Розміщуйте суміжні інструменти на правильному рівні. Розумійте, які навички переносяться, а які експлуатаційні обов’язки потребують окремого навчання.

## Стандарти, виконання та модель застосунку

| Рівень | Приклади | Основне завдання |
| --- | --- | --- |
| Стандарти артефактів і виконання | OCI | Сумісні формати та контракти запуску |
| Компоненти виконання | containerd, runc | Життєвий цикл образів/контейнерів і процеси |
| Рушій та інтерфейс розробника | Docker Engine, Podman | Локальне або віддалене керування контейнерами |
| Опис застосунку | Compose | Сервіси, конфігурація, мережі та томи |
| Оркестрація кластера | Kubernetes, Swarm | Розміщення, узгодження стану й кілька хостів |

Це не просто конкуренти-замінники. Docker може використовувати containerd; Kubernetes може запускати OCI-сумісні образи через відповідне CRI-середовище без Docker Engine на вузлах.

## Podman та альтернативні настільні середовища

Podman надає керування контейнерами та підтримує rootless-роботу. Багато команд схожі, але мережі, інтеграцію Compose, socket, томи та поведінку VM потрібно перевіряти. Сумісність не означає повної тотожності.

Обирайте середовище, підтримуване командою, ОС і CI. Перед переходом перевірте функції Compose, автентифікацію, архітектуру, монтування та інтеграцію тестових бібліотек.

## Що додає Kubernetes

Kubernetes керує бажаним станом у кластері. Вивчайте Pods, Deployments, Services, конфігурацію, секрети, readiness/liveness/startup probes, requests/limits ресурсів, сховища й оновлення. Pod — одиниця розміщення, яка може містити пов’язані контейнери; це не перейменований Docker-образ.

Файли Compose не мають прямої відповідності всім об’єктам Kubernetes. Для стану потрібні явні рішення зі сховищ і резервування. Доступність кластера залежить також від control plane, мережі та сховища. Kubernetes додає експлуатаційну роботу й не є обов’язковою передумовою для малого застосунку на одному хості.

## Swarm і керовані платформи

Swarm mode додає керування сервісами на кількох хостах до Docker Engine. Вивчайте його сервіси, overlay-мережі, секрети, розміщення й оновлення, якщо ваша платформа його використовує. Не всі атрибути Compose без змін переносяться до Swarm stack.

Керовані контейнерні платформи можуть забезпечувати розміщення й ingress, але різняться сховищами, мережами, тривалістю задач, масштабуванням і секретами. Обирайте за вимогами: stateless-запити, фонові задачі, постійні дані, GPU, регіони та відповідальність за експлуатацію.

## Вибір наступного кроку

| Потреба | Що дослідити далі |
| --- | --- |
| Відтворити локальний багатосервісний застосунок | Compose і підсумковий проєкт |
| Тимчасові бази для тестів | Testcontainers і fixtures |
| Однакові редактор та інструменти | Development Containers |
| Один малий хост із допустимим простоєм | Захищений Compose і тренування відновлення |
| Автоматичне розміщення й відновлення між хостами | Kubernetes, Swarm або керована платформа |

GPU-контейнери, привілейований доступ до пристроїв і Windows-контейнери — спеціалізовані розширення. Їм потрібні сумісні драйвери хоста, підтримувані середовища та окремий аналіз безпеки; Dockerfile не створює відсутніх можливостей хоста.

## Контрольне запитання та відповідь

**Запитання:** Вузол Kubernetes використовує containerd замість Docker Engine. Застосунок потрібно переписати, бо образ зібрано Docker?

**Відповідь:** Зазвичай інструмент збирання не є проблемою: сумісний OCI-образ запускається через середовище вузла. Перевірте платформу, доступ до образу та вимоги застосунку. Конфігурацію розгортання потрібно перевести в поняття Kubernetes; не припускайте перенесення специфічних монтувань хоста чи семантики Compose без змін.
