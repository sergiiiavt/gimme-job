# Конфігурація, секрети та розробка

## Результати

Розрізняйте вхідні дані збирання, підстановку Compose і конфігурацію контейнера під час виконання. Обирайте цикл розробки без додавання облікових даних до артефактів.

## Три етапи передавання параметрів

| Етап | Приклад | Коли зміна діє |
| --- | --- | --- |
| Збирання | Базовий образ, зафіксовані залежності, несекретний ARG | Після перебудови й заміни |
| Обчислення Compose | `${DOCKER_COURSE_PORT:-18080}` | Після обчислення конфігурації та заміни відповідних контейнерів |
| Виконання | `DB_PATH=/data/counter.sqlite` | Після створення контейнера з новим середовищем |

`.env` надає значення для підстановки Compose; вони не всі автоматично передаються в кожен контейнер. `environment` та `env_file` налаштовують середовище контейнера. Змінні shell, явні параметри, файли й типові значення образу мають правила пріоритету: перевіряйте підсумкову конфігурацію та реальний контейнер.

## Безпечна локальна зміна

З директорії проєкту:

```sh
DOCKER_COURSE_PORT=18082 docker compose config --quiet
DOCKER_COURSE_PORT=18082 docker compose up -d --wait
curl --fail http://127.0.0.1:18082/health
```

Це команди POSIX shell. Внутрішня адреса перевірок залишається `http://api:8000`. Окремий `docker compose restart` не застосовує нову публікацію порту чи змінене середовище.

## Передавання секрету під час виконання

Умовне визначення файлового секрету:

```yaml
services:
  app:
    image: your-approved-image
    secrets: [database_password]
secrets:
  database_password:
    file: ./secrets/database_password.txt
```

Перед використанням замініть образ і створіть файл поза Git. Застосунок має читати `/run/secrets/database_password`; змінна `_FILE` працює лише за підтримки цієї домовленості конкретним образом. Проєкту пароль не потрібен, тому фрагмент не входить до його стека.

## Життєвий цикл секрету

Файлова ін’єкція Compose — не повноцінне зашифроване сховище секретів. Захищайте вихідний файл, копії, права та доступ до хоста; змінюйте облікові дані й правильно перезавантажуйте або замінюйте споживачів. Секрети збирання — окремий механізм для кроків збірки.

Не публікуйте повне середовище, authorization headers чи підсумкову конфігурацію в CI-артефактах. Після витоку потрібно відкликати або замінити облікові дані; видалення видимого файлу чи зміна одного шару Dockerfile не розв’язує проблему.

## Варіанти циклу розробки

| Підхід | Перевага | Компроміс |
| --- | --- | --- |
| Перебудова й заміна | Найближче до упакованого середовища | Повільніший цикл змін |
| Bind mount коду | Одразу видно локальні файли | Може приховати файли образу та відкрити шляхи хоста |
| Compose Watch | Правила синхронізації та збирання за змінами | Потрібні підтримуваний Compose і правильні правила |
| Dev container | Однакові інструменти редактора й середовище | Образ розробки може містити зайве для production |

Для Watch синхронізуйте зміни коду та перебудовуйте зміни залежностей. Звіряйте вимоги функцій. Проєкт зберігає кореневу систему лише для читання; якщо синхронізація потребує запису, задайте окрему конфігурацію розробки. Не послаблюйте релізну конфігурацію непомітно заради hot reload.

## Контрольне запитання та відповідь

**Запитання:** Ви додали `API_TOKEN` до `.env`, але застосунок його не бачить. Що це означає?

**Відповідь:** Немає доказу, що токен передано в контейнер. `.env` насамперед забезпечує підстановку. Явно оголосіть потрібний параметр виконання або підтримуваний файловий секрет і перевірте результат, не друкуючи самі облікові дані.

## Підсумок

Визначайте, де використовується кожне значення та коли зміна набирає чинності. Явно розділяйте зручності розробки, параметри production і зберігання секретів.
