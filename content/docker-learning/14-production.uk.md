# Розгортання та експлуатація у production

## Результати

Проєктуйте контрольований реліз на одному хості, розумійте обмеження доступності та плануйте перевірки, резервування й відкат. Проєкт пояснює механізми; його неавтентифікований HTTP-сервер стандартної бібліотеки — локальна вправа, не production-шаблон.

## Визначення експлуатаційних вимог

Зафіксуйте публічну адресу, завершення TLS, автентифікацію, дайджест образу, конфігурацію, секрети, постійні дані, бюджет ресурсів, відповідальних і цілі відновлення. Використовуйте придатний для production сервер застосунку та погоджений reverse proxy або керований ingress.

Публікуйте лише потрібні порти. Залишайте бази приватними, захищайте SSH і віддалений демон, оновлюйте хост. Docker не налаштовує замість вас домен, сертифікати, авторизацію застосунку чи резервні копії поза хостом.

## Послідовність релізу

| Крок | Потрібний доказ |
| --- | --- |
| Збирання й тести | Точна ідентичність коду й артефакту, успішні перевірки |
| Підготовка | Коректна конфігурація, секрети, сховище та копії |
| Міграція | Сумісна зміна схеми й план відновлення |
| Заміна | Потрібний дайджест із правильною конфігурацією |
| Перевірка | Зовнішній запит, готовність, ключова операція та журнали |
| Спостереження | Помилки, затримка, ресурси та правильність даних |

Не збирайте production окремо від перевіреного артефакту. Використовуйте погоджене посилання реєстру та зберігайте ідентичність попереднього релізу.

## Форма розгортання Compose

Для стека, вже налаштованого на образи з реєстру:

```sh
docker compose -f compose.yaml -f compose.production.yaml config --quiet
docker compose -f compose.yaml -f compose.production.yaml pull
docker compose -f compose.yaml -f compose.production.yaml up -d --wait --wait-timeout 120
```

`compose.production.yaml` тут означає вашу перевірену конфігурацію розгортання; підсумковий проєкт такого файлу не містить. Вона має вибирати релізний образ, прибирати монтування розробки та задавати обґрунтовані ліміти. Перевіряйте об’єднану конфігурацію до запуску.

## Доступність і перезапуски

Compose на одному хості може підходити невеликій системі з прийнятним часом відновлення. Він автоматично не забезпечує перенесення на інший хост чи оновлення без простою. Заміна єдиного екземпляра може перервати запити.

Політики перезапуску допомагають після завершення процесів. Вони не виправляють диски, втрату хоста, несумісні міграції чи unhealthy-процес, який не завершується. Потрібні зовнішній моніторинг і процедура відновлення; переходьте до оркестратора або керованої платформи за обґрунтованих вимог.

## Дані, відкат і відновлення після аварій

Відкат застосунку — вибір попереднього артефакту та сумісної конфігурації. Він не скасовує міграцію бази. За можливості використовуйте сумісні зміни expand/contract, перевіряйте обидві версії застосунку під час переходу й окремо плануйте руйнівні зміни.

Тренуйте відновлення копій на інший хост або том. Враховуйте повернення секретів і ключів шифрування, не зберігаючи їх незахищено поруч із даними. Визначте дії після повної втрати сервера, а не лише перезапуску контейнера. Заздалегідь налаштуйте зберігання журналів і сповіщення про диск.

## Контрольне запитання та відповідь

**Запитання:** Новий реліз несумісно змінює колонку бази. Повернення старого дайджесту гарантує відкат?

**Відповідь:** Ні. Старий застосунок може бути несумісним із новою схемою чи даними. Потрібні сумісна стратегія міграції або перевірений план відновлення чи виправлення вперед із явними наслідками для даних.

## Підсумок

Розгортайте визначений артефакт, перевіряйте справжню операцію користувача та готуйте відновлення даних. Співвідносьте складність платформи з вимогами доступності й експлуатації.
