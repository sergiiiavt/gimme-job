# Написання Dockerfile

## Результати

Зберіть невеликий образ застосунку та поясніть кожну інструкцію. Приклади посилаються на [повні файли проєкту](https://github.com/sergiiiavt/gimme-job/tree/main/examples/docker-learning); перед виконанням команд отримайте репозиторій. Dockerfile — вхідний файл збірки, а не shell-скрипт, який виконується під час запуску контейнера.

## Контекст і межі файлів

У `docker build -f path/Dockerfile context-directory` останній аргумент визначає контекст збірки. `COPY` читає з нього, а не з довільної директорії поруч із Dockerfile. Обирайте найменший достатній контекст. Через `.dockerignore` виключайте облікові дані, історію Git, кеші, локальні середовища та згенеровані файли.

Підсумковий проєкт використовує список дозволених файлів: виключає все, потім додає лише `app.py`, `checks.py`, `Dockerfile` та `.dockerignore`. `.gitignore` не замінює `.dockerignore`.

## Семантика інструкцій

| Інструкція | Призначення та пастка |
| --- | --- |
| `FROM` | Вибирає основу та починає етап; базовий тег може змінюватися |
| `WORKDIR` | Встановлює директорію для наступних інструкцій і запуску |
| `COPY` | Копіює визначені вхідні файли до образу |
| `RUN` | Виконується під час збирання, не задає запуск |
| `ARG` / `ENV` | Параметр збирання / типова змінна середовища; не сховища секретів |
| `USER` | Встановлює користувача для подальших інструкцій і виконання |
| `EXPOSE` | Документує порт контейнера, не публікує його |
| `CMD` / `ENTRYPOINT` | Типова команда / виконувана точка входу; перевизначаються по-різному |

Для звичайних файлів використовуйте `COPY`. Обирайте `ADD`, лише коли потрібні його додаткові можливості, наприклад розпакування.

## Мінімальний зрозумілий образ

Цей навчальний фрагмент очікує `app.py`, який обслуговує порт 8000 і не записує в `/app`:

```dockerfile
FROM python:3.13-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app
COPY app.py ./
USER 10001:10001
EXPOSE 8000
CMD ["python", "app.py"]
```

Це фрагмент, а не повний приклад збереження даних: Dockerfile проєкту також створює `/data`, призначає власника, додає перевірки та health check. Числовий UID працює без імені користувача, але деяким застосункам потрібні домашня директорія чи запис облікового запису.

## Збирання та запуск повного прикладу

З кореня репозиторію:

```sh
docker build -t gimmejob-docker-course:local examples/docker-learning
docker image inspect gimmejob-docker-course:local --format '{{.Config.User}}'
docker run --rm gimmejob-docker-course:local python -c "import os; print(os.getuid())"
```

Очікуйте користувача `10001:10001` та UID 10001. Команда після назви образу перевизначає CMD. В образу з ENTRYPOINT ці аргументи можуть мати інше значення; перевіряйте конфігурацію перед припущенням, що заміна запускає shell.

## Поширені помилки

Копіювання всього репозиторію перед встановленням залежностей скидає дорогі кроки кешу при кожній зміні коду. Пізніше видалення секретів не очищає попередні шари. Інтерактивне встановлення пакетів у працюючому контейнері створює неперевірені зміни, що зникають після заміни. Shell-форма запуску може ускладнювати передавання сигналів.

Фіксуйте залежності та використовуйте відтворюваний режим їх встановлення. За можливості не додавайте компілятори й облікові дані збірки до фінального образу.

## Контрольне запитання та відповідь

**Запитання:** У Dockerfile є `EXPOSE 8000`, але хост не має доступу до порту 8000. Чого бракує?

**Відповідь:** EXPOSE — метадані. Опублікуйте потрібне зіставлення, наприклад `127.0.0.1:18080:8000`, і перевірте, що застосунок слухає інтерфейс контейнера. Прив’язка застосунку лише до власного loopback теж може перешкоджати доступу через опублікований порт.

## Підсумок

Явно задавайте контекст, вхідні дані, користувача, доступні для запису шляхи та запуск. Далі оптимізуйте збірку, зберігаючи ці межі.
