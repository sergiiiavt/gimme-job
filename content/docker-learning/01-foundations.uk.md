# Docker: основи та послідовність навчання

## Результати та передумови

Навчіться пакувати застосунок, пояснювати межі ізоляції та відтворювати середовище. Потрібні базові команди термінала, розуміння файлів, прав доступу, HTTP-портів, Git і процесів. Попереднє знання Kubernetes не потрібне. Приклади використовують Linux-контейнери та синтаксис POSIX shell; у Windows виконуйте такі команди через WSL.

Розділи 1–5 дають основи, 6–10 — роботу з цілим застосунком, 11–14 — перевірку й експлуатацію; далі йдуть екосистема та підсумковий проєкт. Переходьте далі, коли можете пояснити відповідь на контрольне запитання, а не лише повторити команди.

## Що таке контейнер

Контейнер запускає один або кілька процесів з ізольованим представленням ресурсів. Простори імен Linux відокремлюють видимі процеси, монтування, мережі та інші ресурси; контрольні групи обліковують і обмежують ресурси. Процесу все одно потрібне ядро. Контейнер не є повноцінною віртуальною машиною та не гарантує надійної ізоляції ворожого коду.

На Linux контейнери зазвичай використовують ядро хоста. Docker Desktop запускає Linux-контейнери через віртуальну машину Linux на macOS і Windows. Linux-образ не починає використовувати ядро macOS і не стає звичайною Windows-програмою.

## Терміни та відповідальність

| Компонент | Призначення |
| --- | --- |
| Dockerfile | Інструкції збирання образу |
| Образ | Шари файлової системи та типові параметри запуску |
| Контейнер | Створений екземпляр з конфігурацією і власним записуваним станом |
| Реєстр | Зберігання та розповсюдження маніфестів і вмісту образів |
| Docker CLI | Надсилає запити вибраному демону |
| Docker Engine | Створює та обслуговує ресурси контейнерів |
| BuildKit / Buildx | Виконання збірок / інтерфейс керування збирачами |
| Compose | Опис сервісів, мереж і томів застосунку |

Під Engine Docker зазвичай використовує containerd і низькорівневе середовище виконання на кшталт runc. OCI визначає сумісні специфікації образів, виконання та розповсюдження. Тому образ, зібраний одним інструментом, може запускати інша сумісна платформа.

## Що Docker вирішує, а що залишається вам

Пакування залежностей зменшує відмінності середовищ. Воно не фіксує зовнішні API, вміст бази даних, архітектуру хоста чи секрети. Однакові образи можуть поводитися по-різному через змінні середовища, монтування та ліміти ресурсів.

Постійні дані застосунку зберігайте поза тимчасовим шаром контейнера, а облікові дані — поза образом. Збирайте артефакт один раз і просувайте перевірену версію між середовищами, передаючи окрему конфігурацію під час запуску.

## Перший експеримент

Після налаштування виконайте:

```sh
docker run --rm python:3.13-slim python -c "import platform; print(platform.system(), platform.machine())"
```

Очікуйте Linux та архітектуру вибраного образу, зокрема на Mac. Команда за потреби завантажує образ, запускає процес, друкує результат і видаляє контейнер після завершення. Завантажений образ залишається. Для першого запуску потрібен доступ до реєстру; наступні можуть використовувати локальні дані.

## Поширені помилки

- Плутати образ із запущеним сервісом: образ не має живого процесу.
- Вважати ізоляцію гарантією безпеки: доступ до хоста, capabilities і socket змінюють ризик.
- Очікувати, що контейнер працюватиме після завершення головного процесу.
- Контейнеризувати все без оцінки звичайних інструментів і керованих сервісів.

## Контрольне запитання та відповідь

**Запитання:** Два контейнери використовують однаковий образ. В одному завантажені файли зникають після заміни, в іншому залишаються. Чому?

**Відповідь:** Образ задає початкові файли. Збереження даних залежить від сховища під час виконання. Файли в записуваному шарі зникають разом із контейнером; правильно підключений постійний том переживає заміну. Назва образу не описує всю розгорнуту систему.
