# Спостережуваність і діагностика

## Результати

Перетворюйте симптоми на гіпотези, які можна перевірити. Досліджуйте процеси, журнали, здоров’я, мережу, ресурси та сховище перед змінами системи.

## Послідовність діагностики

З директорії проєкту:

```sh
docker compose ps -a
docker compose logs --tail 100 api
docker compose ps -q api
docker stats --no-stream
docker system df
```

Використайте ID API з `ps -q` у `docker inspect CONTAINER_ID` для дослідження стану, монтувань та історії здоров’я. Не публікуйте повний inspect без перевірки на секрети. Перед перезапуском зафіксуйте симптом, час появи, останню зміну, артефакт і середовище.

## Від симптому до доказів

| Симптом | Перші докази | Можливі класи причин |
| --- | --- | --- |
| Одразу завершується | Журнали, команда, код завершення | Відсутній файл, конфігурація, завершена одноразова задача |
| Працює, але недоступний | Здоров’я, адреса прослуховування, DNS, порти | Неправильна адреса, гонка запуску, відмова залежності |
| Код 137 | OOMKilled, події, пам’ять хоста | SIGKILL, можлива нестача пам’яті |
| Permission denied | Користувач, шлях монтування, власник | UID, read-only шлях, політика хоста |
| Неправильний формат виконуваного файлу | Платформа образу й бінарного файлу | ARM/x86 або пошкоджений виконуваний файл |
| Зростає диск | Журнали, образи, кеш, томи | Необмежені журнали, старі збірки, дані застосунку |

Остання колонка — гіпотези. Підтверджуйте їх доказами; код завершення не дорівнює єдиному діагнозу.

## Журнали, метрики та трасування

Пишіть журнали застосунку до stdout/stderr для збору драйвером. Додавайте час, рівень, request/correlation ID і корисний контекст без облікових даних. Деякі драйвери чи конфігурації обмежують можливості `docker logs`.

Типовий `json-file` потребує налаштування ротації, інакше журнали можуть зростати без обмежень. Проєкт обирає `local`. Метрики ресурсів описують контейнер і хост; затримка, помилки та трасування — поведінку для користувача. `docker stats` є локальним знімком, а не історією моніторингу.

## Ліміти та продуктивність

Контейнер не отримує власну необмежену машину. Налаштовуйте та перевіряйте ліміти пам’яті, CPU і процесів. Квота CPU може сповільнювати сервіс, нестача пам’яті — завершувати його. Ліміти VM Desktop обмежують усі контейнери, навіть якщо фізичної RAM ноутбука більше.

Визначайте робочий набір і навантаження застосунку, не переносіть ліміт цього малого проєкту до production навмання. Bind mount на Linux і Desktop може мати різну продуктивність. Емуляція додає ще одну змінну до порівняння ноутбука й сервера.

## Діагностика мінімальних образів

Почніть із наявних інструментів: проєкт має Python, тому використовуйте його бібліотеки DNS та HTTP. Не очікуйте `bash`, `ps`, `curl` або пакетний менеджер в іншому образі. Обирайте погоджені тимчасові інструменти замість інтерактивного встановлення пакетів у production-контейнер.

Для зупиненого сервісу `exec` не працює. Читайте журнали й метадані, досліджуйте конфігурацію образу або відтворюйте запуск в ізольованому середовищі з тими самими параметрами.

## Контрольне запитання та відповідь

**Запитання:** Після перезапуску сервіс працює, але за кілька годин знову ламається. Частіші перезапуски — повне виправлення?

**Відповідь:** Ні. Це може тимчасово скидати витік пам’яті, вичерпані з’єднання, заповнене тимчасове сховище чи застарілий стан залежності. Зберіть історію ресурсів і застосунку, відтворіть умову та виправте причину. Політика перезапуску допомагає відновленню, але не є діагнозом.

## Підсумок

Збирайте докази до видалення ресурсів. Розрізняйте відмови застосунку, контейнера, демона, VM і хоста та зберігайте історію повторних інцидентів.
