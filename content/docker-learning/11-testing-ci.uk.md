# Тестування контейнерів і CI

## Результати

Використовуйте контейнери як тестову інфраструктуру, не плутаючи контейнеризацію з покриттям перевірками. Розрізняйте тести застосунку, образу, інтеграції та релізні умови.

## Рівні перевірки

| Рівень | Доказ |
| --- | --- |
| Застосунок | Коректна поведінка, негативні випадки, конкурентність, обробка відмов |
| Образ | Правильні файли, користувач, архітектура та команда запуску |
| Стек | DNS, готовність, монтування, права та взаємодія сервісів |
| Реліз | Погоджений дайджест, політика аналізу, відтворювані дані та smoke-перевірка |

Модульні тести можуть працювати без Docker. Інтеграційні перевірки мають використовувати відповідний рушій і сімейство версій бази та шлях міграцій, якщо це впливає на поведінку. Контейнер не скасовує проєктування даних і очищення.

## Запуск перевірок проєкту

З кореня репозиторію перевірте застосунок без Docker:

```sh
python3 -m unittest discover -s examples/docker-learning -p 'test_*.py' -v
```

Потім із директорії проєкту:

```sh
docker compose up --build -d --wait --wait-timeout 90
docker compose --profile checks run --rm --no-deps checks
docker compose up -d --force-recreate --wait --wait-timeout 90 api
docker compose --profile checks run --rm --no-deps checks --require-existing
```

Перший набір охоплює контракти, конкурентні збільшення, відмову сховища, збереження після заміни процесу та коректну зупинку. Перевірки стека додатково досліджують DNS контейнерів і збереження після заміни контейнера. Саме успішне `docker build` цього не доводить.

## Побудова CI-задачі

Надійний конвеєр отримує точну ревізію, перевіряє конфігурацію, збирає образ, запускає залежності з обмеженим очікуванням готовності, виконує тести, зберігає журнали збоїв і прибирає лише власні ресурси. Очищення не повинне втрачати початковий код помилки.

Використовуйте унікальні назви проєктів і не діліть фіксовані порти між паралельними задачами. Не відкривайте облікові дані реєстру чи потужний socket демона недовіреному коду PR. Публікуйте після успішних перевірок і фіксуйте дайджест релізу. Для офіційних build actions обирайте перевірені версії, обмежені права й належний доступ до кешу.

## Testcontainers та інтеграція з фреймворками

Testcontainers дозволяє тестам запускати тимчасові залежності та отримувати їхні опубліковані адреси. API та модулі різняться між мовами: читайте документацію конкретної бібліотеки Python, Java, .NET чи Node. Очікуйте змістовної готовності, а не фіксованої паузи.

Pytest fixtures можуть керувати життєвим циклом залежностей; Robot Framework — викликати контрольовану бібліотеку налаштування; Playwright — звертатися до URL застосунку зі стека. Залишайте перевірки поведінки в обраному фреймворку, не переносіть увесь набір до shell. Браузерним тестам усе одно потрібні сумісні образи та системні бібліотеки.

## Діагностика збоїв і нестабільності

Перед видаленням контейнерів зберігайте журнали, коди завершення, історію здоров’я та стан ресурсів. Не залишайте в артефактах облікові дані й реальні персональні записи. Повідомлення таймаутів мають розрізняти помилку завантаження образу, готовності та assertion.

Кеш прискорює збірку, але не доводить правильність. Повторне використання змінюваного стану бази між CI-задачами може приховувати збої міграцій і створювати залежність від порядку. Скидайте або ізолюйте дані, повторно використовуючи лише навмисні кеші.

## Контрольне запитання та відповідь

**Запитання:** CI успішний, хоча тестовий контейнер завершився з помилкою. Що перевірити?

**Відповідь:** З’ясуйте, як runner передає код завершення контейнера. Фоновий запуск або успішне очищення можуть приховати провал. Використовуйте одноразовий `compose run` із перевіркою статусу або явно налаштовану політику коду завершення стека.

## Підсумок

Окремо перевіряйте поведінку й пакування, зберігайте діагностику та передавайте помилки. Контейнери роблять залежності відтворюваними за контрольованих вхідних даних і життєвого циклу.
