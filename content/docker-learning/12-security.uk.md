# Безпека та ланцюг постачання образів

## Результати

Визначайте практичну модель загроз, обмежуйте привілеї, захищайте облікові дані збирання й виконання та правильно тлумачте аналіз вразливостей і атестації артефактів.

## Багаторівнева ізоляція

Контейнери використовують важливі спільні ресурси хоста. Дефект застосунку, зайві capabilities, записуваний шлях хоста чи відкритий демон можуть змінити межу безпеки. Для ворожого коду обирайте сильнішу ізоляцію, якщо цього потребує модель загроз.

Непривілейований користувач застосунку зменшує права всередині контейнера. Rootless Docker також запускає демон без root-привілеїв хоста. Це різні механізми; один не означає інший. Обидва не усувають усіх вразливостей ядра чи застосунку.

## Посилення конфігурації виконання

Проєкт демонструє сумісні обмеження:

```yaml
read_only: true
cap_drop: [ALL]
security_opt: ["no-new-privileges:true"]
mem_limit: 128m
pids_limit: 64
```

Образ задає UID/GID 10001, `/data` є записуваним томом, `/tmp` — tmpfs. Перед застосуванням до іншої програми перевірте необхідні записи й системні виклики. Seccomp та політики хоста AppArmor/SELinux додають обмеження; не вимикайте їх глобально заради успішного тесту.

## Захист межі демона

Доступ до rootful Docker daemon може дати контроль над хостом. Монтування `/var/run/docker.sock` — значне надання привілеїв, навіть якщо сервіс називає себе «просто панеллю». Bind mount socket лише для читання не перетворює Docker API на API лише для читання.

Уникайте `--privileged`, широких монтувань хоста та неавтентифікованих TCP-інтерфейсів демона. Використовуйте перевірену автоматизацію з обмеженим призначенням та автентифікований віддалений доступ. Обмежуйте запуск коду на власних CI-агентах із доступом до демона.

## Аналіз та підтримка залежностей

Перевіряйте системні пакети й залежності застосунку погодженим сканером. Оцінюйте серйозність, можливість експлуатації, досяжність, виправлення та винятки з власником і строком. Аналіз є знімком за змінюваною базою вразливостей, а не доказом безпеки.

Залишайте в образі зрозумілий мінімальний склад. Фіксуйте погоджені артефакти, перебудовуйте для виправлень, перевіряйте походження основи та не завантажуйте неперевірені інсталяційні скрипти. Мінімальний образ теж може містити вразливий застосунок.

## SBOM, походження та підписування

| Доказ | На що відповідає | Чого не доводить |
| --- | --- | --- |
| SBOM | Які компоненти зафіксовано? | Відсутність вразливостей |
| Provenance | Які процес і вхідні дані збірки заявлено? | Надійність самого процесу |
| Підпис | Чи підписаний вміст довіреною особою або ключем? | Правильність чи нешкідливість |

BuildKit може додавати SBOM і provenance; важлива підтримка реєстру та формату виводу. Перевірка підпису має обмежувати очікуваного підписувача й issuer або довірений ключ і перевіряти потрібний дайджест. Наявності будь-якого валідного підпису недостатньо. Користуйтеся актуальними інструкціями Cosign для своєї моделі довіри, а не необмеженою командою з прикладу.

## Контрольне запитання та відповідь

**Запитання:** Образ підписано, критичних знахідок немає. Чи можна безпечно дати йому Docker socket хоста?

**Відповідь:** Ці факти не обґрунтовують такий привілей. Підпис визначає підписувача, сканер покриває відомі виявлювані проблеми. Обидва не обмежують дії коду через демон. Окремо оцініть потребу в socket і за можливості оберіть вужчий доступ.

## Підсумок

Поєднуйте мінімальні привілеї, захист облікових даних, оновлення залежностей і явну довіру до артефактів. Перевіряйте, що обмеження зберігають потрібну поведінку й обробку відмов.
