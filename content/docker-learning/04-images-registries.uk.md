# Образи, реєстри та ідентичність артефакту

## Результати

Пояснюйте шари образу, відрізняйте тег від дайджесту, перевіряйте цільову платформу та передавайте перевірений артефакт через реєстр без розкриття облікових даних.

## Шари файлової системи та метадані

Образ поєднує шари файлової системи з конфігурацією: типовою командою, робочою директорією та змінними середовища. Шари повторно використовуються, якщо їхній вміст збігається. Запущений контейнер додає записуваний шар; зміни в ньому не оновлюють вихідний образ.

Видалення секрету в пізнішому шарі збірки не прибирає його з попереднього. Менша видима файлова система не доводить відсутність даних у старіших шарах. Виключайте конфіденційні файли до передавання контексту збирачу.

## Назви, теги та дайджести

| Посилання | Значення |
| --- | --- |
| `python:3.13-slim` | Репозиторій і читабельний змінюваний тег |
| `registry.example.com/team/api:release-42` | Повна адреса репозиторію та тег |
| `repository@sha256:...` | Ідентифікатор маніфесту або індексу, обчислений за вмістом |

Теги можуть змінюватися. Дайджест визначає конкретний вміст, але дайджест індексу може посилатися на кілька маніфестів для різних платформ. Для розслідування відмінностей ARM64 та AMD64 фіксуйте індекс і платформу.

Фіксація дайджесту допомагає визначити артефакт, але не встановлює майбутні виправлення безпеки. Плануйте перебудови й оновлюйте погоджені дайджести з перевіркою.

## Дослідження реального образу

```sh
docker pull python:3.13-slim
docker image inspect python:3.13-slim --format '{{json .RepoDigests}}'
docker image inspect python:3.13-slim --format '{{.Os}}/{{.Architecture}}'
docker image history python:3.13-slim
docker buildx imagetools inspect python:3.13-slim
```

Для фіксації копіюйте повний дайджест із результату; скорочення `sha256:...` не є придатним для запуску посиланням. Історія пояснює шари, але не замінює перевірку коду й аналіз вразливостей.

## Робота з реєстром

Зберіть образ локально, виконайте перевірки, призначте незмінну ідентичність релізу, автентифікуйтеся в потрібному реєстрі та завантажте образ. Використовуйте credential helper або секрет CI. `docker login --password-stdin` не передає пароль аргументом команди, але джерело вводу теж не повинне потрапляти в журнали чи історію shell.

Для власного реєстру замініть умовний хост і простір імен:

```sh
docker tag gimmejob-docker-course:local registry.example.com/team/docker-course:release-1
docker push registry.example.com/team/docker-course:release-1
```

Спочатку зберіть локальний підсумковий проєкт. Реєстр у прикладі умовний. Локальний тег нічого не публікує. Права доступу, мережа та політика зберігання реєстру — окремі питання.

## Просування та відтворюваність

Просувайте той самий перевірений дайджест замість окремих збірок для staging і production. Зберігайте ревізію Dockerfile, файли фіксації залежностей, параметри збірки, платформу й результати аналізу. Змінюваний базовий тег, нефіксована залежність або завантажуваний скрипт можуть змінити повторну збірку того самого коду.

Помилка pull може означати неправильні облікові дані, відсутній репозиторій, платформу, ліміт запитів або збій мережі. Досліджуйте конкретну відповідь перед заміною образу випадковим публічним аналогом.

## Контрольне запитання та відповідь

**Запитання:** Staging і production використовують `api:latest`. Це доводить однакову збірку?

**Відповідь:** Ні. Тег міг змінитися, хости могли кешувати різні образи, а платформні маніфести — відрізнятися. Порівняйте дайджест розгорнутого артефакту та платформу, потім конфігурацію виконання. Однакового читабельного тегу недостатньо.

## Підсумок

Використовуйте теги для зручних назв, дайджести — для ідентичності релізу. Не додавайте облікові дані до образів, зберігайте докази перевірок і плануйте оновлення зафіксованих артефактів.
