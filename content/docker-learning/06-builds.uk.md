# BuildKit, кешування та платформи

## Результати

Відокремлюйте інструменти збирання від залежностей виконання, розумійте скидання кешу, захищайте секрети збірки та пояснюйте відмінності ARM64 і AMD64.

## Кеш як оптимізація

BuildKit повторно використовує відповідні результати збірки. Розміщуйте стабільні дорогі кроки встановлення залежностей перед файлами застосунку, які часто змінюються. Для Python чи Node спочатку копіюйте зафіксовані файли залежностей, встановлюйте пакети з них, потім копіюйте код.

Використання кешу не доводить актуальність безпеки. `--no-cache` вимикає кеш збірки, але сам не гарантує свіжий базовий образ; `--pull` запитує новіші метадані основи. Відтворюваність потребує явних версій вхідних даних і контрольованого кешу.

## Багатоетапні збірки

Цей самодостатній приклад створює сторінку на одному етапі та копіює лише артефакт до середовища виконання:

```dockerfile
FROM python:3.13-slim AS build
WORKDIR /build
RUN mkdir /out && python -c "from pathlib import Path; Path('/out/index.html').write_text('<h1>Built artifact</h1>')"

FROM nginx:stable-alpine AS runtime
COPY --from=build /out/ /usr/share/nginx/html/
```

Збережіть як Dockerfile у порожній навчальній директорії. Зберіть через `docker build -t docker-course-site .`, запустіть через `docker run --rm -p 127.0.0.1:18081:80 docker-course-site`. Очікуйте сторінку “Built artifact”. Приклад пояснює межі етапів; стандартний nginx-образ не демонструє непривілейоване посилення захисту з підсумкового проєкту.

## Монтування кешу та секретів

Cache mount може зберігати завантажені пакети між збірками без копіювання до фінального образу. Secret mount відкриває доступ до облікових даних на вибраному кроці. Обидва механізми не завадять вашій команді надрукувати чи скопіювати секрет.

Умовна форма встановлення приватних залежностей потребує ваших файлів залежностей і погодженої конфігурації пакетів:

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    --mount=type=secret,id=pip_config,target=/etc/pip.conf \
    python -m pip install -r requirements.txt
```

Передайте секрет через `docker build --secret id=pip_config,src=private-pip.conf ...`. Не передавайте облікові дані через ARG або ENV і виключіть секретний файл із контексту.

## Багатоплатформні образи

Mac з Apple silicon зазвичай використовує `linux/arm64`, багато серверів — `linux/amd64`. Індекс багатоплатформного образу вибирає відповідний маніфест. Скомпільовані розширення та зовнішні бінарні файли теж мають підтримувати цільову платформу.

Перед примусовою емуляцією дослідіть конфігурацію:

```sh
docker buildx ls
docker buildx imagetools inspect python:3.13-slim
```

Багатоплатформні збірки використовують емуляцію, нативні збирачі або кроскомпіляцію. Емуляція може бути повільнішою та приховувати платформні дефекти. Збирання `linux/amd64` на ARM не замінює перевірку в цільовому середовищі.

## Результат збирання та типові збої

Для сумісного збирача `--load` імпортує одноплатформну збірку в локальне сховище. `--push` публікує її до реєстру. Не кожен драйвер Buildx додає успішну збірку до `docker image ls`. Локальне завантаження кількох платформ залежить від сховища та збирача; перевіряйте свою конфігурацію.

Типові збої: відсутня архітектура, немає нативних wheel-пакетів, жорстко задані x86-файли, застарілий кеш або інструменти збирання у фінальному етапі. Досліджуйте конкретний крок і цільову платформу.

## Контрольне запитання та відповідь

**Запитання:** Успішної збірки Buildx немає в `docker image ls`. Вона непомітно зламалася?

**Відповідь:** Не обов’язково. Результат міг залишитися в кеші збирача або бути опублікованим віддалено. Перевірте драйвер і параметри виводу. Свідомо обирайте відповідний режим `--load` чи `--push`.

## Підсумок

Оптимізуйте повторну роботу, фіксуйте вхідні дані та перевіряйте артефакт на цільовій платформі. Кеш, облікові дані й вміст фінального образу мають окремі життєві цикли.
