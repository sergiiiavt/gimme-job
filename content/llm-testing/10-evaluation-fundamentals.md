An **eval** is a repeatable test of an LLM feature's quality over a dataset, with a defined scoring method and a decision threshold. This chapter covers the core of the job: turning "looks good to me" into a scorecard you can compare between versions.

## 1. Evals vs tests

| | Classic test | Eval |
|---|---|---|
| Expected result | One exact oracle | A scoring rule: assertion, metric, rubric or human label |
| Outcome | Pass or fail | Score per case, aggregated into rates and distributions |
| Determinism | Expected to be stable | Run-to-run variation is normal and must be measured |
| Purpose | Prove a requirement holds | Measure quality, compare versions, catch regressions |
| Typical size | One case per behaviour | Dozens to thousands of cases per behaviour |

In practice you need both. Deterministic tests protect the code around the model. Evals measure the behaviour of the model inside your product.

## 2. The LLM test pyramid

```text
               /  production monitoring  \      live traffic, online judges, user feedback
              /     human review          \     expert labels on samples
             /   model-graded evals        \    LLM-as-a-judge with calibrated rubrics
            /  reference-based metrics       \  similarity, overlap, retrieval metrics
           /  deterministic assertions        \ schema, regex, contains, length, cost, latency
          /  unit tests with a fake model      \ parsing, routing, retries, tool loop
```

Lower layers are cheap, fast and precise. Upper layers are expensive and noisy but measure what users actually care about. Push every check as low as it can go: never ask a judge model whether output is valid JSON.

## 3. Error analysis first

Do not start by picking metrics from a framework. Start by looking at data.

1. Run the system on 50–100 realistic inputs.
2. Read every output. Write a short free-text note on anything wrong.
3. Group the notes into categories. This is **open coding**, followed by **axial coding**: merging similar notes into a **failure taxonomy**.
4. Count how often each category happens.
5. Write evals for the most frequent and most severe categories.

A failure taxonomy for a support bot might look like:

| Failure category | Count / 100 | Severity |
|---|---|---|
| Answer not supported by docs (hallucinated policy) | 9 | High |
| Correct answer, missing citation | 14 | Medium |
| Did not call order tool when needed | 6 | High |
| Too long, buries the answer | 11 | Low |
| Wrong language reply | 3 | Medium |

Metrics chosen this way measure real problems. Generic metrics chosen up front often measure nothing that matters to your product.

## 4. Golden datasets

A **golden dataset** is a versioned set of inputs, with expected outputs or grading notes where possible.

Sources of good cases:

- real user inputs (anonymized), sampled across segments;
- failures found in error analysis and production incidents;
- edge cases: empty input, very long input, mixed languages, typos, ambiguous questions;
- adversarial cases: injections, jailbreak attempts, off-topic requests;
- synthetic cases generated by a model, then reviewed by a human.

A practical JSONL format:

```json
{"id": "refund-007", "input": "Can I return shoes after 40 days?", "expected_facts": ["30-day return window"], "must_not": ["yes, you can"], "tags": ["refunds", "policy-boundary"], "source": "prod-sample-2026-09"}
```

Rules:

- version datasets in Git next to the prompts they test;
- tag cases so you can score by segment (language, feature, difficulty);
- keep a **held-out** subset you do not look at while tuning prompts, so you do not overfit to the eval;
- add every production failure as a new case: the dataset should only grow.

## 5. Deterministic assertions

Many quality requirements are checkable without any model:

| Assertion | Example |
|---|---|
| Schema validity | Output parses as JSON and matches the Pydantic model |
| Contains / not contains | Answer contains the order ID; never contains "as an AI language model" |
| Regex | Phone numbers match the local format; no email addresses leak |
| Length | Summary under 280 characters |
| Language | Reply language matches the user's language |
| Citations | Every cited ID exists in the retrieved set |
| Latency budget | p95 under 4 seconds |
| Cost budget | Under 2,000 tokens per request |

These run on every case, cost almost nothing and never disagree with themselves.

## 6. Reference-based metrics

When a reference answer exists, you can compare the output with it.

| Metric | Measures | Watch out for |
|---|---|---|
| Exact match | Identical string | Too strict for free text; fine for classification labels |
| Token F1 | Word overlap with the reference | Rewards copying words, ignores meaning |
| BLEU / ROUGE | n-gram overlap, from translation and summarization research | Correlate poorly with human judgement for open-ended answers |
| BERTScore | Similarity of contextual token embeddings | Better than n-grams, still blind to negation and factual errors |
| Embedding cosine similarity | Semantic closeness of whole texts | Threshold depends on model; "approved" vs "not approved" can score high |

Use reference metrics for narrow tasks (classification, extraction, short factual answers). For open-ended answers, check **facts** instead: does the answer contain each expected fact and none of the forbidden claims?

## 7. Evaluation frameworks

You can write evals in plain pytest. Frameworks add datasets, scoring, caching, reporting and CI integration.

**promptfoo** uses a declarative YAML config and fits CI pipelines well:

```yaml
description: Support bot refunds
prompts:
  - file://prompts/support_v3.txt
providers:
  - id: openai:gpt-4.1-mini
tests:
  - vars:
      question: Can I return shoes after 40 days?
    assert:
      - type: icontains
        value: 30 days
      - type: not-icontains
        value: yes, you can
      - type: llm-rubric
        value: States that returns are accepted only within 30 days and offers a next step
```

**DeepEval** uses a pytest style:

```python
from deepeval import assert_test
from deepeval.metrics import AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase

def test_refund_answer_is_relevant():
    question = "Can I return shoes after 40 days?"
    case = LLMTestCase(input=question, actual_output=support_bot(question))
    assert_test(case, [AnswerRelevancyMetric(threshold=0.7)])
```

Other common choices: **Inspect AI** (from the UK AI Security Institute) for structured eval tasks and agents, **OpenAI Evals**, **Braintrust** and **Opik**. Choose one for offline evals, learn it well, and avoid framework-specific metrics you cannot explain.

## 8. Reading a scorecard

An eval run should produce a comparison, not a single number:

| Metric | Baseline (prompt v2) | Candidate (prompt v3) | Δ |
|---|---|---|---|
| Schema valid | 100% | 100% | 0 |
| Expected facts present | 81% | 88% | +7 pp |
| Forbidden claims | 4% | 1% | −3 pp |
| Citation valid | 86% | 85% | −1 pp |
| Median tokens | 410 | 520 | +27% |

Then look at the cases that changed. Aggregate scores hide regressions in small but critical segments. Always read the flipped cases (pass to fail and fail to pass) before approving a change.

## 9. QA quick reference

- Error analysis before metrics. Read outputs, build a failure taxonomy, count.
- Push checks down the pyramid; never use a judge for something regex can check.
- Version datasets, tag cases, keep a held-out set, grow with every incident.
- Prefer fact checks over n-gram metrics for open-ended answers.
- Compare against a baseline and read the flipped cases.
