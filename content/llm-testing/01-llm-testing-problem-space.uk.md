# Чим особливе тестування LLM

Тестування програмного забезпечення з великою мовною моделлю (LLM) змінює припущення класичного тест-дизайну. Ті самі вхідні дані можуть давати різні результати. Хибна відповідь звучить так само впевнено й переконливо, як правильна. Очікуваним результатом часто є множина прийнятних відповідей. Поведінка змінюється навіть без правок коду: через оновлення моделі, промпту, знайдених даних чи інфраструктури постачальника.

Розділ пояснює проблему, типи тестових оракулів для згенерованих відповідей, характеристики якості та місце тестування LLM у життєвому циклі системи. На цих визначеннях ґрунтуються наступні розділи.

**Передумови:** тестовий базис, тестовий оракул і рівні тестування з [Основ QA](/reference/qa-fundamentals), а також Python на рівні читання коротких скриптів. Також див. [Огляд генеративного AI та LLM](/learn/llm?topic=generative-ai-overview) і [Як LLM генерують текст](/learn/llm?topic=llm-foundations).

## Що називаємо системою на основі LLM

**Велика мовна модель (large language model, LLM)** — нейронна мережа, навчена передбачати наступний токен тексту. Тут «модель» означає цей компонент: набір ваг, доступний через API постачальника або на вашій інфраструктурі.

**Система на основі LLM**, або **LLM-застосунок**, — програмне забезпечення навколо одного чи кількох викликів моделі. Вона містить промпти, збирання контексту, пошук, інструменти, розбір відповідей, захисні механізми, інтерфейс, журналювання та дані. **Функція на основі LLM** — окрема можливість, наприклад відповіді на питання про правила повернення товару.

```diagram
User and business outcome        (did the customer get a correct, safe answer?)
          ▲
Product feature                  (support assistant answers refund questions)
          ▲
LLM application                  (prompt templates, retrieval, tools, parsing, guardrails, UI)
          ▲
Model                            (weights, decoding, provider-side system behaviour)
          ▲
Training data and training process
```

Кожен рівень має своїх тестувальників і свої питання:

| Рівень | Типове питання | Хто відповідає | Типові докази |
|---|---|---|---|
| Модель | Наскільки добре модель міркує, пише код чи володіє мовою? | Постачальник, дослідники | Порівняльні тести, картки моделей, звіти з імітації атак |
| Застосунок | Чи дають промпт, пошук і розбір правильні результати для наших запитів? | Інженери продукту та QA | Набори оцінювання, оцінювачі, модульні й інтеграційні тести |
| Функція | Чи виконано критерії приймання й обмеження ризику? | QA, власник продукту | Критерії з порогами, регресійні перевірки |
| Результат для користувача | Чи система допомагає й не завдає шкоди? | Продуктова команда, аналітики, QA | Моніторинг, відгуки, дані інцидентів |

Більшість тестувальників працює на рівнях застосунку й функцій. Ваги моделі ви контролюєте рідко, але обираєте модель, версію, промпти, дані, інструменти, перевірку відповідей і моніторинг. Ці керовані частини створюють багато дефектів і становлять основний предмет курсу.

## Чим функції LLM відрізняються від звичайних

Порівняймо калькулятор ціни зі звичайними правилами й асистента, що відповідає на питання про ціни природною мовою.

| Вимір | Звичайна функція | Функція на основі LLM |
|---|---|---|
| Специфікація | Точні правила: «знижка 10% понад 100 EUR» | Відкритий намір: «відповідай корисно і правильно» |
| Простір результатів | Обмежений і структурований: число | Практично необмежений: довільний текст |
| Детермінізм | Ті самі дані дають той самий результат | Ті самі дані можуть давати різні результати |
| Типовий збій | Виняток, неправильне число, аварійне завершення | Переконлива, але хибна чи небезпечна відповідь |
| Джерела змін | Код і конфігурація | Код, промпт, модель, знайдені дані, інструменти, інфраструктура |
| Покриття вхідних даних | Класи еквівалентності в обмеженому просторі | Семантичний простір формулювань користувачів |
| Вартість запуску | Зазвичай мала | Час і гроші на кожен виклик |

З цього випливають три наслідки, що формують решту курсу:

- **Точного очікуваного значення часто недостатньо.** Потрібні інші оракули, описані далі.
- **Один запуск — спостереження, а не остаточний висновок.** Повторюйте випадки й вимірюйте частки успіхів та збоїв ([Статистика для оцінювання](/learn/llm?topic=eval-statistics)).
- **Поведінка змінюється без правок коду.** Фіксуйте версії й продовжуйте перевірки після випуску ([Якість у промисловому середовищі](/learn/llm?topic=production-quality)).

## Проблема тестового оракула

**Тестовий оракул (test oracle)** — джерело для визначення правильності спостережуваного результату. У класичному тесті ним часто є задане очікуване значення: `assert total == 90.0`.

Для згенерованого тексту одного рядка недостатньо. Стислий виклад звернення до підтримки має тисячі правильних формулювань і може бути частково хибним: чотири факти правильні, один вигаданий. Це **проблема оракула (oracle problem)** — визначення правильності там, де еталонний результат важко обчислити.

Поєднуйте оракули з обмеженими можливостями: кожен перевіряє окремий аспект, а разом вони підвищують упевненість у якості.

| Тип оракула | Що перевіряє | Приклад | Перевага | Обмеження |
|---|---|---|---|---|
| Властивість або обмеження | Вимоги до кожної відповіді | Коректний JSON, ID замовлення, до 80 слів | Дешево й детерміновано | Формат не доводить правильності змісту |
| Порівняння з еталоном | Відомі факти чи правильну відповідь | Згадано 30-денний строк повернення | Підходить для фактичних завдань | Потрібні еталони; формулювання різняться |
| Модель-оцінювач (LLM-as-a-judge) | Відповідність рубриці | Чи підтверджує джерело кожне твердження? | Масштабує змістове оцінювання | Сама потребує перевірки |
| Людське оцінювання | Експертний вердикт | Керівник підтримки оцінює прийнятність | Еталон для суб’єктивних критеріїв | Дорого; можливі розбіжності |
| Метаморфне відношення | Зв’язок результатів після зміни запиту | Перефразування зберігає факти | Не потрібна точна еталонна відповідь | Послідовність не доводить правильності |
| Диференційне оцінювання | Різницю між версіями | Попарне порівняння промптів | Показує відносне поліпшення | Не вимірює абсолютну якість |

### Приклад перевірок властивостей відповіді

Вимога: *«Відповідь називає 30-денний строк повернення, дотримується правил магазину, не перевищує 80 слів і містить посилання на сторінку повернень».* Окремі перевірки дешево виявляють різні класи помилок, але не доводять повної правильності.

```python
import re

RETURN_WINDOW_DAYS = 30
MAX_WORDS = 80


def check_refund_answer(answer: str) -> list[str]:
    """Return the properties this answer violates. An empty list means every check passed."""
    violations = []
    text = answer.lower()
    if f"{RETURN_WINDOW_DAYS} days" not in text and f"{RETURN_WINDOW_DAYS}-day" not in text:
        violations.append("does not state the 30-day return window")
    if re.search(r"\b(guarantee[sd]?|always|no questions asked)\b", text):
        violations.append("promises more than the policy allows")
    if len(answer.split()) > MAX_WORDS:
        violations.append(f"longer than {MAX_WORDS} words")
    if "stride.example/returns" not in text:
        violations.append("does not link to the returns page")
    return violations


candidates = [
    "You can return unworn shoes within 30 days of delivery for a full refund. "
    "Start a return at https://stride.example/returns.",
    "Of course! Refunds are guaranteed for every purchase, no questions asked.",
    "Our return policy gives you a 30-day window. " + "We value every customer. " * 20
    + "Details: https://stride.example/returns",
]

for number, answer in enumerate(candidates, start=1):
    problems = check_refund_answer(answer)
    verdict = "PASS" if not problems else "FAIL: " + "; ".join(problems)
    print(f"answer {number}: {verdict}")
```

Результат:

```text
answer 1: PASS
answer 2: FAIL: does not state the 30-day return window; promises more than the policy allows; does not link to the returns page
answer 3: FAIL: longer than 80 words
```

Відповідь «30 днів від покупки» пройде ці перевірки навіть тоді, коли правила встановлюють строк від доставки. Потрібне зіставлення з еталоном або перевірена модель-оцінювач. Тому реальні набори поєднують різні оракули.

## Джерела варіативності

Зміну результату між запусками можуть спричинити такі джерела:

| Джерело | Механізм | Наслідок для тест-дизайну |
|---|---|---|
| Вибірка токенів (sampling) | Наступний токен вибирається з розподілу ймовірностей | Повторюйте випадки й вимірюйте частоти |
| Недетермінованість виконання | Арифметика GPU, пакетна обробка й обладнання можуть впливати навіть за температури 0 | Не покладайтеся на незмінний рядок |
| Версія моделі | Оновився знімок або версія за псевдонімом «latest» | Фіксуйте версії й перевіряйте перехід |
| Промпт і конфігурація | Змінилися інструкції, параметри чи інструмент | Версіонуйте й оцінюйте зміни |
| Знайдений контекст | Індекс повертає інші фрагменти | Записуйте їх ID; фіксуйте контекст регресійних тестів |
| Інструменти й зовнішні дані | API повертають нові відомості | Використовуйте імітації й записані відповіді |
| Стан розмови | Репліки, пам’ять і профіль змінюють контекст | Перевіряйте багатокрокові діалоги й межі стану |

Дрейф поведінки є реальним ризиком. У дослідженні 2023 року ті самі API-версії перевіряли з інтервалом у три місяці й виявили зміни на кількох завданнях ([Chen, Zaharia and Zou](https://arxiv.org/abs/2307.09009)). Зафіксовані версії допомагають керувати моментом переходу.

### Діагностика зміни без нового розгортання

Порівняйте трасування успішного й невдалого запусків поле за полем:

| Дані трасування | Можливе пояснення |
|---|---|
| Ті самі дані, різні відповіді між повторами | Варіативність генерації: потрібна оцінка частот |
| Інша модель чи відбиток конфігурації виконання | Оновлення постачальника або псевдоніма |
| Інші ID фрагментів | Змінився індекс |
| Інша версія промпту | Зміна інструкцій окремо від коду |
| Інша історія розмови чи профіль користувача | Поведінка залежить від стану |
| Інші результати інструментів | Зміни зовнішніх даних |

Для цього потрібне трасування версій і контексту; див. [Якість у промисловому середовищі](/learn/llm?topic=production-quality).

### Чому одного успіху недостатньо

Якщо ймовірність успіху в незалежному запуску дорівнює `p`, імовірність усіх `k` успіхів становить `p` у степені `k`. Симуляція показує, як функція з дефектом проходить швидку ручну перевірку і як оцінка частки успіхів уточнюється після численних запусків.

```python
import random

# Probability that k independent manual tries all look correct
for p_correct in [0.95, 0.9, 0.7]:
    for tries in [3, 5]:
        print(f"feature correct {p_correct:.0%} of the time -> {tries} tries all pass with probability {p_correct ** tries:.2f}")

# Estimating the real rate from repeated runs of a feature that is correct 90% of the time
rng = random.Random(42)
true_rate = 0.9
for runs in [10, 100, 1000, 10000]:
    passed = sum(rng.random() < true_rate for _ in range(runs))
    print(f"{runs:>5} runs: observed pass rate {passed / runs:.3f}")
```

Результат:

```text
feature correct 95% of the time -> 3 tries all pass with probability 0.86
feature correct 95% of the time -> 5 tries all pass with probability 0.77
feature correct 90% of the time -> 3 tries all pass with probability 0.73
feature correct 90% of the time -> 5 tries all pass with probability 0.59
feature correct 70% of the time -> 3 tries all pass with probability 0.34
feature correct 70% of the time -> 5 tries all pass with probability 0.17
   10 runs: observed pass rate 1.000
  100 runs: observed pass rate 0.900
 1000 runs: observed pass rate 0.894
10000 runs: observed pass rate 0.904
```

Функція з одним збоєм на десять запусків частіше проходить п’ять ручних спроб, ніж провалює їх. Тут навіть десять спроб дали ідеальний результат. Для оцінювання частот потрібні вибірки, а для порівняння — оцінка невизначеності ([Статистика для оцінювання](/learn/llm?topic=eval-statistics)).

### Скільки запусків потрібно для рідкісного збою?

За ймовірності збою `q` імовірність не побачити його за `n` незалежних запусків дорівнює `(1 − q)^n`. Для щонайменше 95% імовірності побачити хоча б один збій потрібно `n ≥ log(0.05) / log(1 − q)`.

```python
import math

# How many independent runs are needed to see at least one failure with 95% probability,
# if the feature fails with probability q on each run?  Solve 1 - (1 - q) ** n >= 0.95.
for q in [0.2, 0.05, 0.01]:
    n = math.ceil(math.log(0.05) / math.log(1 - q))
    print(f"failure rate {q:.0%}: need {n} runs")

p_correct = 0.8
print(f"80%-correct feature passes 4 manual checks with probability {p_correct ** 4:.2f}")
```

Результат:

```text
failure rate 20%: need 14 runs
failure rate 5%: need 59 runs
failure rate 1%: need 299 runs
80%-correct feature passes 4 manual checks with probability 0.41
```

Рідкісні збої потребують численних запусків. Тому потрібні достатні набори випадків і моніторинг робочої системи.

## Характеристики якості функцій LLM

Спершу визначте, що означає якість. Ці характеристики доповнюють модель якості програмного забезпечення ISO/IEC 25010; ISO/IEC 25059 адаптує її для систем AI.

| Характеристика | Питання | Приклад збою | Перевірка |
|---|---|---|---|
| Успішність завдання | Чи правильно його виконано? | Хибна сума повернення коштів | Еталони, моделі-оцінювачі, людські оцінки |
| Відповідність джерелам (faithfulness, groundedness) | Чи підтверджене кожне твердження? | Посилання на неіснуюче правило | Зіставлення тверджень із джерелами |
| Релевантність | Чи відповідь стосується питання? | Доставка замість повернення | Змістове оцінювання |
| Повнота | Чи наведено все потрібне? | Пропущений виняток | Перелік очікуваних фактів |
| Формат | Чи правильна структура? | Пропущене поле JSON | Перевірка схеми |
| Послідовність і стійкість | Чи зберігається якість після несуттєвих змін запиту? | Перефразування змінює факти | Метаморфні тести, повтори |
| Безпечність | Чи немає шкідливих відповідей і дій? | Небезпечні інструкції | Класифікатори, атакувальні набори |
| Захищеність | Чи система протистоїть маніпуляціям? | Виконує приховані інструкції документа | Ін’єкції промптів, перевірки витоку |
| Справедливість | Чи зіставна якість для різних груп? | Гірші відповіді для певних імен | Контрфактичні тести за групами |
| Приватність | Чи належно захищені персональні дані? | Розкрита чужа адреса | Тести витоку й пошук персональних даних |
| Затримка | Чи достатня швидкість? | Перший токен через 12 секунд | Час до першого токена, p95 |
| Вартість | Чи прийнятні витрати? | 9 000 токенів на запит | Облік токенів на запит і завдання |

Пріоритети залежать від функції. Асистент рецензування коду може допускати затримку в 10 секунд, але не вигадані API. Для публічного чату важливі швидкість і безпечність.

## Від нечітких вимог до перевірюваних критеріїв

Вимогу *«Асистент має корисно відповідати про повернення коштів»* потрібно перетворити на вимірювані критерії.

```diagram
1. Users and tasks      Who asks what, in which language, with what goal?
        ↓
2. Risks                What happens if the answer is wrong, unsafe, slow or leaks data?
        ↓
3. Characteristics      Which quality characteristics matter for these risks?
        ↓
4. Criteria             Measurable statement + measurement method + threshold + priority
        ↓
5. Evidence plan        Which data, scorers and reviews will produce the measurements?
```

### Приклад: асистент із повернення коштів

*Крок 1. Користувачі й завдання.* Клієнти магазину взуття **Stride** питають англійською та українською, чи можна повернути товар, у який строк і як.

*Крок 2. Ризики.* Хибне «так» створює невиправдану обіцянку, хибне «ні» може коштувати продажу. Чужі дані порушують приватність, а затримка змушує залишати чат.

*Крок 3. Характеристики.* Відповідність правилам, коректне утримання від непідтвердженої відповіді (abstention), формат, мова, приватність і затримка.

*Крок 4, критерії.*

| ID | Критерій | Вимірювання | Поріг | Пріоритет |
|---|---|---|---|---|
| R1 | Твердження підтверджені чинними правилами | Модель-оцінювач, перевірена на 100 людських оцінках | Щонайменше 97% випадків | Критичний |
| R2 | За відсутності відповіді в правилах асистент повідомляє про це й пропонує допомогу людини | 40 питань поза правилами | Щонайменше 95% | Високий |
| R3 | До 120 слів і посилання на повернення | Програмні перевірки | 100% | Середній |
| R4 | Мова відповіді відповідає питанню | Евристика за системою письма | Щонайменше 99% | Високий |
| R5 | Немає чужих персональних даних | Контрольні дані в тестах витоку | 0 збоїв | Критичний |
| R6 | Час до першого токена | Пікове навантаження | p95 не більше 1,5 с | Високий |

*Крок 5. Докази.* Анонімізовані й синтетичні питання, перевірена модель-оцінювач для R1, програмні перевірки для R3 й R4, тести витоку для R5 і навантаження для R6. Система письма є лише евристикою: кирилиця сама по собі не доводить української мови.

Кожен критерій називає, *що* вимірюється, *як* вимірюється, *який результат прийнятний* і *наскільки це важливо*. Це мінімум, щоб критерій був тестованим.

## Місце тестування в життєвому циклі

Тестування триває протягом усього життєвого циклу, а досвід експлуатації має вдосконалювати наступні перевірки.

```diagram
 design ──► build ──► offline evaluation ──► pre-release ──► release ──► production
   │          │              │                    │             │            │
 criteria   unit tests,   datasets, scorers,   red teaming,   canary,     tracing, online
 and risks  fake models,  judges, regression   performance,   shadow      evaluation,
            prompt review baselines            release gate   traffic     feedback, alerts
   ▲                                                                         │
   └────────────── new failure cases become evaluation dataset cases ◄───────┘
```

|---|---|---|

## Типові помилки

- **Плутати демонстрацію з тестом.** Кілька вдалих відповідей мало що доводять.
- **Перевіряти лише модель**, пропускаючи промпти, пошук, розбір та інструменти.
- **Вимагати точного збігу вільного тексту**, відхиляючи правильні перефразування.
- **Вибирати метрики до аналізу помилок** ([Методологія оцінювання та набори даних](/learn/llm?topic=evaluation-fundamentals)).
- **Не записувати версії й параметри**, втрачаючи можливість пояснити результат.
- **Ігнорувати затримку й вартість**, які також є вимогами продукту.

## Підсумок

- Система на основі LLM містить керовані промпти, пошук, інструменти й перевірки поряд із моделлю.
- Поєднуйте перевірки властивостей, еталони, модельне й людське оцінювання, метаморфні та диференційні перевірки.
- Враховуйте варіативність генерації, версій, контексту й стану. Вимірюйте частоти результатів.
- Перетворюйте характеристики якості на критерії з методом вимірювання, порогом і пріоритетом.
- Тестуйте протягом життєвого циклу й поповнюйте набори оцінювання після робочих збоїв.
