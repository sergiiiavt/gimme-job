# Генеративний AI та LLM: вступ

Генеративний AI — більше, ніж чатботи, а велика мовна модель (LLM) — лише один із компонентів корисного продукту. Почнімо з загального розуміння галузі, термінів, архітектури систем і структури навчання. Досвід тестування або попередня робота з AI не потрібні.

**Prerequisites:** немає.

## AI, ML, генеративний AI та LLM

Штучний інтелект (AI) — загальна назва систем, що виконують задачі, пов'язані з інтелектуальною діяльністю людини. Частина систем працює за явними правилами. Машинне навчання (ML) натомість засвоює закономірності з даних. Deep learning — сімейство ML-методів із багатошаровими нейромережами. Transformers — архітектура, яку використовують багато сучасних мовних моделей.

Generative AI створює контент: текст, code, зображення, audio або video. LLM — генеративна модель, орієнтована передусім на мову; її часто навчають передбачати наступний token у послідовності. Класифікатор spam — це ML, але не обов'язково generative AI. Генератор зображень — generative AI, але не обов'язково LLM. Multimodal моделі стирають частину меж між категоріями.

| Поняття | Основне призначення | Приклад |
|---|---|---|
| Artificial intelligence | Широка галузь інтелектуального software | Планування і рекомендації |
| Machine learning | Засвоювати закономірності з прикладів | Виявлення шахрайства |
| Deep learning | Вивчати представлення нейромережами | Розпізнавання мовлення |
| Generative AI | Створювати новий контент | Генерація тексту чи зображення |
| Large language model | Обробляти і генерувати послідовності tokens | Відповісти на питання або пояснити code |

Це категорії, які перетинаються, а не обов'язковий стек технологій. Можна розробляти AI features без LLM, а LLM можна вбудувати у звичайне software.

## Як мовна модель створює відповідь

Tokenizer перетворює текст на tokens. Модель обробляє їхню послідовність і обчислює scores можливих наступних tokens. Decoding вибирає token, і процес повторюється до умови завершення. Модель не шукає готове речення в базі при кожному запиті. Наступний розділ пояснює tokenization, attention, sampling і training на прикладах.

Pretraining навчає модель широких статистичних закономірностей із тексту та інших даних. Instruction tuning і preference optimization можуть зробити її кориснішою, але не гарантують достовірних фактів чи стабільних міркувань. Переконлива відповідь не доводить, що модель перевірила джерело, використала калькулятор чи здійснила дію. Для зовнішньої інформації та дій потрібні інші компоненти застосунку.

При виборі моделі важливі context size, modality, latency, вартість, підтримка мов, обробка даних, спосіб deployment і якість виконання потрібної задачі. Більша модель не завжди краща: reliability і cost часто важливіші за популярність.

## Модель, застосунок і продукт

Модель — це компонент із навченими weights, логікою inference та інтерфейсом inputs і outputs. Застосунок поєднує prompts, історію сесії, retrieved information, tools, validation та business rules. Продукт додає authentication, user experience, feedback, monitoring і відповідальність за експлуатацію.

Для support assistant шлях запиту може виглядати так:

| Крок | Компонент | Відповідальність |
|---|---|---|
| 1 | Application API | Авторизувати користувача, прийняти та перевірити input |
| 2 | Orchestrator | Зібрати instructions та релевантний context розмови |
| 3 | Retriever, якщо потрібен | Знайти актуальні документи, які користувач має право читати |
| 4 | LLM | Згенерувати відповідь або запропонувати structured tool call |
| 5 | Tool executor, якщо потрібен | Авторизувати та виконати зовнішню дію |
| 6 | Output layer | Перевірити, показати чи stream результат і записати usage |

Сама модель не встановлює права на читання замовлення й не підтверджує, що refund уже відбувся. Навколишнє software забезпечує permissions і перевіряє зовнішні результати. Prompt — інструкція для моделі, а не межа безпеки.

## Поширені способи побудови систем

| Підхід | Типова задача | На що звернути увагу |
|---|---|---|
| Direct prompt | Узагальнити наданий документ | Межі context і точність |
| Structured generation | Витягнути запис у JSON | Schema validation і відсутні поля |
| Retrieval-augmented generation (RAG) | Відповідати з бібліотеки актуальних policies | Якість пошуку, freshness і access control |
| Tool calling | Перевірити дозволене замовлення | Server-side permissions і обробка помилок |
| Agents | Виконати багатокроковий workflow | Approval boundaries, цикли, cost і tracing |
| Fine-tuning | Адаптувати модель на спеціалізованих прикладах | Навчальні дані, evaluation і підтримка |

RAG і fine-tuning — не одне й те саме. RAG додає зовнішню інформацію під час запиту, а не оновлює model weights. Agent — дизайн застосунку з циклом вибору дій, а не особливий тип моделі. Structured output допомагає software розібрати відповідь, але не гарантує правдивість її вмісту.

## Базовий словник

Ці терміни постійно зустрічаються в курсі. Позначення конкретних providers можуть відрізнятися.

| Термін | Значення |
|---|---|
| Foundation model | Широко навчена модель для різних задач |
| Model weights | Вивчені parameters, що визначають поведінку нейромережі |
| Inference | Виконання навченої моделі на input |
| Token і tokenizer | Одиниця input/output та компонент, що переводить текст у token IDs |
| Context window | Максимальна послідовність tokens, включно з історією і retrieved material |
| Prompt | Вхідні дані та інструкції, зібрані для моделі |
| Message roles | Ролі на зразок system, developer і user; підтримка залежить від provider |
| Sampling і temperature | Способи вибору наступного token та регулювання варіативності |
| Embedding | Числове представлення для similarity та пошуку |
| Retrieval | Вибір релевантної інформації із зовнішніх джерел |
| RAG | Retrieval-augmented generation — додавання context до запиту моделі |
| Tool call | Структурований запит моделі до застосунку для виклику функції |
| Agent | Цикл застосунку, який обирає дії та багаторазово використовує tools |
| Multimodal | Робота з кількома типами даних |
| Grounding | Зв'язок відповіді з наданими доказами |
| Hallucination | Правдоподібний output без підтвердження фактами чи джерелами |
| Guardrail | Контроль, який обмежує, перевіряє чи блокує input/output |
| Latency і token cost | Час та обсяг ресурсів, потрібних на запит |

### Терміни evaluation, які знадобляться пізніше

Evaluation і тестування — важлива частина роботи з LLM продуктами, але детальне вивчення починається після основ. Визначення зібрані тут, щоб словник можна було використовувати із самого початку.

Інструменти й статті вживають терміни непослідовно. Цей курс використовує їх так, як визначено тут.

| Термін | Значення в цьому курсі |
|---|---|
| Evaluation (eval) | Повторюване вимірювання якості: dataset, спосіб прогнати на ньому систему, scorers і правило рішення |
| Case (sample) | Один input для оцінювання з опційною reference answer, metadata і tags |
| Dataset | Версіонована колекція cases; «golden dataset» — курований, довірений dataset |
| Scorer (grader) | Code, модель або людина, що ставить score чи вердикт одному output |
| Metric | Агрегат scores по dataset, наприклад pass rate чи середня faithfulness |
| Judge | Модель, що використовується як scorer (LLM-as-a-judge) |
| Rubric | Письмові критерії, які застосовує judge або людина |
| Reference answer | Відома хороша відповідь або факти, які вона має містити |
| Baseline | Результати поточної production версії для порівняння |
| Regression | Статистично і практично значуще падіння порівняно з baseline |
| Trace / span | Запис одного запиту і кожного кроку в ньому (model call, retrieval, tool call) |
| Hallucination (confabulation) | Гладкий output, не підтверджений фактами чи джерелами |
| Grounding | Опора output на надані джерела, яку можна перевірити через citation |
| Guardrail | Контроль навколо моделі, що блокує чи змінює inputs або outputs |
| Red teaming | Adversarial тестування, що намагається змусити систему шкідливо зламатися |
| Prompt injection | Input, що змушує модель виконувати інструкції атакувальника замість інструкцій розробника |
| Benchmark | Публічна стандартизована evaluation для порівняння моделей |
| pass@k / pass^k | Ймовірність, що хоча б одна з k спроб пройде / що всі k спроб пройдуть |

## Вибираємо найпростіше рішення

Для питання про умови повернення магазину потрібна актуальна policy. RAG застосунок може знайти текст, а tool — за потреби перевірити авторизоване замовлення. LLM пояснить результат із посиланнями на джерела. Натомість фіксоване перетворення CSV в JSON краще реалізувати детермінованим parser. Для узагальнення різних повідомлень клієнтів генерація може бути справді корисною, але privacy і формат результату все одно важливі.

Архітектура залежить від задачі: correctness, freshness, privacy, latency, складності експлуатації та cost. Тестування допомагає досягти цих цілей, але не є головним принципом структурування знань про LLM.

## Типові помилки

- Вважати кожну AI систему чатботом, а кожну нейромережу — LLM.
- Сприймати згенерований текст як факт, підтверджений зовнішнім джерелом.
- Думати, що сама модель може керувати permissions або виконувати зовнішню дію.
- Використовувати agent там, де достатньо script, пошуку чи одного model call.
- Обирати frameworks і providers до визначення задачі та меж системи.

## Підсумок

- Generative AI створює контент; LLM — одна із сімей генеративних моделей.
- Модель, застосунок і продукт мають різні обов'язки.
- Tokens, context, embeddings, RAG і tool use потрібні для різних задач.
- Спочатку вивчаємо основи й архітектуру, потім evaluation, testing і експлуатацію.
