# Тестування протягом SDLC

Модель життєвого циклу змінює організацію тестування, але не усуває аналіз ризиків, вимог і результатів.

## Практики для різних життєвих циклів

Для кожної розробницької діяльності плануйте відповідну перевірку. Починайте аналіз і дизайн рано, переглядайте робочі продукти та пояснюйте дефекти джерелом. Shift left переносить частину роботи раніше, а не скасовує пізніше тестування системи.

## Test-first і DevOps

TDD: red/green/refactor; ATDD: спільно узгоджені acceptance-tests перед реалізацією; BDD: приклади поведінки зрозумілою предметною мовою. DevOps підтримує швидкий feedback через CI/CD, але автоматичний pipeline не гарантує правильності oracle.

## Рівні тестування

Component перевіряє одиницю; component integration — взаємодію компонентів; system — систему; system integration — зовнішні системи; acceptance — відповідність потребам і готовність до використання. Межу рівня визначає об’єкт і мета, не лише назва інструмента.

## Типи тестування

Функціональні тести оцінюють що робить продукт, нефункціональні — як добре за заданими характеристиками. Black-box спирається на специфікацію, white-box — на внутрішню структуру. Для моделей якості уточнюйте редакцію стандарту, не змішуйте списки характеристик різних років.

## Підтвердження й регресія

Confirmation перевіряє конкретне виправлення; regression шукає побічні наслідки змін у раніше робочій поведінці. Один успішний повтор дефектного сценарію не покриває всі залежні компоненти.

## Тестування супроводу

Зміни, міграції, оновлення середовища та виведення системи з експлуатації потребують impact analysis. Обсяг визначають ризик, розмір зміни й залежності, а не довільний обов’язок щоразу повторювати все.

## Вибір рівня й обсягу регресії

Для зміни discount перевірте чотири правила на component-рівні, серіалізацію через API та видиму суму в системі. Відтворіть member/100 для confirmation; додайте non-member і 99/101 для regression. Спільна функція впливає на invoice, тому лише початковий сценарій недостатній.
