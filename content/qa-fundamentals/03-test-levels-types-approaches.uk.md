# Рівні, типи та підходи до тестування

Термінологія тестування стає заплутаною, коли незалежні виміри змішують в один список. **Рівень тестування** описує, де тестування розташоване відносно декомпозиції системи. **Тип тестування** описує мету або характеристику якості, що оцінюється. Static/dynamic та manual/automated — це інші незалежні виміри.

## Рівні тестування

Корисна базова модель містить чотири поширені рівні.

| Рівень | Основний фокус | Типові приклади |
| --- | --- | --- |
| Component / unit | Малий тестований компонент ізольовано або майже ізольовано | функція, клас, модуль |
| Integration | Взаємодія між компонентами або системами | сервіс–база даних, сервіс–сервіс, зовнішній провайдер |
| System | Поведінка повністю інтегрованої системи | end-to-end бізнес-можливість, характеристики якості системи |
| Acceptance | Докази того, що система прийнятна для користувачів, бізнесу чи інших стейкхолдерів | user acceptance, operational acceptance, contractual acceptance |

```diagram
Acceptance: чи прийнятна система для цільових стейкхолдерів?
        ↑
System: чи поводиться інтегрований продукт відповідно до вимог?
        ↑
Integration: чи працюють разом межі та взаємодіючі компоненти?
        ↑
Component: чи правильно поводиться найменша корисна одиниця?
```

Рівні не є жорсткою організаційною схемою. Команда може безперервно виконувати тести кількох рівнів. Важлива відмінність — **об’єкт і мета доказів**.

## Рівень тестування — не тип тестування

«Integration testing» описує рівень або scope взаємодії. «Security testing» описує мету. Перевірки безпеки можуть існувати на component, integration і system рівнях. Те саме стосується performance, reliability та багатьох інших типів тестування.

> **Поширена помилка:** сприймати «unit, integration, system, regression, smoke і performance» як один плоский список. Ці назви описують різні осі.

## Функціональне та нефункціональне тестування

Функціональне тестування перевіряє, чи надає система потрібні функції та поведінку. Нефункціональне тестування оцінює характеристики якості та обмеження, наприклад продуктивність, сумісність, надійність, взаємодію, безпеку, супроводжуваність або safety.

Розподіл корисний, але він не означає, що нефункціональні аспекти другорядні. Функція, яка повертає правильну відповідь через 90 секунд, може бути непридатною до використання. Функція, яка працює, але розкриває чутливі дані, не має прийнятної якості.

ISO/IEC 25010:2023 надає сучасну модель якості продукту, що допомагає команді визначити, для яких характеристик якості потрібні докази.

## Статичне і динамічне тестування

**Dynamic testing** виконує програмне забезпечення або систему та спостерігає за поведінкою. **Static testing** оцінює робочі продукти без виконання тестованого програмного забезпечення. Рев’ю вимог, дизайну, тест-кейсів або коду є активностями статичного тестування; інструменти static analysis — ще одна форма.

Статичне тестування може знаходити проблеми раніше за динамічне виконання, оскільки робочі продукти можна аналізувати ще до появи виконуваного ПЗ.

## Confirmation testing і regression testing

Ці поняття часто плутають.

- **Confirmation testing** перевіряє, чи конкретний дефект справді виправлено. Воно націлене на поведінку, яка раніше була неправильною.
- **Regression testing** перевіряє, чи не спричинила зміна ненавмисні проблеми в інших місцях.

```diagram
Дефект виправлено
   ├── Confirmation: чи працює початкова проблема тепер правильно?
   └── Regression: що ще могла зламати ця зміна?
```

Один тест іноді може виконувати обидві ролі, але логіка цих цілей різна.

## Smoke і sanity

«Smoke» і «sanity» широко використовуються в індустрії, але різні організації трактують їх по-різному. Тому їх краще визначати локально, а не вважати універсальними стандартними термінами.

Практична домовленість може бути такою:

- **Smoke suite:** невеликий широкий набір перевірок, який визначає, чи достатньо стабільні build або environment для глибшого тестування.
- **Sanity check:** сфокусований набір перевірок невеликої зміни або області, щоб визначити, чи є сенс продовжувати.

Важливо не сперечатися про назву, а узгодити мету, покриття та рішення, яке підтримує набір.

## Exploratory, scripted і checklist-based підходи

Scripted testing заздалегідь визначає детальні очікувані перевірки. Checklist-based testing фіксує важливі області покриття, але залишає деталі виконання тестувальнику. Exploratory testing поєднує навчання, дизайн і виконання під час дослідження продукту.

Ці підходи доповнюють один одного. Стабільний регульований workflow може потребувати детальних повторюваних процедур, тоді як функція, що швидко змінюється, може краще перевірятися exploratory-дослідженням, керованим ризиком.

## Manual і automated — це підходи до виконання

Manual versus automated **не** описує рівень тестування чи характеристику якості.

Те саме бізнес-правило можна перевірити вручну через браузер, автоматично через API, автоматично на component level або інтерактивно дослідити тестувальником. Питання полягає в тому, який спосіб виконання дає корисні докази за прийнятної вартості.

Автоматизація найсильніша, коли очікування відомі й повторюваний швидкий зворотний зв’язок має цінність. Людське дослідження найсильніше, коли важливі спостереження, навчання, судження та адаптація.

## Як обрати правильну комбінацію

Замість запитання «який тип тестування нам виконати?» опишіть задачу за кількома вимірами:

```diagram
Що тестуємо?             → component / integration / system / acceptance
Навіщо тестуємо?         → functional / security / performance / reliability / ...
Як виводимо тести?       → specification / structure / experience / collaboration
Як виконуємо?            → manual / automated / mixed
Коли застосовуємо?       → static / dynamic / pre-release / production
```

Це створює чіткіші стратегії та не дозволяє термінології підміняти собою мислення.

## Підсумок

- Рівні тестування і типи тестування — різні виміри.
- Component, integration, system і acceptance testing відповідають на різні запитання про докази.
- Функціональна коректність — лише один аспект якості продукту.
- Static testing оцінює робочі продукти без виконання ПЗ; dynamic testing спостерігає виконання.
- Confirmation testing перевіряє виправлення; regression testing шукає ненавмисні побічні ефекти.
- Smoke і sanity слід визначати через локальну мету.
- Manual і automated описують способи виконання, а не типи чи рівні тестування.
