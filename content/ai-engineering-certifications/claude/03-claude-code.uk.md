# Конфігурація та робочі процеси Claude Code

Project guidance, permissions і перевірки виконують різні функції. Наявність правил у файлі не доводить їх виконання.

## Ієрархія CLAUDE.md

Спільні команди й конвенції зберігайте в Git; особисті home-налаштування не переносяться колезі. Перевіряйте реально завантажені memory-files і область nested-правил. Не записуйте секрети або випадкову історію задач у project-memory.

## Правила за шляхом

Path-scoped rules застосовують guidance до glob, наприклад test-files у різних папках. Відокремлюйте API/UI/test інструкції за потребою, зберігаючи root коротким. Це не access-control.

## Команди й skills

Project commands і skills пакують повторні процедури; skill може виконувати роботу в fork-контексті за підтримки runtime. Спільні файли версіонуються, особисті залишаються локальними. Процедура не надає зовнішніх credentials.

## План чи пряма дія

Велика неоднозначна міграція потребує аналізу залежностей і плану. Малий зрозумілий fix можна виконати без зайвого ритуалу. Перед будь-якою зміною перевірте scope, working tree і релевантні тести.

## Claude Code у CI/CD

Noninteractive запуск має відповідний режим; машинний output перевіряйте за схемою. Обмежте credentials, дозволені commands, час і scope. Публікація review-коментарів потребує окремої авторизації; не вважайте raw-текст готовими зовнішніми діями.

## Робочий приклад

Спільні testing-conventions працюють у автора, але не в колеги. Перевірте home/project scope й завантажені файли до зміни моделі. Визначте один source of truth команд перевірки.

## Мінімальний workflow

У scratch-copy відтворіть member/100→10 замість 20, додайте незалежний тест і виправте > на >=. Запустіть focused та required checks, перегляньте diff. Reviewer отримує вимогу й evidence, а не лише впевнене «готово». Свіжий контекст зменшує anchoring, не гарантує істину.
