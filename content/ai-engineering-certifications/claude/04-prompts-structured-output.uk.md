# Промпти та структурований вихід

Вибір tool, відповідність JSON-схемі, бізнесова правильність і підтримка джерелами — окремі перевірки.

## Явні критерії

«Лише bugs/security/data-loss із відтворенням» корисніше за «будь консервативним». Визначте включені й виключені категорії, доказ і формат. Вимірюйте false positives та пропущені критичні issues.

## Few-shot приклади

Використовуйте оцінений набір релевантних і неоднозначних випадків із правильним handling. Універсального найкращого числа прикладів немає. Перевірте нові, не показані моделі cases.

## Схеми та strict-enforcement

Input_schema описує args, tool_choice обирає tool; самі вони не вмикають strict enforcement. Для підтримуваних конфігурацій використовуйте strict:true або JSON structured-output mode із прийнятною схемою. Обробляйте refusal, truncation та transport-error. Nullable/unclear поля дозволяють не вигадувати відсутні факти.

## Validation і retry

Перевіряйте types, суми, порядок дат, пов’язані поля й джерела. Передайте конкретну помилку з потрібним базисом для обмеженого виправлення. Retry не створює інформацію, якої немає в документі.

## Message Batches

Offline-обробка має окреме вікно та цінові умови; звіряйте custom_id, per-item statuses і retries. Не використовуйте Batches як гарантію негайного pre-merge feedback. Перевіряйте актуальні тарифи й processing-window: після24 годин невиконаний request може мати expired, а не success.

## Великі зміни

Перевірте файли окремо, потім зв’язки між ними: перейменовані виклики, shared types, routes й tests. Один довгий prompt може втрачати увагу; обсяг не замінює систематичну перевірку.

## Приклад відсутнього ID

Invoice-ID відсутній у джерелі. Required непорожнє поле створює тиск вигадати значення. Дозвольте null і перевірте known-missing fixtures; ще більше прикладів лише з ID не розв’язує відсутність даних.

## Три шари перевірки

Title=QA, salary_min5000, salary_max3000, remote=hybrid може мати правильні типи й хибний порядок сум. Інший запис із правильним порядком теж може вигадати зарплату. Check_extraction перевіряє структуру/правила; grounded_claims — підтримку фактів. Строгий формат не доводить жоден відсутній факт.
