## Відповіді з поясненнями

1. **D** — Exclusion є організаційною можливістю Business/Enterprise; конкретну підтримку surface перевіряють окремо.
2. **B** — Потрібно перевірити збіг шляху, підтримку клієнта й оновлення policy; exclusion не є універсальним sandbox.
3. **C** — Деякий непрямий контекст може зберігатися; filesystem і сторонні інтеграції мають власні межі доступу.
4. **D** — Відповідна policy фільтрує public-code matches; це не універсальна гарантія відсутності всіх ліцензійних питань.
5. **D** — Посилання на збіг і ліцензію дає докази для перевірки; остаточне рішення не випливає лише з генерації.
6. **D** — Repository custom instructions мають визначений шлях; це guidance, а не deterministic enforcement.
7. **C** — Path-specific instructions використовують glob у підтримуваному client/feature; перевірте область застосування.
8. **C** — Prompt-file версіонується разом із repo; сама його наявність не гарантує правильний набір тестів.
9. **B** — Agent mode виконує багатокрокову роботу в межах policy; конкретні approval-механізми залежать від клієнта.
10. **A** — Cloud/coding agent працює асинхронно й готує результат для рев’ю; перевірки й merge-policy залишаються потрібними.
11. **A** — Команди мають різні задачі; підтримку перевірте у своєму клієнті, а очікування тестів — за вимогою.
12. **B** — Repository retrieval розширює доступний контекст; це не гарантія включення кожного файлу в запит.
13. **C** — REST API підтримує керування seats за належних прав; audit і metrics не виконують цю операцію.
14. **B** — Audit-events допомагають атрибутувати адміністративні зміни; звичайні usage-метрики не замінюють журнал дій.
15. **A** — Це навчальна схема, не інваріант реалізації та безпеки всіх Copilot-surfaces.
16. **B** — Доступні джерела залежать від surface й policy; релевантні файли допомагають, але включення не гарантоване.
17. **A** — Предметні критерії й приклад задають потрібну поведінку; перевірте unshown edge cases незалежно.
18. **C** — Кількість shot стосується прикладів; одна демонстрація є one-shot, а не few-shot.
19. **A** — Oracle має походити зі специфікації: модель, що бачить хибний код, може повторити його припущення.
20. **A** — Приймаюча сторона відповідає за перевірку й release-рішення; походження від AI не скасовує стандартів якості.
21. **C** — CLI працює з локальним середовищем у межах дозволів; назва інструмента сама не створює безпечного sandbox.
22. **D** — LLM може вигадати API чи повторити небезпечний патерн; перевірте документацію, source і поведінку.
23. **B** — Guidance спрямовує review, але не гарантує виконання кожного пункту й не замінює required checks.
24. **A** — Використовуйте доступні для вашого плану й surface політики функцій; їхня підтримка змінюється.
25. **B** — MCP надає контракт викликів; сервісні credentials, scopes і approvals перевіряються окремо.
26. **A** — Окремий контекст може зменшити шум; потрібні явні inputs, передача findings і перевірка результатів.
27. **B** — Незалежний базис і очікування запобігають автоматичному закріпленню поточної хибної поведінки.
28. **D** — Модель може підтвердити власну галюцинацію; першоджерело й виконання дають незалежний доказ.
29. **C** — Це відповідальність за review й release, не універсальний юридичний висновок щодо ownership.
30. **D** — Перевіряйте реальний client/feature-контракт; зі схеми не випливає універсальний pipeline чи retention-гарантія.

## Оцінювання результату

Одна правильна відповідь — один навчальний бал. Результат є діагностичним і не визначає готовність до офіційного іспиту.
