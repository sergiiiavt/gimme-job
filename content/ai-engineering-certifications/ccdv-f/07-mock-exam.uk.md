## Відповіді з поясненнями

1. **B** — 429 можна повторити за бюджету й безпечного replay; безмежні повтори або обхід ліміту не є коректною стратегією.
2. **A** — Max_tokens позначає обрізаний вихід; не приймайте частковий JSON за валідний завершений запис.
3. **C** — Messages містить user/assistant turns; system задається окремим полем API, а не довільною роллю.
4. **B** — Message_delta перед message_stop містить завершальну інформацію; початковий usage може оновлюватися протягом stream.
5. **A** — Помилка запиту потребує виправлення; transient-retry не робить невалідний input коректним.
6. **A** — Streaming покращує видимий прогрес, але не гарантує швидшого повного обчислення або успіху.
7. **C** — Pause_turn потребує продовження за контрактом сервера; це не довільний клієнтський tool-error.
8. **C** — Платформи відрізняються IDs, auth і доступністю можливостей; перевірте конкретну комбінацію.
9. **D** — Зберігайте operation-ID та звіряйте невідомий результат до replay; повтор HTTP сам не гарантує єдиний бізнес-ефект.
10. **C** — Відмову обробляють явно; діагностика має бути санітизованою та не розкривати приватний payload.
11. **B** — Для exact-prefix match зміна timestamp руйнує збіг; в інших випадках також перевірте minimum length, TTL і scope.
12. **C** — Рішення спирається на заданий quality-bar і маршрутизацію складних випадків, а не універсальну перевагу tier.
13. **A** — Batches придатний для дозволеного offline-вікна; звіряйте IDs і повторюйте лише потрібні failures.
14. **B** — Змінні дані після breakpoint не змінюють стабільний prefix; TTL, scope і minimum length також важливі.
15. **A** — Count оцінює input-токени; резервуйте output і рахуйте валютну вартість за відповідними тарифами окремо.
16. **D** — Routing дозволяє дати refund-tool лише потрібному шляху, але backend усе одно перевіряє авторизацію.
17. **B** — Orchestrator може декомпозувати динамічно; потрібні явні inputs, бюджети та передавання результатів.
18. **A** — Кожен result має matching tool_use_id; не губіть множинні виклики й повідомляйте про errors явно.
19. **D** — Відкритий вибір дій обґрунтовує agent-loop; для відомих кроків workflow зазвичай простіший.
20. **D** — Managed runtime бере частину harness-роботи; власні data, approval та evaluation-вимоги нікуди не зникають.
21. **C** — Auto залишає вибір між текстом і tool; any вимагає якийсь tool, а none забороняє їх.
22. **A** — Stdio зручний для локального процесу; stdout резервують для протоколу, diagnostics — stderr.
23. **A** — Порожній успіх означає відсутність записів; збій має окрему ознаку для recovery та чесного handoff.
24. **B** — Теги допомагають структурі, але не гарантують ізоляції; tool-authorization та перевірки залишаються окремими.
25. **C** — Схема повинна дозволяти відсутність факту; retry чи більша модель не створять джерельного значення.
26. **D** — Типи й структура не замінюють бізнес-правила; окремо перевіряйте джерельну підтримку.
27. **B** — Недовірений документ не надає повноважень. Дозволені адресати й approval перевіряє межа дії.
28. **D** — Потрібні авторизація, ліміти та gate до незворотного ефекту; журнал після події не запобігає їй.
29. **D** — Noninteractive mode усуває очікування користувацького вводу; інші причини досліджують окремо.
30. **B** — Агрегат приховує погіршення важливої групи; сегментні очікування й regression-set потрібні до release.
