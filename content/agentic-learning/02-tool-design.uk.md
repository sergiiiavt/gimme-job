# Проєктування інструментів для агентів

Інструмент — єдиний спосіб, у який агент може щось зробити у світі, а опис інструмента — єдине, що модель знає про цю дію. Модель читає назву, опис і схему аргументів і лише з них вирішує, коли викликати інструмент і з якими параметрами. Тому проєктування інструментів — це наполовину дизайн інтерфейсу, а наполовину написання промпта.

У цьому розділі: як описувати інструменти, обмежувати їхні аргументи, формувати результати й помилки, працювати з побічними ефектами й повторами та скільки інструментів давати агенту. Як тестувати описи інструментів і окремі виклики, розказано в розділі [Оцінювання агентів і викликів інструментів](/learn/llm?topic=agent-testing&section=testing-tool-definitions-and-calls).

**Передумови:** [Як працює AI-агент](/learn/agentic?topic=how-agents-work).

## Що таке опис інструмента

API провайдерів і Model Context Protocol описують інструмент однаково: назва, опис і JSON Schema для аргументів. Ось реальний приклад, інструмент пошуку вакансій із MCP-сервера GimmeJob:

```json
{
  "name": "search_jobs",
  "description": "Search GimmeJob vacancies through the canonical RAG pipeline, with optional source, status, and remote filters.",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["query"],
    "properties": {
      "query": { "type": "string", "minLength": 1, "maxLength": 500, "description": "Natural-language vacancy search." },
      "limit": { "type": "integer", "minimum": 1, "maximum": 25, "default": 10 },
      "remote": { "type": "boolean" },
      "source": { "type": "string", "minLength": 1, "maxLength": 100 },
      "status": { "type": "string", "minLength": 1, "maxLength": 100 }
    }
  }
}
```

Модель бачить цей текст і більше нічого: ні коду за ним, ні бази даних, ні домовленостей інших команд. Кожну прогалину в описі вона заповнює здогадкою.

## Назви й описи — це промпти

Пишіть опис інструмента так, ніби вводите в курс справи нового колегу: що інструмент робить, коли його використовувати, коли ні і що означають аргументи, разом із форматами й одиницями.

| Слабко | Краще | Чому |
|---|---|---|
| `search` | `search_jobs` | Називає ресурс і не конфліктує з `search_docs` з іншого сервера |
| `user` | `user_id` | Видно, що потрібен ідентифікатор, а не ім'я чи e-mail |
| "Gets data." | "Returns open vacancies matching a natural-language query. Use it before analyze_vacancy to find a job_id." | Каже, що повернеться і як інструмент поєднується з іншими |
| `date` | `posted_after` з поясненням "ISO 8601 date, e.g. 2026-11-01" | Прибирає здогадки щодо формату й значення |
| `status` (довільний текст) | `status` з `enum` допустимих значень | Модель не зможе вигадати значення, якого не існує |

Коли під'єднано кілька серверів, назви інструментів конкурують між собою. Префікс за сервісом чи ресурсом (`jobs_search`, `jobs_analyze`) робить вибір однозначним. Над описами варто працювати так само, як над будь-яким промптом: невелика зміна формулювання може помітно змінити, як часто модель обирає правильний інструмент.

Опис GimmeJob вище — непоганий старт, який ще можна покращити. Він каже, що інструмент робить, але не каже, коли саме його обирати, а `status` і `source` — це довільні рядки, тож модель мусить вгадувати їхні значення. `enum` для кожного з них і одне речення про зв'язок з `analyze_vacancy` прибрали б обидві здогадки.

## Обмежуйте аргументи схемою

Схема — перша лінія захисту від поганих викликів. Використовуйте ключові слова, які перетворюють здогадку на помилку:

- `required` для аргументів, без яких інструмент не працює;
- `enum` для закритих наборів значень;
- `minimum`, `maximum`, `minLength`, `maxLength` і `pattern` для діапазонів і форматів;
- `additionalProperties: false`, щоб вигаданий аргумент відхилявся, а не тихо ігнорувався.

Деякі API провайдерів мають строгий режим, у якому вивід моделі гарантовано відповідає схемі. Це допомагає, але на сервері все одно перевіряйте: клієнт може не вмикати строгий режим, якесь ключове слово схеми може не підтримуватися, а виклик, що відповідає схемі, усе одно може містити значення, хибне для цього запиту. Про проблеми валідації повідомляйте так, щоб модель могла їх виправити:

```python
SEARCH_JOBS_SCHEMA = {
    "required": ["query"],
    "properties": {
        "query": {"type": "string", "maxLength": 500},
        "limit": {"type": "integer", "minimum": 1, "maximum": 25},
        "remote": {"type": "boolean"},
    },
}

PY_TYPES = {"string": str, "integer": int, "boolean": bool}

def validate_arguments(schema, arguments):
    errors = []
    for name in schema["required"]:
        if name not in arguments:
            errors.append(f"'{name}' is required.")
    for name, value in arguments.items():
        rule = schema["properties"].get(name)
        if rule is None:
            allowed = ", ".join(schema["properties"])
            errors.append(f"Unknown argument '{name}'. Allowed: {allowed}.")
            continue
        expected = PY_TYPES[rule["type"]]
        if isinstance(value, bool) and expected is int:
            errors.append(f"'{name}' must be an integer, got a boolean.")
        elif not isinstance(value, expected):
            errors.append(f"'{name}' must be a {rule['type']}.")
        elif expected is int and not rule["minimum"] <= value <= rule["maximum"]:
            errors.append(f"'{name}' must be between {rule['minimum']} and {rule['maximum']}, got {value}.")
        elif expected is str and len(value) > rule.get("maxLength", 10_000):
            errors.append(f"'{name}' is longer than {rule['maxLength']} characters.")
    return errors

for call in [
    {"query": "Senior QA Python", "limit": 10},
    {"limit": 100, "city": "Kyiv"},
    {"query": "Playwright", "remote": "yes"},
]:
    problems = validate_arguments(SEARCH_JOBS_SCHEMA, call)
    print("OK" if not problems else "isError: " + " ".join(problems))
```

На продакшен-сервері замість такої ручної перевірки варто взяти бібліотеку для схем (сервер GimmeJob використовує Zod зі строгими об'єктами), але принцип той самий: відхиляти невідомі аргументи, перевіряти діапазони й точно казати, що змінити.

## Повертайте те, що потрібно моделі

Результат інструмента потрапляє прямо в контекст моделі й конкурує там із самою задачею за увагу. Повертайте найменший результат, з яким модель може зробити наступний крок.

- **Змістовні поля замість сирих записів.** Назва, компанія й статус допомагають ухвалити наступне рішення, а внутрішні прапорці й службові колонки — ні.
- **Ідентифікатори, які модель здатна перенести.** Короткі читабельні id модель копіює правильно частіше, ніж довгі непрозорі.
- **Обмеження й пагінація великих результатів.** Поверніть першу сторінку із загальною кількістю й курсором і прямо в результаті скажіть, як отримати більше.
- **Стислий і детальний режими**, коли одному викликачу потрібен список, а іншому повний текст.
- **Структуровані дані разом із текстом.** Результат MCP може містити `structuredContent` для програм і текстовий блок для моделі. Специфікація просить сервери, які повертають структурований вміст, додавати той самий JSON як текст.

| Поле результату | Залишати? | Причина |
|---|---|---|
| `id`, `title`, `company`, `status` | Так | Потрібні, щоб обрати й викликати наступний інструмент |
| `description` | Скорочено | Корисне, але довге; інструмент GimmeJob обрізає його до 4 000 символів |
| `retrievalScore` | За потреби | Допомагає зважити результати; для більшості задач — шум |
| Внутрішні мітки часу рядків, сирі JSON-блоки | Ні | Токени без інформації для задачі |

## Помилки, після яких модель може виправитися

Повідомлення про помилку — це інструкція для наступного кроку. Порівняйте:

| Некорисно | Корисно |
|---|---|
| `Error 400` | `'limit' must be between 1 and 25, got 100.` |
| `Not found` | `No vacancy with id 'job_9'. Use search_jobs to find current ids.` |
| Стек викликів | `The vacancy source did not respond in 10 s. Try again later or search without 'source'.` |

MCP розрізняє два види збоїв. **Помилка протоколу** — це JSON-RPC-помилка для запиту, який сервер узагалі не може обробити, наприклад виклик невідомого інструмента. **Помилка виконання інструмента** — це звичайний результат з `isError: true` і повідомленням для збоїв, з якими модель може щось зробити, зокрема для хибних значень аргументів. Ревізія специфікації 2025-11-25 прямо каже, що помилки валідації вхідних даних належать до другої групи, бо лише результат інструмента доходить до моделі й дає їй змогу виправити виклик. Сервер GimmeJob так і робить: невідома назва інструмента повертає JSON-RPC-помилку `-32602`, а хибні аргументи — результат з `isError`, де перелічено, що не так.

## Читання, запис і побічні ефекти

Позичте словник HTTP. **Безпечна** операція лише читає. **Ідемпотентну** операцію можна повторити з тим самим ефектом, що й від одного запуску. Класифікуйте кожен інструмент, бо від цього залежить, як його повторювати і чи має людина його підтверджувати.

| Тип | Приклад | Повтор | Підтвердження |
|---|---|---|---|
| Читання | `search_jobs`, `lookup_order` | Вільно, з паузами між спробами | Не потрібне |
| Ідемпотентний запис | «встановити вакансії X статус APPLIED» | Так, ефект той самий | Залежно від наслідків |
| Неідемпотентний запис | «надіслати лист», «створити тікет» | Лише з ключем ідемпотентності | Зазвичай потрібне |
| Руйнівна дія | «видалити гілку», «повернути платіж» | Без автоматичних повторів | Завжди |

Записи безпечнішими роблять два прийоми. **Ключ ідемпотентності**, який обирає викликач, дає серверу змогу впізнати повторний запит і застосувати його один раз. **Режим попереднього перегляду (dry-run)** показує, що станеться, нічого не роблячи, тож справжній виклик може затвердити людина або перевірка в коді.

Будьте уважні з інструментами, які лише здаються читанням. У GimmeJob `analyze_vacancy` повертає аналіз, але водночас зберігає його в базі й може викликати платний API моделі. Отже, це запис із вартістю, і саме так його треба розглядати, коли вирішуєте про повтори й ліміти.

MCP дозволяє серверу описати поведінку інструмента підказками, а попередні ревізії визначали анотації на зразок read-only і destructive. Специфікація чітко каже, що клієнти мають вважати їх недовіреними, якщо сам сервер не є довіреним. Дозволи й підтвердження визначайте в host, а не на підставі опису самого інструмента. Як тестувати підтвердження й дозволи, розказано в розділі [Безпека: дозволи та підтвердження](/learn/llm?topic=agent-testing&section=safety-permissions-and-approvals).

## Тайм-аути, повтори й ліміти

Інструменти звертаються до мереж, баз даних та інших моделей, тож вони і падають, і зависають. Поведінку визначайте в коді, для кожного інструмента окремо:

- **Тайм-аут на кожен виклик.** Інструмент, який ніколи не повертається, блокує весь цикл.
- **Повторюйте лише те, що безпечно повторити.** Читання та ідемпотентні записи можна повторювати з експоненційною затримкою і випадковим розкидом (jitter); інші записи потребують ключа ідемпотентності або взагалі не повторюються.
- **Уникайте багаторівневих повторів.** Якщо HTTP-клієнт, інструмент і цикл агента повторюють по три рази, один збій перетворюється на 27 викликів. Оберіть один рівень.
- **Ліміти, які модель не може обійти.** Максимальний розмір сторінки, максимальна кількість викликів на запуск і максимальні витрати належать застосунку, а не промпту.
- **Повідомляйте про повтори в результаті.** «Вдалося після 2 повторів» підказує моделі й вам, що із залежністю щось не так.

## Скільки інструментів давати

Більше інструментів не робить агента здібнішим. Кожен інструмент додає тексту в кожен запит і ще один варіант для вибору, а схожі інструменти погіршують вибір. Створюйте кілька інструментів під цілі задачі замість того, щоб віддзеркалювати кожен ендпоінт API.

| Інструменти за ендпоінтами | Інструмент під задачу |
|---|---|
| `list_jobs`, `get_job`, `get_company`, `get_salary` | `search_jobs`, що одразу повертає назву, компанію, зарплату й статус |
| `list_test_runs`, `get_run`, `get_failures`, `get_logs` | `summarize_failed_run(run_id)`, що повертає збої з потрібними рядками логів |

Корисна перевірка — дати агенту реалістичні задачі й прочитати трасування. Інструменти, якими він не користується, інструменти, які він плутає, і довгі ланцюжки викликів, що могли б бути одним викликом, показують, де набір інструментів треба змінити.

## Приклад: MCP-інструменти GimmeJob

Сервер GimmeJob надає чотири інструменти. Разом вони покривають вузьку задачу — знайти вакансії й підготуватися до них, — і це хороша форма для набору інструментів агента.

| Інструмент | Призначення | Ліміти | Побічні ефекти |
|---|---|---|---|
| `search_jobs` | Семантичний пошук вакансій із фільтрами | `limit` від 1 до 25, запит до 500 символів | Немає |
| `get_interview_questions` | Пошук у публічному каталозі питань для співбесід | `limit` від 1 до 25 | Немає |
| `get_learning_progress` | Читання приватного прогресу користувача й відповідних навчальних матеріалів | `limit` від 1 до 15 | Немає, але повертає приватні дані |
| `analyze_vacancy` | Аналіз однієї збереженої вакансії й поради з підготовки | Один `job_id` на виклик | Зберігає аналіз; може викликати платну модель |

Що зроблено добре: кожна схема має `additionalProperties: false` і явні діапазони, сервер ще раз перевіряє виклик строгими схемами, проблеми валідації повертаються як результати з `isError`, а результати містять і JSON-текст, і `structuredContent`. Покращувати варто переважно описи: закриті набори значень у вигляді `enum` і в кожному описі речення про те, коли використовувати інструмент і який інструмент іде наступним. Наступний розділ дивиться на той самий сервер з боку протоколу: [Model Context Protocol](/learn/agentic?topic=model-context-protocol).

## Типові помилки

- **Віддзеркалювати API по інструменту на ендпоінт.** Агент витрачає кроки на зшивання даних, які міг би повернути один інструмент під задачу.
- **Розмиті назви й описи.** `search`, `data` чи `run` змушують модель вгадувати, і здогадка змінюється від запуску до запуску.
- **Довільні рядки для закритих наборів.** Без `enum` модель рано чи пізно надішле значення, якого не існує.
- **Покладатися лише на схему.** Перевіряйте кожен виклик на сервері й повертайте помилки з підказками як результати інструмента.
- **Величезні результати.** Повні записи, логи чи сторінки рядків витісняють задачу; обмежуйте, обрізайте й розбивайте на сторінки.
- **Сліпо повторювати записи.** Повторений «надіслати лист» надішле два листи, якщо цьому не завадить ключ ідемпотентності.
- **Вважати анотації дозволами.** Те, що інструмент називає себе read-only, — лише підказка; що дозволено, вирішує host.

## Підсумок

Модель знає інструмент лише за назвою, описом і схемою, тож пишіть їх так само уважно, як промпт, і так само точно, як інтерфейс. Обмежуйте аргументи через `required`, `enum`, діапазони й `additionalProperties: false` і ще раз перевіряйте на сервері. Повертайте невеликі змістовні результати й повідомлення про помилки, які кажуть, що робити далі; у MCP хибні аргументи — це помилки виконання інструмента, а не помилки протоколу. Класифікуйте кожен інструмент як читання, ідемпотентний запис, неідемпотентний запис або руйнівну дію, і нехай саме це визначає повтори й підтвердження. Кілька інструментів під задачі кращі за багато інструментів під ендпоінти.
