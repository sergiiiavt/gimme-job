# AI coding agents у роботі QA

Coding agent — це цикл агента, застосований до репозиторію коду. Інструменти на кшталт Claude Code, OpenAI Codex, coding agent у GitHub Copilot і Cursor читають файли, шукають у коді, редагують його й запускають команди, а потім показують diff або відкривають pull request. QA-інженерам вони можуть писати й лагодити тести, відтворювати баги, пояснювати збої CI та переглядати зміни — і так само можуть створювати тести, які виглядають правильними, але нічого не перевіряють.

У цьому розділі: що таке coding agent, як передати йому правила проєкту, які задачі QA йому підходять, як перевіряти його роботу, як цей сайт будується з агентами і що кажуть дослідження про продуктивність. Оцінювання агентів загалом описано в розділі [Оцінювання агентів і викликів інструментів](/learn/llm?topic=agent-testing).

**Передумови:** [Як працює AI-агент](/learn/agentic?topic=how-agents-work), [Підтвердження людиною й межі дій](/learn/agentic?topic=human-approval).

## Що таке coding agent

Цикл той самий, що й у будь-якого агента; інструменти — це репозиторій і командний рядок:

```diagram
Задача від вас («зроби тест оформлення замовлення стабільним»)
        ↓
Агент читає файли з інструкціями, шукає й читає код
        ↓
Агент редагує файли й запускає команди (тести, лінтери, збирання)
        ↓
Агент читає вивід і вирішує, що робити далі        (і так по колу)
        ↓
Результат: diff, коміт або pull request на перегляд
```

Coding agents відрізняються переважно тим, де вони працюють і скільки можуть зробити самостійно:

| Середовище | Типова форма | На що зважати |
|---|---|---|
| Локально, інтерактивно | CLI чи IDE-агент у вашій робочій копії | Режим дозволів: які команди й правки потребують вашого підтвердження |
| У хмарі, асинхронно | Агент працює в пісочниці й відкриває pull request | До чого має доступ пісочниця: секрети, мережі, інші репозиторії |
| Запуск із CI | Агент виправляє непройдені перевірки чи відповідає на коментарі рев'ю | Хто переглядає його коміти перед злиттям |

Модель дозволів — це те саме підтвердження з [попереднього розділу](/learn/agentic?topic=human-approval), застосоване до вашої машини: читати — дешево, правки мають бути придатні до перегляду, а запуск команд, встановлення пакетів, push і видалення заслуговують на явний контроль.

## Передайте агенту правила проєкту

Агент знає мову та поширені фреймворки, але не знає домовленостей, інваріантів і визначення «готово» саме вашого проєкту. Запишіть їх туди, де агенти їх читають.

**AGENTS.md** — звичайний Markdown-файл у корені репозиторію, який його автори описують як README для агентів: як збирати, як тестувати, чого не чіпати. Його читає багато coding agents; вкладені файли можуть описувати окремі частини монорепозиторію, діє файл, найближчий до коду, що редагується, а явна інструкція в чаті має пріоритет над ним. Claude Code читає власні файли `CLAUDE.md` і використовує `AGENTS.md`, якщо `CLAUDE.md` немає. І те, й інше — контекст, а не механізм примусу: агента просять дотримуватися інструкцій, а реально щось забезпечують хуки, CI і дозволи.

Корисний файл інструкцій для тестового проєкту — короткий і конкретний:

```markdown
# Agent instructions

## Commands
- Install: `npm ci`
- Fast checks while working: `npm run lint && npm run test:unit`
- Before finishing: `npm run verify` (all must pass)

## Testing rules
- Test behaviour through public functions, API responses or rendered output, not source text.
- Never delete, skip or weaken an existing assertion to make a test pass. If a test is wrong, say why.
- A bug fix starts with a test that fails before the fix and passes after it.
- No real network calls or production credentials in tests; use the fixtures in `tests/fixtures`.

## Scope
- Change only the files the task needs. Ask before touching CI configuration or dependencies.
```

Тримайте одне джерело істини. Цей репозиторій зберігає свої правила в `AGENTS.md`, а його `CLAUDE.md` лише посилається туди, тож вони ніколи не розходяться.

## Задачі QA, що добре підходять агенту

| Задача | Чому підходить | Що ви перевіряєте |
|---|---|---|
| Відтворити баг як тест, що падає | Чітка мета, перевірюваний результат | Тест падає саме з описаної причини, а не через помилку підготовки |
| Написати тести до добре специфікованої функції | Специфікація слугує оракулом | Кейси взято зі специфікації, а не з читання реалізації |
| Стабілізувати нестабільний тест | Агенти терплячі до логів і перезапусків | Виправлення прибирає причину (очікування, дані, порядок), а не симптом (повтор, довший sleep) |
| Перенести тести на новий API чи версію фреймворку | Повторювано, механічно, перевірювано | Кількість змістовних перевірок до і після однакова |
| Пояснити збій у CI | Довгі логи, голка в копиці сіна | Пояснення вказує на конкретний рядок, який можна перевірити |
| Згенерувати тестові дані чи фікстури | Нудно писати вручну | Граничні випадки є; реальних персональних даних немає |
| Переглянути pull request на відсутні тести | Систематичне читання | Пропозиції називають конкретні неперевірені гілки коду |

Спільне в усіх — результат, який можна перевірити, не довіряючи агенту: тест, що падає, а потім проходить, diff, який можна прочитати, рядок у лозі, який можна знайти.

## Задачі, які варто лишити собі

Деякі рішення має ухвалювати людина, навіть якщо агент здатен дати відповідь:

- **Визначати, яка поведінка правильна.** Коли специфікація мовчить, агент виведе очікуваний результат із поточного коду, і сьогоднішній баг стане завтрашньою перевіркою.
- **Робити червоне збирання зеленим будь-якою ціною.** Агенти, яких просять «зробити так, щоб тести пройшли», іноді видаляють перевірки, послаблюють очікувані значення чи пропускають тести. Просіть знайти причину.
- **Усе, що має доступ до продакшну чи реальних секретів.** Давайте агентам пісочниці й тестові облікові дані.
- **Великі рефакторинги без страховки.** Без тестів, що ловлять регресії, великий рефакторинг від агента — це велика неперевірена зміна.

## Як перевіряти роботу агента

Ставтеся до результату агента як до pull request від швидкого, впевненого колеги, який ніколи не бачив вашого продукту. Самі запускайте тести, читайте весь diff і шукайте типові способи, у які зміни тестів псуються:

| Тривожний знак | Що це зазвичай означає |
|---|---|
| Перевірки видалено або їх стало менше | Тест тепер перевіряє менше |
| Очікувані значення розширено (`== 201` стало `in (200, 201)`) | Справжню зміну поведінки приховано |
| Тести позначено як пропущені чи очікувано непрохідні | Проблему відкладено, а не розв'язано |
| Перевірки лише на істинність (`assert items`) | Проходить майже будь-який результат |
| Моки самого коду, що тестується | Тест перевіряє мок |
| До нестабільного тесту додано sleep чи повтори | Гонка нікуди не зникла |

Частину з цього легко позначати автоматично. Функція нижче читає diff тестового файлу й повідомляє про підозрілі зміни; справжня версія запускалася б у CI на кожен pull request, що змінює тести.

```python
import re

DIFF = """\
-    assert response.status == 201
+    assert response.status in (200, 201)
-    assert order["total"] == 105.40
+    @mark.skip(reason="flaky on CI")
+    def test_refund_rounding():
-    assert len(items) == 3
+    assert items
"""

def review_test_diff(diff):
    removed = [line[1:].strip() for line in diff.splitlines() if line.startswith("-")]
    added = [line[1:].strip() for line in diff.splitlines() if line.startswith("+")]
    findings = []
    removed_asserts = sum(1 for line in removed if line.startswith("assert "))
    added_asserts = sum(1 for line in added if line.startswith("assert "))
    if added_asserts < removed_asserts:
        findings.append(f"{removed_asserts - added_asserts} assertion(s) removed")
    for line in added:
        if re.search(r"skip|xfail", line):
            findings.append(f"test disabled: {line}")
        if re.fullmatch(r"assert \w+", line):
            findings.append(f"only checks truthiness: {line}")
        if line.startswith("assert ") and " in (" in line:
            findings.append(f"expected value widened: {line}")
    return findings

for finding in review_test_diff(DIFF):
    print("-", finding)
```

Автоматичні позначки не замінюють читання diff; вони гарантують, що найпоширеніші способи послабити тест не пройдуть непоміченими.

## Приклад: як цей сайт будується з агентами

Багато чого в GimmeJob, зокрема цей навчальний розділ, написано за допомогою coding agents. Робочим це робить не сам агент, а правила й перевірки навколо нього:

- **Один файл інструкцій.** `AGENTS.md` визначає правила обсягу змін, інваріанти продукту (наприклад, що публічний навчальний контент живе в Git і що кожен навчальний розділ один раз реєструється для пошуку), як писати тести і як випускати зміни. `CLAUDE.md` лише посилається на нього.
- **Одна команда, що вирішує, чи «готово».** `npm run verify` запускає лінтинг, перевірку типів, валідатори контенту, збирання, набір тестів і перевірку артефакту розгортання. Просто зелене збирання не рахується.
- **Невеликі pull requests із написаною причиною.** Кожна зміна проходить draft pull request, CI і статичний аналіз перед злиттям, а після розгортання перевіряється продакшн.
- **Перевірки, що ловлять і агента.** Виправляючи ваду верстки на телефонах, агент виявив, що CSS-клас, призначений саме для цього випадку, ніколи не був визначений; виправлення прийшло разом із невеликим тестом («кожен CSS-клас, який використовує компонент, має існувати»), щоб це не повторилося. Статичний аналіз також позначав зміну агента як надто складну, і перед злиттям її довелося розбити.

Цей підхід узагальнюється: що більше робить агент, то більше проєкту потрібні явні правила, одна довірена команда перевірки та зміни невеликими частинами, які можна переглянути.

## Що кажуть дослідження про продуктивність

Твердження про продуктивність агентів коливаються від величезного приросту до від'ємного, а ретельні дослідження змушують бути скромнішими. У рандомізованому дослідженні METR досвідчені розробники open source працювали над власними репозиторіями з інструментами початку 2025 року, і з дозволеним AI задачі тривали приблизно на 19% довше, хоча самі розробники вважали, що AI прискорив їх приблизно на 20%. Продовження METR у лютому 2026 року з новішими агентними інструментами, більшою кількістю розробників і понад 800 задачами оцінило скорочення часу на 18% для учасників першого дослідження і на 4% для нових — із невизначеністю, достатньо широкою, щоб не виключати відсутності ефекту. Автори назвали ці докази дуже слабкими й змінили дизайн дослідження, зокрема тому, що розробники дедалі частіше відмовлялися працювати без AI.

Для QA з цього випливають два уроки. Перший: враження — не доказ; вимірюйте на власній роботі, наприклад порівнюючи дефекти, що проскочили, час на рев'ю й переробки для змін, написаних агентом і людиною. Другий: бенчмарки на кшталт SWE-bench, що оцінюють агента за тим, чи проходять після його зміни тести самого репозиторію, такі хороші, як ці тести; агент, що обходить слабкі тести, отримує високий бал і випускає баги.

## Типові помилки

- **Немає файлу інструкцій.** Агент вгадує домовленості й команди, щоразу по-різному.
- **Продубльовані інструкції.** `AGENTS.md`, `CLAUDE.md` і сторінка у вікі, що суперечать одна одній, гірші за один файл.
- **«Зроби, щоб тести пройшли».** Просіть знайти причину збою, інакше чекайте послаблених перевірок.
- **Дозволяти агенту визначати правильну поведінку.** Очікувані результати беруться зі специфікації або від вас, а не з поточного коду.
- **Переглядати опис замість diff.** Опис зміни від агента — це не сама зміна.
- **Широкі права за замовчуванням.** Облікові дані продакшну й необмежений доступ до командного рядка перетворюють дрібні помилки на інциденти.
- **Вважати прискорення очевидним.** Вимірюйте результати; розробники стабільно переоцінюють виграш.

## Підсумок

Coding agent — це цикл агента, що працює з репозиторієм через інструменти для файлів, пошуку й командного рядка, тож його дозволи — це підтвердження дій на вашій машині. Запишіть правила проєкту один раз, у файл інструкцій на кшталт `AGENTS.md`, а те, що справді важливо, забезпечуйте через CI, а не лише інструкціями. Давайте агентам задачі з перевірюваним результатом, рішення про правильну поведінку лишайте собі й перевіряйте кожну зміну тестів на видалені перевірки, розширені очікування, пропуски й перевірки лише на істинність. Сприймайте твердження про продуктивність, зокрема власні враження, як гіпотези, які треба виміряти.
