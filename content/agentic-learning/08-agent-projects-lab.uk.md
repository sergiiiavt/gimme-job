# Проєкти й лабораторія MCP

Найшвидше зрозуміти агентів можна, якщо зібрати невеликого агента, що працює від початку до кінця: вузька задача, кілька інструментів за справжнім протоколом, цикл з обмеженнями, межа, яку контролює людина, і перевірки, що показують, чи зробив він правильно. Одна така система навчить більше, ніж великий асистент, який береться за все і якого неможливо протестувати.

У цьому розділі: як обрати вузький проєкт, визначення «готово» для агентних проєктів і практична лабораторна: MCP-сервер, клієнт і агент для розбору збоїв, побудовані за ревізією Model Context Protocol 2026-07-28. Систематичне тестування того, що ви збудуєте, описано в розділі [Тестування серверів MCP](/learn/llm?topic=agent-testing&section=testing-mcp-servers).

**Передумови:** [Model Context Protocol](/learn/agentic?topic=model-context-protocol), [Підтвердження людиною й межі дій](/learn/agentic?topic=human-approval), [Оцінювання та спостережуваність агентів](/learn/agentic?topic=agent-observability).

## Оберіть вузький проєкт

Хороший перший агентний проєкт має одну задачу, від двох до чотирьох інструментів, результат, який можна перевірити, не довіряючи агенту, і принаймні одну дію, яку має підтвердити людина. У роботі QA таких задач багато:

| Проєкт | Інструменти | Межа | Як зрозуміти, що спрацювало |
|---|---|---|---|
| Розбір нестабільних тестів (лабораторна нижче) | Список збоїв, історія тесту, пропозиція карантину | Карантин лише як пропозиція | Нестабільні тести запропоновано, справжні регресії позначено, нічого не застосовано |
| Пояснення збою CI за логом | Читання логу джоби, читання diff | Лише читання | Пояснення вказує на рядок, який можна перевірити |
| Перевірка розходжень з контрактом API | Читання OpenAPI, виклики тестового середовища | Чернетки тікетів потребують підтвердження | Усі навмисно внесені зміни контракту виявлено |
| Тест-кейси з вимоги | Читання вимоги, запис чернетки у файл | Чернетку схвалює рецензент | Для кожного критерію приймання є кейс |
| Підбір вакансій | Пошук вакансій, аналіз однієї вакансії | Лише читання, жодних надісланих заявок | Збіги узгоджуються з розміченим набором |
| Чекліст регресії до релізу | Читання змерджених pull requests | Лише читання | Чекліст покриває кожну змінену область |

Уникайте проєктів, успіх яких не можна перевірити («зробити наш QA розумнішим»), і проєктів, перша версія яких потребує доступу до продакшну чи грошей.

## Визначення «готово» для агентного проєкту

Перш ніж назвати агентний проєкт завершеним, перевірте, що в нього є:

- **Обсяг в одному реченні**, де сказано, що агент робить і чого він ніколи не повинен робити.
- **Інструменти з назвами, описами й строгими схемами**, класифіковані як читання, запис чи зовнішня комунікація.
- **Дозволи й підтвердження в коді**: облікові дані агента і які дії потребують людини.
- **Обмеження**: бюджет кроків, ліміт часу й ліміт вартості, які забезпечує цикл.
- **Трасування** з кожним кроком і причиною зупинки.
- **Набір для оцінювання**: кілька десятків задач із перевірками результату й траєкторії, які запускаються багато разів.
- **README**, що пояснює, як запустити проєкт і що він демонструє.

## Лабораторна MCP

Лабораторна в [examples/agentic-mcp-lab](https://github.com/sergiiiavt/gimme-job/tree/main/examples/agentic-mcp-lab) — повна невелика система на чистому Python без залежностей і без API-ключа. Замість моделі працює політика зі сценарієм, тож кожен запуск відтворюваний.

```diagram
agent.py   цикл: політика пропонує виклик інструмента → клієнт виконує → результат повертається; бюджет кроків; трасування
   ↓
client.py  запускає server.py як підпроцес, спершу питає server/discover, одне JSON-RPC-повідомлення на рядок
   ↓  stdin / stdout (лише повідомлення протоколу)        stderr (логи)
server.py  MCP-сервер: server/discover, tools/list, tools/call; перевіряє версію протоколу й можливості клієнта в кожному запиті
```

| Файл | Що робить |
|---|---|
| `server.py` | Надає `ci_list_failures` і `ci_test_history` (читання) та `ci_propose_quarantine`, який лише створює пропозицію зі статусом `PENDING_APPROVAL` |
| `client.py` | Запускає сервер, надсилає запити з `_meta`, кидає виняток на помилки протоколу й зупиняє сервер, закриваючи його stdin |
| `agent.py` | Розбирає один запуск CI: отримує збої, читає історію кожного тесту, пропонує карантин для нестабільних тестів і позначає ймовірні регресії |
| `test_lab.py` | Перевіряє discovery, обробку версій, схеми інструментів, різницю між помилками інструмента й протоколу, правила stdio і рішення агента |

Запустіть із кореня репозиторію з Python 3.12 або новішим:

```bash
python examples/agentic-mcp-lab/agent.py
python -m unittest discover -s examples/agentic-mcp-lab -v
```

Вивід агента показує трасування, одну пропозицію, що чекає на людину, і один тест, з яким треба розібратися:

```text
step 1: ci_list_failures {"run_id": "run-512"} error=False
step 2: ci_test_history {"test": "checkout::test_apply_coupon"} error=False
step 3: ci_test_history {"test": "api::test_refund_rounding"} error=False
step 4: ci_propose_quarantine {"test": "checkout::test_apply_coupon", ...} error=False
stop: done
needs approval: proposal-1 checkout::test_apply_coupon - Failed 3 of 10 recent runs on unchanged code.
investigate (likely regression, not flaky): api::test_refund_rounding
```

## Що лабораторна показує про протокол

Лабораторна відповідає ревізії 2026-07-28, яка в кількох місцях відрізняється від старіших туторіалів, і там легко помилитися:

- **Discovery замість початкового узгодження.** `initialize` немає. Клієнт спершу питає сервер через `server/discover`, а той повертає `supportedVersions`, `capabilities`, а в `_meta` — свою назву й версію.
- **Версія й можливості в кожному запиті.** Кожен запит містить `io.modelcontextprotocol/protocolVersion` і `io.modelcontextprotocol/clientCapabilities` у `params._meta`. На версію, яку сервер не підтримує, він відповідає помилкою `-32022` з `supported` і `requested` у даних помилки.
- **Кожен результат має `resultType`.** Результати списків і discovery також містять `ttlMs` і `cacheScope`, які кажуть клієнту, як довго їх можна кешувати.
- **Правила stdio.** Одне повідомлення на рядок, у stdout лише повідомлення протоколу, логи в stderr, і сервер завершується, коли закривається його stdin.

Невелика перевірка ловить найпоширеніші помилки у відповідях сервера. Тут вона порівнює відповідь, написану для старішої ревізії, з відповіддю за 2026-07-28:

```python
REQUIRED = {
    "server/discover": ["resultType", "supportedVersions", "capabilities", "ttlMs", "cacheScope"],
    "tools/list": ["resultType", "tools", "ttlMs", "cacheScope"],
    "tools/call": ["resultType", "content"],
}
SERVER_INFO_KEY = "io.modelcontextprotocol/serverInfo"

def check_response(method, response):
    problems = []
    if "error" in response:
        error = response["error"]
        if error.get("code") == -32022 and set(error.get("data", {})) != {"supported", "requested"}:
            problems.append("version error must report supported and requested versions")
        return problems
    body = response.get("result", {})
    for field in REQUIRED[method]:
        if field not in body:
            problems.append(f"{method}: missing {field}")
    for tool in body.get("tools", []):
        if tool.get("inputSchema", {}).get("type") != "object":
            problems.append(f"tool {tool.get('name')}: inputSchema.type must be object")
    if SERVER_INFO_KEY not in body.get("_meta", {}):
        problems.append(f"{method}: _meta should carry serverInfo")
    return problems

older = {"result": {"tools": [{"name": "ci_list_failures", "inputSchema": {"properties": {}}}]}}
current = {"result": {"resultType": "complete", "ttlMs": 3600000, "cacheScope": "public",
                      "tools": [{"name": "ci_list_failures", "inputSchema": {"type": "object"}}],
                      "_meta": {SERVER_INFO_KEY: {"name": "flaky-triage-lab", "version": "1.0.0"}}}}
version_error = {"error": {"code": -32022, "message": "Unsupported protocol version", "data": {"supported": ["2026-07-28"]}}}

for label, method, response in [("older", "tools/list", older), ("current", "tools/list", current), ("error", "tools/list", version_error)]:
    print(label, check_response(method, response) or "OK")
```

## Правило, яке варто перейняти: нестабільний тест чи регресія

Агент із лабораторної не відправляє в карантин кожен тест, що іноді падає. Він вважає тест нестабільним, лише якщо той знову пройшов після падіння на незміненому коді. Тест, що дев'ять разів пройшов і впав в останньому запуску, натомість позначається як імовірна регресія, бо карантин сховав би справжній баг за міткою «нестабільний».

Таке правило має жити в коді, де його можна протестувати, а не в промпті. Модель усе одно може допомогти, наприклад прочитати повідомлення про збої й запропонувати причину, але рішення про те, що можна сховати від збирання, лишається детермінованим і придатним до перегляду.

## Як розвивати лабораторну

Лабораторна навмисно невелика. Природні наступні кроки, кожен із яких відповідає розділу цього курсу:

- **Справжня модель.** Надішліть описи інструментів із `tools/list` в API провайдера й відображайте його виклики інструментів на `client.call_tool`, зберігши бюджет кроків і трасування ([Як працює AI-агент](/learn/agentic?topic=how-agents-work)).
- **Крок підтвердження.** Показуйте людині кожну пропозицію з конкретним тестом і причиною і лише потім викликайте окремий API карантину з перевіркою прав ([Підтвердження людиною й межі дій](/learn/agentic?topic=human-approval)).
- **Трасування вартості й затримки.** Додайте кількість токенів і час для кожного кроку й рахуйте їх на задачу ([Оцінювання та спостережуваність агентів](/learn/agentic?topic=agent-observability)).
- **HTTP-транспорт.** Віддавайте той самий обробник через Streamable HTTP з перевіркою `Origin` і прив'язкою до localhost ([Model Context Protocol](/learn/agentic?topic=model-context-protocol)).
- **Систематичні тести.** Додайте контрактні тести, property-based тести й внесення збоїв ([Тестування серверів MCP](/learn/llm?topic=agent-testing&section=testing-mcp-servers)).

## Типові помилки

- **Починати із загального асистента.** Широкі агенти важко оцінювати й легко використати не за призначенням; почніть з однієї задачі.
- **Немає перевірюваного результату.** Якщо не можна сказати, чи правильний запуск, не довіряючи агенту, його неможливо покращити.
- **Копіювати старий туторіал протоколу.** Перевірте, яку ревізію MCP підтримують ваші клієнт і сервер; приклади з початковим узгодженням не відповідають 2026-07-28.
- **Писати логи в stdout зі stdio-сервера.** Клієнт читає їх як зламані повідомлення протоколу.
- **Дії із записом без кроку пропозиції.** Тримайте важливі дії за підтвердженням із першої версії.
- **Класти рішення в промпти.** Правила на кшталт «не відправляй регресії в карантин» мають жити в протестованому коді.

## Підсумок

Будуйте вузьких агентів: одна задача, кілька строго описаних інструментів, перевірюваний результат і підтвердження для всього важливого. Вважайте обсяг, дозволи, обмеження, трасування, набір для оцінювання й README визначенням «готово». Лабораторна показує повну невелику систему на ревізії MCP 2026-07-28: discovery замість початкового узгодження, версію й можливості в кожному запиті, `resultType` у кожному результаті, строгі правила stdio і інструмент запису, який лише пропонує. Розвивайте її розділ за розділом, а важливі рішення тримайте в коді.
