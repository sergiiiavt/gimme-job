# Стан, пам'ять і RAG

Мовна модель нічого не пам'ятає між викликами. Усе, що вона знає під час виклику, — це текст, який ви надіслали саме в ньому: інструкції, описи інструментів, розмова, результати інструментів і знайдені документи. Те, що користувачі сприймають як «пам'ять» агента, — це інженерія застосунку: що зберігати, де і що повертати в наступний запит.

У цьому розділі: контекстне вікно як єдина робоча пам'ять моделі, які види стану має агент, як тримати довгі розмови в межах бюджету, пошук (retrieval) як пам'ять, довга пам'ять та її межі, а також Learning Path Advisor у GimmeJob як приклад. Як перевіряти якість пошуку, описано в розділі [Оцінювання систем RAG](/learn/llm?topic=rag-testing).

**Передумови:** [Як працює AI-агент](/learn/agentic?topic=how-agents-work), [Ембеддинги та схожість](/learn/llm?topic=embeddings-similarity).

## Контекстне вікно — єдина пам'ять

Кожен запит збирає контекст із кількох джерел:

```diagram
Системний промпт (роль, правила)     ─┐
Описи інструментів                    │
Довга пам'ять, яку ви вирішили додати ├──→  контекстне вікно  ──→  модель  ──→  відповідь або виклик інструмента
Документи, знайдені для цього кроку   │
Розмова до цього моменту              │
Результати інструментів із попередніх кроків ─┘
```

Вікно має жорсткий ліміт у токенах, але практичний ліміт нижчий. Моделі краще використовують інформацію на початку й наприкінці довгого входу, ніж посередині, як показало дослідження «Lost in the Middle», а Anthropic описує, що точність пригадування падає з ростом контексту. Тож більше контексту — не безкоштовно: кожен додатковий блок коштує грошей і часу і може витіснити з фокусу головне.

Робоче правило — те, що Anthropic називає context engineering: дати моделі найменший набір інформативних токенів, з яким вона добре зробить наступний крок.

## Чотири види стану

| Стан | Що містить | Скільки живе | Де зазвичай зберігається | Головний ризик |
|---|---|---|---|---|
| Розмова | Репліки цієї сесії | Одну сесію | Клієнт або серверне сховище сесій | Росте без меж |
| Робочий стан | План, прогрес, проміжні результати поточної задачі | Одну задачу | Середовище агента, файли, чернетка | Губиться при збої; застаріває після повторів |
| Довга пам'ять | Факти, що мають пережити сесію, як-от уподобання користувача | Від тижнів до назавжди | База даних або сховище пам'яті, окремо для кожного користувача | Хибні, застарілі чи підкинуті записи |
| Знання | Документи, які агент може знайти | Поки існує джерело | Пошуковий індекс над джерелом істини | Застарілий індекс, нерелевантні результати |

Розділити їх — це більша частина проєктування. Уподобання «відповідай українською» — довга пам'ять; «ми вже перевірили тест логіну» — робочий стан; розділ про HTTP-кешування — знання. У кожного свій власник, строк життя і правило видалення, а змішування робить кожен із них важчим для розуміння.

## Як тримати довгу розмову в межах бюджету

Рано чи пізно розмова або задача перестає вміщатися в бюджет, який ви готові витрачати на один запит. Поширені стратегії:

| Стратегія | Як працює | Компроміс |
|---|---|---|
| Ковзне вікно | Залишити системний промпт і найновіші репліки | Просто; забуває ранні факти |
| Стискання (summary, compaction) | Замінити старі репліки коротким підсумком | Зберігає суть; підсумок може загубити деталі або помилитися |
| Структуровані нотатки | Агент записує прогрес у файл чи сховище і перечитує його | Переживає довгі задачі; потребує дисципліни щодо формату |
| Субагенти | Помічник досліджує у власному контексті й повертає стислий результат | Головний контекст лишається малим; викликів більше |
| Пошук «вчасно» (just in time) | Зберігати посилання (id, шляхи до файлів) і підтягувати вміст лише за потреби | Мало контексту наперед; додаткові виклики інструментів |

Розумний варіант за замовчуванням — ковзне вікно з приміткою про те, що відкинуто. Код нижче залишає найновіші репліки, що вміщаються в бюджет токенів, а решту замінює підсумком-заглушкою. Кількість токенів оцінюється як один токен на чотири символи; справжня система використовувала б токенізатор провайдера.

```python
def fit_history(system, turns, budget):
    # An estimator for plain-text teaching messages, not a provider tokenizer.
    def cost(message):
        return 4 + (len(message["content"]) + 3) // 4

    system_message = {"role": "system", "content": system}
    latest_user = next((i for i in range(len(turns) - 1, -1, -1)
                        if turns[i]["role"] == "user"), len(turns))
    # Keep the latest request and every following reply together.
    for dropped in range(latest_user + 1):
        kept = turns[dropped:]
        notice = ([{"role": "system", "content": f"{dropped} older messages omitted."}]
                  if dropped else [])
        history = [system_message, *notice, *kept]
        used = sum(cost(message) for message in history)
        if used <= budget:
            return history, used
    raise ValueError("Budget cannot hold the system, omission notice and latest request")

turns = [
    {"role": "user", "content": "I test a payments API. Which status codes matter most?"},
    {"role": "assistant", "content": "Start with 200, 201, 400, 401, 403, 404, 409, 422 and 5xx handling. " * 6},
    {"role": "user", "content": "How do I test idempotency keys?"},
    {"role": "assistant", "content": "Send the same request twice with one key and compare the effects. " * 4},
    {"role": "user", "content": "And retries after a timeout?"},
]
history, used = fit_history("You are a QA mentor.", turns, budget=160)
for turn in history:
    print(turn["role"], "|", turn["content"][:70])
print("tokens used:", used)
```

Це оцінка для звичайного тексту. Повідомлення про пропуски також входить до бюджету; останній запит не видаляється. Якщо обов’язкові дані не вміщуються, приклад явно відмовляє. У production використовуйте tokenizer провайдера, резервуйте output-токени й зберігайте цілі групи tool-call/result. Не вставляйте неперевірений підсумок користувацького тексту як системні інструкції.

Що б ви не відкидали, робіть це свідомо й помітно. Тихе обрізання гірше за короткий підсумок, бо модель відповідатиме так, ніби відкинутих реплік ніколи не було.

## Пошук як пам'ять

Retrieval-augmented generation (RAG) перетворює великий обсяг знань на кілька релевантних фрагментів для кожного запиту: розбити джерела на шматки, обчислити ембеддинги, знайти шматки, найближчі до запиту, і додати їх у контекст разом із джерелом. Для агента пошук — це пам'ять, яка не вміщається в жодне вікно, і він може бути інструментом, який агент викликає, коли вирішує щось перевірити.

Три рішення важать більше, ніж вибір векторної бази:

- **Одиниця пошуку.** Шукайте розділи, а не цілі документи. На цьому сайті кожен розділ `##` навчального матеріалу — окремий документ для пошуку з власним deep link, тож відповідь може вказати на конкретний розділ.
- **Запит.** Останнє повідомлення користувача часто погано підходить як запит. «А повтори?» нічого не означає без попередньої репліки про платежі. Будуйте запит із розмови, а не лише з останнього рядка.
- **Посилання назад.** Зберігайте канонічне джерело для кожного шматка, щоб відповідь могла на нього послатися, а застосунок — звірити посилання з тим, що насправді знайшлося.

Якість пошуку можна виміряти: повноту знайдених релевантних фрагментів, точність того, що потрапляє в контекст, і чи лишається фінальна відповідь вірною їм. Ці перевірки описано в розділі [Оцінювання систем RAG](/learn/llm?topic=rag-testing).

## Довга пам'ять та її межі

Деякі продукти пам'ятають факти між сесіями: бажану мову, технологічний стек, рівень користувача. Довга пам'ять робить агента особистішим, але саме тут найлегше створити проблеми з приватністю й безпекою.

| Варто пам'ятати | Не зберігати |
|---|---|
| Сталі уподобання («відповідай українською», «пише на Playwright і TypeScript») | Секрети, токени, паролі, персональні ідентифікатори |
| Факти, які користувач сам повідомив про свою роботу | Здогадки моделі про користувача |
| Рішення, які не варто переглядати щоразу | Одноразові деталі окремої задачі |
| Вказівники на те, де щось лежить | Копії документів, які вже мають джерело істини |

Чотири правила роблять пам'ять безпечною:

- **Обмежуйте одним користувачем або тенантом.** Запис, зроблений в одному акаунті, ніколи не має читатися в іншому. Тестуйте це так само, як будь-яку іншу ізоляцію даних.
- **Дайте користувачу бачити, виправляти й видаляти пам'ять.** Пам'яті, яку не можна переглянути, неможливо довіряти.
- **Ніколи не записуйте пам'ять безпосередньо з недовірених даних.** Якщо вебсторінка чи лист, які прочитав агент, можуть створити запис у пам'яті, зловмисник може підкинути інструкції, що житимуть і в майбутніх сесіях. Це непряма prompt injection із довгим періодом дії.
- **Встановлюйте строк дії або перевіряйте заново.** Факти застарівають; запис із датою та джерелом можна перевірити, а без них — ні.

## Приклад: Learning Path Advisor

Advisor на сторінці [AI Assistant](/ai-assistant) радить навчальні матеріали цього сайту. Це хороший приклад того, як тримати стан простим.

```diagram
Браузер зберігає розмову й надсилає її з кожним запитом
        ↓
Контекстуалізація запиту: якщо нове повідомлення — коротке уточнення, додати попередню репліку користувача (без виклику моделі)
        ↓
Пошук: канонічний RAG по розділах навчальних матеріалів сайту, до 8 результатів, обраною мовою
        ↓
Маршрут: відповідь із матеріалів сайту, якщо щось знайшлося, інакше загальна відповідь
        ↓
Модель складає відповідь із посиланнями на знайдені джерела
        ↓
Перевірка обґрунтованості: прибрати кожне посилання, якого не було серед знайдених результатів
```

Рішення, які варто перейняти:

- **Сервіс не зберігає стану.** Розмова живе в браузері й приходить із кожним запитом, тож на сервері немає сесії, яка могла б витекти, застаріти чи загубитися. Ціна — клієнт щоразу надсилає історію.
- **Побудова контексту детермінована й трасується.** Правило уточнень — це звичайний код: повідомлення з чотирма чи менше змістовними словами вважається уточненням, і до пошукового запиту додається попередня тема користувача. Трасування показує, яка саме гілка спрацювала.
- **Пошук спільний з рештою сайту.** Advisor і MCP-сервер використовують один канонічний RAG-конвеєр, тож новий навчальний розділ стає доступним для пошуку в обох без окремої реєстрації.
- **Застосунок перевіряє посилання моделі.** Після того як модель написала відповідь, код прибирає кожне посилання на джерело, якого немає серед знайдених документів. Модель не може вигадати посилання, яке дійде до користувача.

## Типові помилки

- **Надсилати все щоразу.** Довгий контекст коштує дорожче, відповідає повільніше й ховає головне.
- **Тихо обрізати історію.** Підсумуйте або позначте відкинуте, інакше модель суперечитиме попереднім реплікам.
- **Шукати за сирим останнім повідомленням.** Короткі уточнення потребують розмови, щоб стати корисним запитом.
- **Шукати цілими документами.** Великі шматки розмивають релевантність і роблять посилання нечіткими.
- **Змішувати види стану.** Уподобання, прогрес задачі й знання потребують різного зберігання, строку життя й видалення.
- **Записувати пам'ять із недовірених даних.** Підкинуті інструкції тоді переходять у майбутні сесії.
- **Пам'ять без обмеження користувачем.** Пам'ять одного користувача в сесії іншого — це витік даних.

## Підсумок

Єдина пам'ять моделі — це контекст, який ви надсилаєте, і менший, точніший контекст зазвичай працює краще за більший. Розділяйте розмову, робочий стан, довгу пам'ять і знання, бо в кожного свій власник, строк життя й ризики. Тримайте довгі сесії в межах бюджету через свідоме обрізання, підсумки, нотатки чи субагентів. Використовуйте пошук як пам'ять, що не вміщається у вікно: шматки на рівні розділів, запити з урахуванням розмови й канонічні посилання. Ставтеся до довгої пам'яті як до даних користувача: обмежена ним, видима, з можливістю видалення і ніколи не записана з недовірених даних.
