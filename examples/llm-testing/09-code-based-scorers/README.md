# Code-based scorers

Chapter: [Code-based scorers and metrics](https://gimme-job.com/learn/llm?topic=code-based-scorers)

Code-based scorers are the cheapest and most reproducible layer of evaluation, and they are software: they need tests, validation against human labels and a version. This project scores the recorded answers of a bilingual (English and Ukrainian) support assistant and the SQL generated by a text-to-SQL feature.

| File | Content |
|---|---|
| `text_metrics.py` | SQuAD exact match and token F1 with Unicode-aware normalization, sentence and corpus BLEU, ROUGE-N and ROUGE-L, written out step by step |
| `classification.py` | Confusion matrix, per-class precision, recall and F1, macro and weighted F1. Command-line tool |
| `fact_scorer.py` | Required facts, forbidden claims and unsupported numbers, with accepted wordings in English and Ukrainian |
| `validate_scorer.py` | Agreement of the fact scorer with human labels, split into false passes and false failures. Command-line tool |
| `scorers.py` | The answer contract and the scorers for length, language, facts, citations, links and personal data |
| `harness.py` | Every scorer on every case, pass rates by slice, and a comparison of two versions of the assistant re-scored by the same scorer version. Command-line tool |
| `sql_scorer.py` | Execution-based scoring of generated SQL on read-only fixture databases with a step budget. Command-line tool |
| `data/cases.jsonl`, `data/policies.json` | 12 support questions in two languages with the retrieved policies, required facts and forbidden claims |
| `data/outputs_v1.jsonl`, `data/outputs_v2.jsonl` | Recorded answers of two versions of the assistant |
| `data/labelled_answers.jsonl` | 20 answers with human labels: the regression test of the fact scorer |
| `data/triage_labels.jsonl` | 20 triaged messages with human and model labels, the classification example of the chapter |
| `data/sql_cases.jsonl` | 10 questions with a reference query and a recorded generated query |
| `test_*.py` | Worked examples, property-based tests with Hypothesis, adversarial outputs, agreement with human labels, the harness and the SQL safeguards |

## Compare two versions of the assistant

```bash
cd examples/llm-testing/09-code-based-scorers
uv run --project .. python harness.py data/outputs_v2.jsonl --baseline data/outputs_v1.jsonl
```

## Validate the fact scorer against human labels

```bash
uv run --project .. python validate_scorer.py data/labelled_answers.jsonl
uv run --project .. python validate_scorer.py data/labelled_answers.jsonl --naive
```

The scorer agrees with all 20 human labels. The `--naive` variant is its first version, which accepted only numbers found in the retrieved policies:

```text
fact scorer (numbers from sources only): agrees with human labels on 16/20 answers
  false passes (accepts what humans reject): none
  false failures (rejects what humans accept): a01, a02, a07, a15
    a01: unsupported numbers: 40
    a02: unsupported numbers: 40
    a07: unsupported numbers: 1042
    a15: unsupported numbers: 40
```

Good answers repeat the customer's own numbers ("after 40 days", "order A-1042"). The command exits with status 1 when the scorer disagrees with any label, so it can run in CI whenever a scorer or the labelled set changes.

## Score generated SQL by executing it

```bash
uv run --project .. python sql_scorer.py data/sql_cases.jsonl
```

```text
s1 PASS same rows on 2 databases
s2 FAIL base database: expected [(330.0,)], got [(555.4,)]
s3 PASS same rows on 2 databases
s4 FAIL boundary database: expected [('A-1001',), ('A-1004',), ('A-1008',)], got [('A-1001',), ('A-1004',), ('A-1007',), ('A-1008',)]
s5 FAIL boundary database: expected [(670.4,)], got [(970.4,)]
s6 FAIL base database: expected [('maria',), ('olena',)], got [('olena',), ('maria',)]
s7 FAIL base database: DatabaseError: not authorized
s8 FAIL base database: ProgrammingError: You can only execute one statement at a time.
s9 FAIL base database: OperationalError: interrupted
s10 FAIL base database: OperationalError: near "SELEC": syntax error
execution accuracy: 2/10
```

`s1` and `s3` differ from the reference query in text and still pass. `s4` (`>=` instead of `>`) and `s5` (a forgotten filter on cancelled orders) return the right rows on the base database by coincidence; the boundary database catches both. The writes in `s7` and `s8` are refused, and the accidental cross join in `s9` is interrupted by the step budget instead of hanging the evaluation.

## Classification metrics

```bash
uv run --project .. python classification.py data/triage_labels.jsonl
```

The output is the confusion matrix and the per-class report from the chapter, computed from a labelled file instead of an inline list.

## What the tests show

- Token overlap rewards wording, not truth: "60 days from delivery" gets a higher token F1 than a correct paraphrase, and BLEU and ROUGE score a wrong number and an opposite meaning around 0.7 to 0.9.
- Property-based tests check every metric on generated text: scores stay between 0 and 1, identical text gets the maximum score, token F1 is symmetric, normalization is idempotent. The empty-input guard in BLEU exists because the brevity penalty of two empty texts would otherwise be e ≈ 2.72.
- Every fact pattern has wordings it must accept and near misses it must reject, in both languages, including all three apostrophes used in Ukrainian text.
- Known limits are pinned by tests rather than hidden: a forbidden pattern cannot read negation ("not guarantees"), and a short Russian sentence without ы, э, ъ or ё passes the language check.
- Scorers never crash on malformed output (deeply nested JSON raises `RecursionError` inside `json.loads`) and stay fast on runaway output: the first e-mail pattern needed about 3 seconds for 20,000 characters, the current one about 0.1 seconds for 200,000.
- The default tokenizer of the rouge-score package keeps only a-z and 0-9, so it sees no Ukrainian words at all; `tokenize` in `text_metrics.py` keeps every script.
